# 상품 관리 설계 (거래 상태 변경 · 삭제 · 상태 필터)

**바퀴**: RN 앱 5바퀴 · **선행**: #791(마이 목록 3종, PR #792 머지 완료)
**작성일**: 2026-07-29 (수)

## 1. 무엇을 만드는가

판매 내역 · 구매 내역 목록에서 **상품을 관리**할 수 있게 한다.

| 기능 | API |
|---|---|
| 거래 상태 변경 | `PATCH /products/{id}/trade-status` (이미 있음) |
| 삭제 | `DELETE /products/{id}` (이미 있음) |
| 상태 필터 | 목록 조회에 `tradeStatus` 파라미터 **추가 필요** |

세 저장소를 함께 건드린다.

- **앱**: 관리 UI 전부
- **백엔드**: 목록 조회에 선택적 `tradeStatus` 파라미터
- **웹**: 그 파라미터를 쓰도록 전환(§5). 모바일 폭 ⋮ 메뉴는 이번에 손대지 않는다(§6)

### 범위 밖

| 항목 | 언제 | 왜 |
|---|---|---|
| 상품 수정 | 6바퀴 | 수정 화면이 없으면 메뉴를 만들어도 갈 곳이 없다 |
| 찜한 상품의 필터 · 관리 | — | 찜 목록은 고르는 곳이지 관리하는 곳이 아니다 |
| 대시보드(웹)에 관리 붙이기 | — | **미리보기에는 되돌릴 수 없는 동작을 붙이지 않는다**(#791 설계 §9) |
| 웹 모바일 폭 ⋮ → 하단 시트 | **#793** | 결함이 아니라 개선. 웹에 하단 시트 패턴이 없고 레이어 다툼이 따라온다(§6) |

## 2. 앱 화면

```
← 뒤로   판매 내역
┌────┐ ┌─────┐ ┌─────┐ ┌──────┐     ← 칩 필터
│전체│ │판매중│ │예약중│ │판매완료│
└────┘ └─────┘ └─────┘ └──────┘
내가 등록한 상품            [+ 상품 등록]
전체 2                      ← 필터 이름 + 개수
┌──────────────────────────┐
│ [사진] 퍼피러브 하네스      ⋮ │  ← ⋮ 는 정보 영역 오른쪽 위
│        15,000원            │
│        은평구 · 찜 2   3일 전 │
└──────────────────────────┘
```

**칩 필터**는 웹과 같은 모양이다(웹 `Tabs variant="card-pill"`). 선택된 칩은 브랜드 브라운 채움 + 흰 글자, 나머지는 흰 배경 + 브라운 테두리·글자.

**개수 라벨**은 `상품 2`가 아니라 **`전체 2`** — 선택된 필터 이름 + 개수다. 웹이 그렇게 한다. 필터를 바꾸면 `판매중 1`로 바뀐다.

**필터 목록**

| 화면 | 칩 |
|---|---|
| 판매 내역 | 전체 · 판매중 · 예약중 · 판매완료 |
| 구매 내역 | 전체 · 요청중 · 구매완료 |

구매 내역에 `예약중`이 없는 것은 웹과 같다(`TRADE_STATUS_LABEL`).

### ⋮ → 하단 시트

```
┌────────────────────┐
│  판매중으로 변경      │
│  예약중으로 변경      │
│  판매완료로 변경      │
│  삭제               │   ← 빨강, 맨 아래
└────────────────────┘
```

- 아래에서 올라오고, **바깥을 누르면 닫힌다.** 취소 버튼을 따로 두지 않는다
- 위쪽 모서리만 둥글게, 손잡이 바 없음, 제목 없음, 항목 **가운데 정렬** + 얇은 구분선
- **문구는 동사형** — `판매중` 이 아니라 `판매중으로 변경`. 웹 드롭다운은 라벨만 적어서 "지금 상태 표시인가, 바꾸는 건가"가 헷갈린다

### 삭제 → 확인 창

「삭제」를 누르면 시트가 닫히고 확인 창이 뜬다. **상품 제목을 보여준다** — 무엇을 지우는지 눈으로 확인해야 한다. 웹도 제목·가격·사진을 확인 모달에 띄운다.

탈퇴 모달과 같은 껍데기를 쓴다(가운데 모달 · 모서리 8 · 확인 버튼 `#DC2626`).

## 3. 메뉴 규칙

웹과 같다.

| 화면 | 완료 전 | 완료 후 |
|---|---|---|
| 판매 내역 | 현재 상태를 뺀 나머지 + `판매완료로 변경` | **상태 변경 항목 없음** — 삭제만 |
| 구매 내역 | `구매완료로 변경` | 삭제만 |

**완료는 종착역이다.** 웹 `MyList`도 `isCompleted`면 상태 변경 항목을 전부 감춘다. 거래가 끝난 뒤 되돌리는 건 서버가 허용하더라도 화면에서 열어주지 않는다.

`TradeStatus` 값은 `SELLING` · `RESERVED` · `COMPLETED` 셋뿐이다(서버 enum 확인. `BUYING`은 주석 처리되어 있다).

## 4. 백엔드 — 필터를 서버로 옮긴다

### 지금 무엇이 문제인가

웹은 **이미 받아온 페이지에서만** 거른다.

```js
myProductsData?.pages.flatMap(page => page.content)
  .filter(p => p.tradeStatus === activeTradeStatus)
```

그리고 `/profile/me/products`는 `Pageable`만 받는다. 그래서 이런 일이 생긴다.

```
상품 50개 = 판매중 45 + 판매완료 5 (판매완료는 오래돼서 뒤쪽 페이지에 있음)
첫 페이지 20개는 전부 판매중
「판매완료」 필터 → 0개 → "등록한 상품이 없습니다"
   실제로는 5개가 있다. 스크롤을 더 내려야 나타난다.
```

상품이 20개를 안 넘으면 아무도 눈치채지 못한다. 늘어나면 **"필터를 켰더니 없다고 나온다"** 가 된다.

### 어떻게 고치나

```
GET /profile/me/products?page=0&size=20&tradeStatus=COMPLETED
GET /profile/me/purchase-requests?page=0&size=20&tradeStatus=COMPLETED
```

`tradeStatus`는 **선택적**이다. 안 주면 지금처럼 전부 돌려준다. 따라서 **기존 호출이 그대로 동작하고**, 앱·웹 배포 순서에 매이지 않는다. 서버를 먼저 올려도 아무것도 깨지지 않는다.

`/profile/me/favorites`에는 추가하지 않는다 — 찜 목록에는 필터가 없다.

## 5. 웹 — 필터를 서버 조회로

- 조회 함수에 `tradeStatus`를 넘긴다
- `activeTradeStatus`를 **쿼리 키에 넣는다** → 필터를 바꾸면 새로 조회한다
- 화면에서 거르던 코드(`.filter(p => p.tradeStatus === ...)`)와 `filteredMyProductData` 류를 **제거**한다
- 개수(`전체 2`)도 서버가 준 `total`을 그대로 쓴다. 지금은 걸러낸 배열 길이를 쓰고 있어 같은 결함을 갖는다

## 6. 웹 모바일 폭의 ⋮ 는 이번에 손대지 않는다

앱이 하단 시트를 쓰게 되므로 웹 모바일 폭(`!isMd`)의 ⋮ 도 하단 시트로 맞추는 안을 검토했다. **이번 바퀴에서는 하지 않는다.**

지금 웹은 버튼 옆에 붙는 드롭다운이다.

```tsx
<div className="... absolute top-7 right-0 ... rounded-lg border bg-white">
```

**왜 미루나**

- **웹에 하단 시트 패턴이 없다.** 모달 12개가 전부 `<dialog>` 가운데 모달이다. 새로 만들면 포커스 가두기 · ESC · 배경 스크롤 잠금까지 따라온다
- **웹에는 하단 고정 네비(`BottomNav`)가 있다.** 시트가 그 위로 겹쳐야 해서 레이어 다툼이 생긴다
- **그 다툼이 이미 미해결로 남아 있다.** #788의 `SelectDropdown` 건이 정확히 `<dialog>`의 top-layer 문제이고 아직 보류 중이다. 웹에서 겹치는 레이어를 새로 만드는 것은 이 저장소에서 이미 까다롭다고 확인된 영역이다
- **지금 드롭다운이 불편한지 확인되지 않았다.** 항목이 4개(상태 3 + 삭제)라 드롭다운으로도 감당된다. 불편을 확인하기 전에 고치는 것은 순서가 거꾸로다
- **이건 결함이 아니라 개선이다.** 이번에 웹을 건드리는 이유는 §5의 필터 결함이다. 성격이 다르다

**언제 하면 좋은가**

모바일 웹에서 실제로 써보고 드롭다운이 불편하다는 근거가 생겼을 때. 그때는 #788의 `SelectDropdown` 건과 묶어 **"웹의 겹치는 레이어 정리"** 로 한 번에 하는 편이 낫다. **이슈 #793으로 남겨 두었다.**

> 이번 주에 반복해서 나온 결론과도 맞는다 — **상황이 다르면 모양이 달라도 된다.** 빈 상태는 홈과 마이 목록을 일부러 다르게 뒀고(웹도 그렇다), 모달 정렬도 짧은 확인창만 가운데로 했다. "무조건 통일"은 원칙이 아니다.

## 7. 데이터 흐름

### 쿼리 키에 필터를 넣는다

```ts
['my', 'products', tradeStatus]     // tradeStatus: 'ALL' | 'SELLING' | 'RESERVED' | 'COMPLETED'
['my', 'purchases', tradeStatus]
```

필터를 바꾸면 **새 무한스크롤이 시작**된다. 이전 필터의 결과는 캐시에 남아 있어 되돌아오면 즉시 보인다.

### 상태 변경 · 삭제 후

**해당 목록을 무효화한다.** 찜과 달리 여기서는 **항목이 사라지는 게 맞다** — 「판매중」 필터를 보고 있다가 판매완료로 바꿨으면 그 목록에 없는 것이 옳다.

상세 캐시(`['product', id]`)도 함께 무효화한다. 상태가 바뀌었으니 상세의 뱃지도 달라져야 한다.

### 낙관적 갱신을 하지 않는다

요청이 끝난 뒤 다시 받는다. 이유:

- 4바퀴에서 찜 낙관적 갱신이 **현재 값을 어디서 읽느냐**에 걸려 방향이 뒤집힌 적이 있다. 여기는 상태가 3가지라 더 얽힌다
- **삭제는 되돌릴 수 없다.** 먼저 지운 척했다가 실패하면 되살릴 방법이 마땅치 않다
- 이 동작들은 찜처럼 연타하는 성격이 아니다. 한 번 누르고 결과를 기다려도 어색하지 않다

요청 중에는 시트를 닫고 해당 카드를 흐리게 둔다.

## 9. 검증

### 단위 테스트

- `product-actions.ts`: 상태 변경(경로 · 본문 `{tradeStatus}` · 토큰), 삭제(경로 · 메서드), 실패 시 오류
- `my-lists.ts`: `tradeStatus`를 주면 쿼리에 붙고, 안 주면 안 붙는다

### 실기기

1. 판매 내역 → ⋮ → 시트가 올라온다. 현재 상태 항목은 **없다**
2. 「예약중으로 변경」 → 목록 카드의 뱃지가 바뀐다
3. 상세로 들어가면 상세 뱃지도 바뀌어 있다
4. 「판매완료로 변경」 → 다시 ⋮ 를 열면 **상태 변경 항목이 사라져 있다**
5. 필터 「판매중」 → 방금 완료한 상품이 목록에서 빠진다. 개수 라벨이 `판매중 N`으로 바뀐다
6. 구매 내역 → 시트에 `구매완료로 변경`만 있다
7. **삭제(버릴 상품으로 한 번)** → 확인 창에 제목이 보이고, 확인하면 목록에서 사라진다
8. 시트 바깥을 누르면 닫힌다

### 웹

- 필터를 바꾸면 **새 요청이 나간다**(네트워크 탭)
- 20개가 넘는 목록에서 뒤쪽 페이지에만 있던 상태도 필터에 잡힌다
- ⋮ 메뉴와 데스크탑은 그대로다(이번에 안 건드림)

### 게이트

- 앱: `npx tsc --noEmit` · `npx jest` · `npx expo lint`
- 웹: `npx tsc --noEmit` · 변경 파일 `npx eslint`
- 백엔드: EC2에서 빌드 (이 맥에는 JDK 11만 있어 컴파일 확인 불가 — #784 때와 같음)
