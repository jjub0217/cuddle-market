# 앱 비밀번호 찾기 — 설계 (2026-08-05 · #838)

> 14바퀴. 앱에 비밀번호 찾기 화면을 만들고, 그 김에 웹의 소셜 계정 안내도 함께 손본다.

## 0. 왜 지금인가

3바퀴 설계 §8.2에서 이 링크를 **일부러 뺐다** — 「앱에 해당 화면이 없어 눌러도 갈 곳이 없다. 소셜/회원가입 바퀴에서 화면과 함께 살린다」. 그 바퀴가 지났고, #829에서 **링크만 먼저 살려** 웹 페이지를 앱 밖 브라우저로 열게 해 뒀다. 이제 화면을 만든다.

「웹 페이지를 앱에서 보기 좋게 다듬는다」와 「앱 안에 화면을 만든다」 중 **후자를 골랐다**(2026-08-05). 앞의 것은 앱을 벗어나는 흐름이 남고, 비밀번호 재설정은 로그인 직전 단계라 앱을 벗어나면 되돌아오지 않는 사람이 생긴다.

## 1. 뼈대 — 화면은 배치만, 로직은 훅

```
mobile/app/find-password.tsx                     화면. 단계별로 무엇을 보여줄지만 정한다
mobile/lib/find-password/use-find-password.ts    값·단계·타이머·검증·서버 호출
mobile/lib/find-password/api.ts                  서버 주소 셋
```

가입 화면이 이미 이 구조다. `lib/signup/use-signup-form.ts` 주석이 이유를 적어 뒀다 — *「화면은 이걸 어떻게 배치할지만 정한다. 그래서 A안(한 화면)과 B안(2단계)이 로직을 통째로 공유한다」*. 같은 결로 간다.

## 2. 보이는 것은 웹·가입과 같게, 코드만 따로

**먼저 층을 갈라 둔다.** 아래 이야기가 세 가지 다른 뜻으로 읽힐 수 있어서다.

```
① 웹 ↔ 앱          화면 조각은 애초에 나눠 쓸 수 **없다**. 웹은 <div>, 앱은 <View> —
                    그리는 엔진이 다르다. 여기서 「웹과 같이 간다」는 **같은 설계도로
                    각자 짓는다**는 뜻이지 같은 파일을 쓴다는 뜻이 아니다.
                    실제로 나눠 쓰는 것은 packages/shared 의 순수 로직·문구뿐이다
                    (예: 탈퇴 안내 WITH_DRAW_ALERT_LIST · 신고 사유 목록).

② 앱 안: 가입 ↔ 재설정   둘 다 React Native 라 조각을 나눠 **쓸 수는 있다.**
                    그런데 서버 사정이 달라 안 쓰기로 했다 (아래 「새로 쓴다」).

③ ② 안에서 다시      서버를 **모르는** 것은 같이 쓴다 (Field · PasswordChecklist · 검증 함수)
                    서버를 **아는** 것은 각자 갖는다 (api.ts · 훅)
                    경계는 「서버를 아는가」다.
```

⚠️ **②에서 조각 하나를 안 가져온다고 화면이 달라 보이는 것이 아니다.** 안 가져오는 것은
부품들을 「이렇게 배열해라」로 묶어 둔 껍데기 하나뿐이고, 부품(칸 모양·체크리스트·검증 규칙·
타이머 표시)은 그대로 쓴다. 그래서 **눈에는 가입 화면과도, 웹과도 같아 보인다.**

### 재사용하는 것과 새로 쓰는 것

| | 무엇 |
| --- | --- |
| **그대로 쓴다** | `components/signup/field.tsx` (라벨 + 칸 + 오류)<br>`components/signup/password-checklist.tsx`<br>`lib/signup/validation.ts` 의 `validateEmail` · `validatePassword` · `validatePasswordConfirm` · `passwordRules` |
| **새로 쓴다** | `api.ts` — 서버 주소가 가입과 **다르다**(§4)<br>훅 — 가입 훅은 칸 9개 + 닉네임 중복확인까지 들고 있어 무겁다 |

⚠️ **`components/signup/email-verification.tsx` 는 못 쓴다.** props 가 `form: ReturnType<typeof useSignupForm>` 통째라 다른 훅을 받지 못한다. 타이머 표시(`3:00` 꼴)만 같은 모양으로 새로 그린다.

**가입 조각을 억지로 나눠 쓰지 않는 쪽을 골랐다**(위 ②). 두 화면이 부르는 서버 주소가 달라서(§4), 하나로 묶으면 「어느 주소를 쓸지」·「무엇이 오류인지」를 밖에서 넘기는 구조가 된다.

```tsx
// 하나로 묶으면 이렇게 된다
<EmailVerification
  onSend={가입이냐 재설정이냐에 따라 다른 함수}
  onVerify={또 다른 함수}
  errorPolicy={가입은 「이미 있는 이메일」이 오류, 재설정은 「없는 이메일」이 오류}
/>
```

조각 하나가 **가입 사정과 재설정 사정을 둘 다** 짊어지게 된다. 그러면 가입 규칙 하나를 고칠 때 재설정 화면이 조용히 깨진다. 이 저장소가 이미 겪은 함정이다 — `formatPrice` 를 웹·앱이 다른 뜻으로 쓰다 부딪혔다(2바퀴).

## 3. 화면과 단계

한 화면 안에서 3단계. **웹과 같은 흐름이다** — 웹도 주소 하나(`/auth/find-password`)에서 한 번에 한 단계씩 보여준다(`FindPasswordForm.tsx`).

```
┌──────────────────────┐
│ ‹    비밀번호 찾기     │   헤더는 로그인 화면과 같은 모양
│  ①━━②──③            │   단계 표시
│                       │
│  [단계별 안내 문구]     │   앞 단계 값을 여기서 알린다
│  [칸        ] [단추]   │   ← 단추는 칸 **옆**이다 (아래 참고)
└──────────────────────┘
```

**단추는 칸 옆에 둔다** (2026-08-05 실기기 확인 뒤 정정).

```
1단계   [example@gmail.com  ] [인증받기]
2단계   [6자리 인증코드      ] [확인]        남은 시간 4:32
3단계   새 비밀번호는 칸 둘이라 아래 전체폭 단추(비밀번호 변경) 그대로다
```

처음에는 이 그림을 「칸 아래 전체폭 단추」로 그렸다. **웹 비밀번호 찾기만 보고 그린 것**이고,
**앱 회원가입이 이미 칸 옆(trailing)을 쓰고 있다는 걸 대조하지 않았다**
(`components/signup/email-verification.tsx`).

웹과 앱 중 어느 쪽에 맞출지 충돌할 때는 **같은 앱 안의 일관성이 먼저다.** 사용자는 웹과 앱을
나란히 놓고 비교하지 않지만, 앱 안에서 가입과 비밀번호 찾기는 며칠 사이에 둘 다 겪는다.

단추 모양은 `components/signup/field.tsx` 의 `fieldStyles.button` 을 그대로 쓴다.

**앞 단계는 칸을 남기지 않고 헤더 문구로 알린다** — 웹과 같은 방식이다.

```
2단계 헤더:  이메일 인증
            ○○○@메일로 인증코드를 발송했습니다.
```

처음에는 「앞 단계를 읽기 전용 칸으로 남기자」고 제안했다가 물렀다. 목적(어느 계정을 고치는 중인지 보여주기)은 같은데 웹만 다른 방법을 쓰면 두 화면이 갈린다.

**단계 표시는 넣는다.** 웹 `StepIndicator` 에 해당한다. 다만 넣은 뒤 **뺀 모습도 만들어 비교하고 최종 결정**한다(2026-08-05 사용자 요청).

**뒤로가기**: 2·3단계에서는 앞 단계로, 1단계에서는 화면을 닫는다. 가입 화면과 같은 규칙이다.

## 3-1. 웹과 앱이 갈릴 때 — 무엇을 먼저 보는가 (2026-08-05 추가)

이 바퀴에서 「웹에 맞출까, 앱에 맞출까」가 **여러 번** 나왔다. 그때마다 같은 기준으로 정했으니 적어 둔다.

```
같은 앱 안의 일관성이 먼저다.
```

**왜** — 사용자는 웹과 앱을 나란히 놓고 비교하지 않는다. 하지만 앱 안에서 가입과 비밀번호 찾기는
며칠 사이에 둘 다 겪는다. 웹·앱이 조금 다른 것보다, 같은 앱 안에서 같은 일을 다르게 하는 것이
더 크게 걸린다.

실제로 이 기준으로 갈라진 것들:

| | 웹 | 앱 | 왜 |
| --- | --- | --- | --- |
| 인증 단추 자리 | 칸 아래 전체폭 | **칸 옆** | 앱 가입 화면이 칸 옆을 쓴다 |
| 단계 표시 이름표 | 있다 | **없다** | 앱은 가로가 좁고, 본문 제목이 같은 말을 해서 겹쳤다 |
| 칸↔단추 간격 | 24 | 16 | 폰은 좁아 24가 헐겁다 |

**반대로 웹에 맞춘 것도 있다** — 화면 구조(한 화면 3단계), 앞 단계를 헤더 문구로 알리는 방식,
단계 표시의 크기(동그라미 32·숫자 16), 단추 둘 사이 간격(10), 문구.

기준을 다시 쓰면 이렇다.

```
뜻·문구·흐름      웹에 맞춘다 — 같은 서비스가 두 말을 하면 안 된다
자리·크기·간격     그 판이 이미 쓰는 규칙을 따른다 — 화면 크기가 다르면 답도 다르다
```

⚠️ **갈릴 때는 이유를 코드 주석에 남긴다.** 안 남기면 다음 사람이 「어? 왜 다르지」 하고
되돌린다. 이 바퀴에서 실제로 그 주석들이 여러 번 판단 근거가 됐다.

## 4. 서버와의 대화

DTO 를 직접 열어 확인했다(추측하지 않는다 — 저장소 규칙).

```
1  POST  /auth/password/reset/send     { email }
2  POST  /auth/password/reset/verify   { email, verificationCode }
3  PATCH /auth/password/reset          { email, newPassword, confirmPassword }
```

**함정 둘.**

```
① 가입과 주소가 다르다
   가입     /auth/email/verification/send · /verify
   재설정   /auth/password/reset/send · /verify
   → 훅·api 를 새로 쓰는 이유가 이것이다

   ⚠️ 보내는 값은 똑같다(이메일 하나, 그다음 이메일+코드). 그런데도 주소가 갈린 이유는
      **서버가 하는 일이 정반대**라서다.

        가입 send      사용자를 찾아보지도 않는다. 그냥 코드를 만들어 메일로 보낸다
                       (AuthController:123 → sendEmailVerificationCode)
        재설정 send    ① 그 이메일로 가입한 사람이 있나?  없으면 거절
                       ② 그 사람이 LOCAL 계정인가?       소셜이면 거절
                       ③ 그제서야 코드를 만들어 보낸다
                       (AuthServiceImpl:188~204)

        가입     「이 이메일 처음이신가요?」   처음이어야 통과
        재설정   「이 이메일로 가입한 적 있나요?」  있어야 통과

      같은 열쇠 구멍처럼 생겼지만 안쪽 자물쇠가 다르다. §2 ②에서 조각을 나눠 쓰지
      않기로 한 근거가 여기다

② 3번은 confirmPassword 도 보내야 한다
   PasswordResetRequest.java 에 @NotBlank 로 셋 다 필수다.
   「확인 칸은 앱에서만 검사하면 되겠지」 하고 빠뜨리면 400 이 난다
```

셋 다 `SecurityConfig` 의 `permitAll` 이라 **로그인 없이 부를 수 있다**. 그래서 앱의 `apiFetch`(토큰을 붙이는 래퍼)가 아니라 맨 `fetch` 를 쓴다 — 가입 api 가 이미 그렇게 한다.

## 5. 어긋났을 때

| 경우 | 앱이 하는 일 |
| --- | --- |
| 등록되지 않은 이메일 | 서버 메시지 그대로 (「등록되지 않은 이메일입니다」) |
| **소셜로 가입한 계정** | 안내 + 「로그인하러 가기」 단추 (§6) |
| 코드가 틀림·만료 | 칸 아래 오류. 만료면 「재발송」으로 다시 받는다 |
| 네트워크 | 앱의 다른 화면과 같은 토스트 |

**실패하면 단계를 넘기지 않는다.** 웹이 이걸 어겨서 버그가 됐다(#836 — 전송이 실패해도 인증코드 칸이 떴다). 앱은 처음부터 「성공했을 때만 전진」으로 만든다.

## 6. 소셜 계정 — 웹도 함께 고친다

서버가 1단계에서 막는다.

```java
// AuthServiceImpl.sendPasswordResetCode
if (user.getProvider() != AuthProvider.LOCAL) {
    throw new IllegalArgumentException("소셜 로그인 사용자는 비밀번호 재설정이 불가능합니다.");
}
```

지금은 웹도 앱도 이 문장 한 줄이 전부다. **그런데 여기 온 사람은 대개 「카카오로 가입한 걸 잊고」 이메일 로그인을 시도하다 실패해서 온 사람**이다. 「불가능합니다」만 보여주면 다음에 뭘 해야 할지 모른 채 막힌다.

**안내와 함께 길을 준다.**

```
카카오·구글로 가입한 계정이에요.
그 방법으로 로그인해 주세요.
              [로그인하러 가기]
```

**웹도 같은 대접을 한다**(2026-08-05 결정). 앱만 고치면 같은 사람이 웹에서 또 막힌다.

## 7. 성공한 뒤 — 여기는 웹과 다르다. 웹도 함께 고친다

이메일 로그인 화면으로 `replace` 하고 토스트로 알린다 — *「비밀번호를 바꿨어요. 새 비밀번호로 로그인해 주세요.」*

**웹이 지금 하는 일과 비교하면 이렇다.**

```js
// 웹 FindPasswordForm.tsx:131
setTimeout(() => { router.push(ROUTES.LOGIN) }, 1500)
```

| | 웹(지금) | 앱(설계) |
| --- | --- | --- |
| 이동 방식 | `push` | `replace` |
| 어디로 | `/auth/login` | 이메일 로그인 화면 |
| 알림 | **없다** · 1.5초 멈췄다 이동 | 토스트 |

**① `replace` 인 이유** — 앱은 화면을 스택으로 쌓아서 `push` 로 가면 뒤로가기로 방금 끝낸 재설정 화면에 돌아온다. 이미 다 쓴 화면이다.

**② 「이메일 로그인 화면」은 웹의 `/auth/login` 과 같은 자리다.** 웹은 로그인이 화면 하나뿐이지만 앱은 관문과 이메일 로그인 둘로 나뉘어 있다. 새 비밀번호로 로그인하려면 **칸이 있는 화면**이어야 하므로 이메일 로그인이 그 자리다.

**③ 웹에는 성공 알림이 빠져 있다.** 1.5초를 기다리는 것은 성공 메시지를 보여주려던 자리로 보이는데 정작 메시지가 없다. 사용자에게는 **「눌렀는데 멈췄다가 갑자기 화면이 바뀐」** 것으로 보이고, 바뀐 게 맞는지도 알 수 없다.

**웹에도 성공 안내를 넣는다**(2026-08-05 결정). 어차피 §6 소셜 안내로 같은 파일을 손대고, 지금 상태는 「성공했는지 알 수 없다」는 실제 불편이다.

## 8. 진입점

```
로그인 관문(app/login.tsx)     아래 「비밀번호 찾기 │ 회원가입」 줄 — 웹 링크를 라우트로 바꾼다
이메일 로그인(email-login)      비밀번호 칸 아래에 새로 넣는다 — 웹이 링크를 두는 자리다
```

관문에만 두면 비밀번호를 틀렸을 때 한 화면 뒤로 나가야 찾기가 보인다. 둘 다 둔다.

**`FIND_PASSWORD_URL` 은 지운다.** 화면이 생기면 쓸 데가 없다. 쓰는 곳이 관문 한 곳뿐인 것을 확인했다(`lib/support-links.ts`).

## 9. 시험 (Jest · 앱)

```
lib/find-password/use-find-password.test.ts   단계 전이(1→2→3) · 타이머 · 실패하면 단계가 안 넘어감
lib/find-password/api.test.ts                 주소·본문이 DTO와 맞는지 · 실패 응답 처리
```
