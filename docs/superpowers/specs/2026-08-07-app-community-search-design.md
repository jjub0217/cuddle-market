# 앱 커뮤니티 검색·정렬 설계 (#857)

> 17바퀴. 16바퀴(#855)에서 상품에 붙인 검색·필터를 커뮤니티에도 붙인다.
> 다만 **상품과 일부러 다르게 간 곳이 있다** — §2에 이유를 적었다.

## 1. 무엇이 없나

```
웹 커뮤니티   목록 화면에 검색창 + 정렬 셋
앱 커뮤니티   GET /community/posts?boardType=&page=&size=   ← 조건이 없다
```

10바퀴(커뮤니티 읽기+댓글)에서 일부러 미뤘고 코드에도 적어 뒀는데, 일정을 안 잡아 잊고 있었다
(`mobile/app/(tabs)/(community)/index.tsx:15`).

**서버 작업은 0이다.** 직접 열어 확인했다.

```
CommunityController.java:95-102     searchType · keyword · sortBy 를 다 받는다
PostRepositoryCustomImpl.java:56-72  검색 종류 셋이 진짜로 돈다
                                     title · title_content · writer
PostRepositoryCustomImpl.java:112-127 정렬 넷이 진짜로 돈다
                                     latest · oldest · views · comments
```

⚠️ 값이 안 맞으면 400을 던지지 않고 **그냥 무시하고 조건 없이 조회한다.**

## 2. 상품과 다르게 가는 곳

### 검색을 목록 안에 둔다 (상품은 별도 화면)

15바퀴에서 상품 검색을 별도 화면으로 뺀 근거 셋 중 **둘이 커뮤니티에는 안 맞는다.**

```
① 모바일 웹이 헤더 돋보기다        ⚠️ 웹 커뮤니티는 목록에 검색창을 둔다 — 반대다
② 중고거래 앱의 관례다 (당근)      ⚠️ 「중고거래」의 관례다. 커뮤니티는 다른 갈래다
③ 알약 두 줄 때문에 세로가 빠듯하다  △ 커뮤니티는 칩 한 줄뿐이라 덜하다
```

**웹 자신이 이미 둘을 다르게 다루고 있다** — 상품 헤더에는 돋보기, 커뮤니티 목록에는 검색창.

행동으로도 갈린다.

```
상품 검색     찾을 게 정해져 있어 들어온다   → 검색부터 시작. 별도 화면이 맞다
커뮤니티 검색  목록을 보다가 찾게 된다       → 보던 자리에 검색창이 있는 게 맞다
```

### 검색 종류를 안 고른다

서버는 셋을 받지만 **늘 `title_content`(제목+내용)로만 보낸다.** 웹과 같다.

⚠️ **웹은 `COMMUNITY_SEARCH_TYPE` 상수를 만들어 두고 안 쓴다**(`CommunityPage.tsx:38`이
`title_content`로 못 박혀 있다). 그 죽은 상수 때문에 #857 이슈 본문이 「웹은 그걸 쓴다」로
잘못 적혔고, 서버까지 열어보고서야 밝혀졌다. **주석을 달아 다음 사람이 또 속지 않게 한다.**

안 두는 이유 셋:

1. **「제목+내용」이 나머지를 덮는다.** 「제목」은 그것의 부분집합이다. 「제목만」을 고를 이유는
   *내용에 걸리는 글이 너무 많을 때*인데, 그만큼 쌓이려면 한참 걸린다.
2. **「작성자로 찾기」는 다른 기능의 그림자다.** 특정 사람의 글을 보려면 보통 프로필로 간다 —
   앱에 이미 그 화면이 있다.
3. **고르는 자리는 공짜가 아니다.** 서버 비용은 0이지만, 검색할 때마다 「어디서 찾지?」를
   한 번 더 판단해야 한다.

필요해지면 그때 웹·앱에 함께 넣는다.

### 정렬을 나란히 놓는다 (상품은 시트)

```
웹·앱 커뮤니티   최신순 | 조회 순 | 댓글 순      셋뿐이라 나란히
앱 상품         [⚙] 최신순 ▾  → 시트          넷이라 접었다
```

셋뿐이면 시트를 열 이유가 없다. 한 번에 고를 수 있고 지금 무엇으로 정렬 중인지도 늘 보인다.

⚠️ **서버에 있는 `oldest`(오래된 순)는 안 쓴다.** 웹도 넷 중 셋만 쓴다 — 우연이 아니라
고른 결과로 보인다.

### 목록을 조각으로 안 뺀다

이슈에는 「상품 때와 같이 조각으로 빼낸다」고 적혀 있지만, **상품이 뺀 이유가 커뮤니티에는 없다.**

```
상품      홈 + 검색 결과 **두 화면**이 나눠 쓴다 → 빼야 필터를 두 번 안 만든다
커뮤니티   검색을 같은 화면에서 한다 → 나눠 쓸 상대가 없다
```

`index.tsx` 안에서 더한다. 나눠 쓸 일이 생기면 그때 뺀다.

## 3. 화면 모양

```
┌──────────────────────────────┐
│ 커뮤니티              ✏️      │  헤더 (지금 그대로)
├──────────────────────────────┤
│ [질문 있어요][정보 공유]        │  ↑ 고정
│ [🔍 궁금한 내용을 검색해보세요]  │  ↓
├──────────────────────────────┤
│ 최신순 | 조회 순 | 댓글 순      │  ← 스크롤되어 사라진다
│ 게시글…                       │
└──────────────────────────────┘
```

웹 순서 그대로다(탭 → 검색창 → 정렬).

**무엇을 고정하나** — 상품에서 정한 기준을 그대로 쓴다: 「오가는 축은 고정한다. 홈에
「맨 위로」 단추가 없어 한 번 내려가면 닿기 어렵다」.

```
질문 ↔ 정보   오가는 축이다        → 고정
검색창        찾는 중인 걸 보여야 한다 → 고정
정렬          한 번 정하면 잘 안 바꾼다 → 스크롤
```

```
고정 두 줄     칩 50 + 검색창 52 = 약 102dp
게시글 카드    약 104dp (썸네일 76 + 위아래 14씩)
→ 6장쯤 보인다
```

⚠️ **붙는 줄이 없으니 `SectionList` 가 필요 없다.** 상품은 정렬 툴바를 붙이느라
`SectionList` 로 바꿔야 했지만(안드로이드는 `stickySectionHeadersEnabled` 가 기본으로 꺼져 있다),
커뮤니티는 지금 쓰는 `FlatList` 그대로 간다.

## 4. 서버에 보내는 것

```
GET /community/posts?boardType=&page=&size=
                    &searchType=title_content&keyword=&sortBy=
```

- `searchType` 은 **늘 `title_content`**
- `sortBy` 는 `latest`(기본) · `views` · `comments`
- ⚠️ **빈 값은 아예 안 싣는다.** 상품에서 정한 규칙 그대로 — 빈 글자를 보내면 서버가
  그런 조건을 찾는다

⚠️ **조건을 `queryKey` 에 다 넣는다.** 하나라도 빠지면 그 조건만 안 먹고 뒤섞인 목록이 된다
(16바퀴에서 겪었다).

### 탭을 바꾸면 검색어·정렬이 **풀린다**

웹이 그렇다. 탭 전환만 다른 파라미터를 안 이어붙인다.

```
handleTabChange   router.replace(`?tab=${tabId}`)      ← 검색어·정렬을 안 들고 간다
handleSortChange  params.set(...) 로 기존 것을 이어붙인다  ← 정렬 바꿀 때는 검색어가 남는다
```

질문 ↔ 정보는 **다른 갈래**라 조건을 들고 갈 이유가 없다. 검색어를 바꾸거나 정렬만 바꿀
때는 나머지가 그대로 남는다.

## 5. 빈 화면 문구

```
조건 없이 0건   「아직 게시글이 없어요 / 첫 번째 이야기를 나눠보세요!」   지금 그대로 (웹에서 온 것)
검색해서 0건    「검색 결과가 없습니다 / 다른 검색어로 찾아보세요」      ← 새로
```

⚠️ **웹에는 뒤엣것이 없다.** 웹은 검색해서 0건이어도 「첫 번째 이야기를 나눠보세요!」가 그대로
뜬다. 검색 결과가 없는데 그 문구는 어색하므로 앱에서 갈랐다 — 상품에서도 같은 문제를 겪고
갈랐다(`product-list-view.tsx`).

앞 줄(「검색 결과가 없습니다」)은 상품과 같은 문구라 앱 안에서 통일된다.
**새로 지은 것은 「다른 검색어로 찾아보세요」 한 줄뿐이다.**

## 6. 고칠 파일

```
mobile/app/(tabs)/(community)/index.tsx   검색창·정렬 줄을 더한다
mobile/lib/community.ts                   fetchPosts 에 조건을 더한다
src/constants/constants.ts                COMMUNITY_SEARCH_TYPE 에 「왜 안 쓰는지」 주석
```

새로 만드는 조각은 **정렬 줄 하나**다. 검색창은 앱에 이미 있는
`components/products/search-bar-header.tsx` 를 쓸지 목록 안에 놓을 새 입력칸을 만들지
구현할 때 코드를 보고 정한다.

## 7. 함정

```
죽은 상수         웹 COMMUNITY_SEARCH_TYPE 은 아무도 안 쓴다. 이슈 본문이 그것 때문에 틀렸다
서버는 400을 안 준다  잘못된 searchType·sortBy 는 조용히 무시된다 — 오타가 안 드러난다
빈 값             안 싣는다. 빈 글자를 보내면 서버가 그런 조건을 찾는다
queryKey          조건을 다 넣는다. 하나라도 빠지면 뒤섞인 목록이 된다
검색해서 0건       웹 문구를 그대로 쓰면 「첫 번째 이야기를 나눠보세요」가 뜬다 — 갈라야 한다
```

## 8. 실기기 확인

- [ ] 검색어를 치면 목록이 좁혀진다
- [ ] 검색어를 지우면 원래대로 돌아온다
- [ ] **질문 ↔ 정보를 오가면 검색어·정렬이 풀린다** (웹과 같다)
- [ ] 정렬만 바꿀 때는 검색어가 남는다
- [ ] 정렬 셋이 다 먹는다
- [ ] 스크롤하면 정렬 줄은 사라지고 칩 줄·검색창은 남는다
- [ ] 검색해서 0건이면 「검색 결과가 없습니다」가 뜬다
- [ ] 게시글이 몇 장 보이는지 — 고정 두 줄이 세로를 너무 먹지 않는지
