## 1. 개요와 목적 (Why)

기존 Next.js 웹앱 **Cuddle Market**의 사용자용 화면을 **React Native(Expo) 모바일 앱**으로 만들고, 웹과 앱이 로직을 공유하도록 저장소를 **모노레포**로 점진 전환한다.

**진짜 목적**: 채용 공고 대응. 자격요건은 대부분 충족하는데 **RN**이 걸리는 공고, **우대사항에 모노레포 경험자**를 요구하는 공고가 있어, 이력서·면접에서 설명 가능한 실경험을 만드는 것이 최우선이다. 따라서 "동작하는 결과물"만큼 **"왜 이렇게 했는지 설명 가능한 구조"**가 중요하다. 출시는 부차적("잘 되면 출시").

## 2. 목표 범위 (Scope)

- **대상**: 사용자용 앱만. (관리자 페이지는 웹에 그대로 둔다.)
- **첫 마일스톤 = 얇은 수직 슬라이스**: **로그인 → 상품 목록 → 상품 상세** 3화면.
  - "웹 → 앱" 전체 파이프라인(모노레포 세팅·RN·실기기 실행·API 연동)을 **작게 한 바퀴** 도는 것이 목표. 기능 완성도가 아니라 **경로 검증**이 목적.

### 범위 밖 (Out of Scope, 이번 마일스톤에서 안 함)

- 채팅·검색·거래·지도 등 나머지 사용자 기능
- 기존 웹을 `apps/web/`으로 옮기는 **무거운 대이사** (5번에서 후순위)
- 스토어(App Store/Play Store) 실제 출시, CI/CD
- Turborepo 도입 (필요해지면 나중에)

## 3. 핵심 전제 (반드시 이해하고 갈 것)

웹(Next.js)과 앱(React Native)은 **같은 React지만 화면은 공유하지 않는다.**

```
                     웹(Next.js)        앱(React Native)
화면 재료             <div> <button>     <View> <Text>     ← 다름, 공유 불가
스타일                Tailwind (CSS)     StyleSheet        ← 다름, 공유 불가
──────────────────────────────────────────────────────────
타입·API·상수·로직     ────── 공유 가능 ──────               ← 여기만 공유
```

→ 화면(UI)은 앱용으로 새로 그린다. 공유하는 건 **로직뿐**이다.

## 4. 아키텍처 — 방향 3(점진적 모노레포) + 방식 A

### 저장소 구조 (첫 마일스톤 종료 시점)

```
📦 cuddle-market  (저장소 하나 = 모노레포)
   ├── src/ ...            ← 기존 Next.js 웹, 그대로 (이번엔 안 건드림)
   ├── package.json        ← 루트, workspace 선언 추가
   ├── pnpm-workspace.yaml  ← [신규] "mobile, packages/* 도 워크스페이스"
   │
   ├── mobile/             ← [신규] Expo 앱
   │   ├── app/            (로그인·목록·상세 화면 + RN용 API 호출)
   │   ├── metro.config.js  (packages/shared 를 찾도록 설정)
   │   └── package.json
   │
   └── packages/
       └── shared/         ← [신규] 웹·앱 공유 로직
           ├── types/      (Product, 로그인 관련 타입 등)
           └── package.json
```

- **모노레포 엔진**: pnpm workspace. 저장소 루트가 워크스페이스가 되므로 **웹의 의존성 설치도 pnpm으로 넘어간다**(루트 `package.json`이 곧 웹 것이라 피할 수 없음). 단, 웹의 **코드·폴더 위치는 그대로** 두고, `.npmrc`에 `node-linker=hoisted`(npm처럼 평평한 `node_modules`) 안전장치를 깔고 **직후 웹 빌드로 즉시 검증**해 리스크를 최소화한다.
- **후순위로 미루는 "무거운 대이사"**: 웹을 `apps/web/`으로 **옮기고**, 웹이 `packages/shared`를 **소비**하게 만드는 완전 공유. (이번 마일스톤 범위 밖)
- **방식 A**: 처음부터 공유 코드를 `packages/shared`에 두고 `mobile`이 참조한다. (복붙 후 나중에 빼는 방식 B가 아니라, 처음부터 정석 구조.)

### 무엇을 공유하고, 무엇을 공유하지 않나 (근거 기반)

실제 웹 코드를 확인한 결과에 따른 결정이다.

| 대상 | 첫 마일스톤 처리 | 이유 |
|---|---|---|
| **타입** (`src/types/product.ts`, `auth.ts` 등) | 🟢 `packages/shared/types`로 (복사 이전) | 순수 TypeScript. 플랫폼 의존 전혀 없음 → 깨끗하게 공유 |
| **순수 공유 로직**(헬퍼: 예 `formatPrice`, `isTradeAvailable`) | 🟢 `packages/shared/lib`에 새로 작성 + **Vitest로 테스트** | 플랫폼 무관한 순수 함수. 웹·앱이 같은 로직·같은 테스트를 공유 → 모노레포 진가. Vitest에 실제 테스트 대상을 제공 |
| **API 클라이언트** (`src/lib/api/api.ts`) | 🔴 공유 안 함. 앱에 별도로 얇게 작성 | axios 인스턴스가 `useUserStore`(Zustand)·`NEXT_PUBLIC_` 환경변수에 묶임. 토큰 저장 방식이 웹(스토어 persist)과 앱(RN 보안 저장소)이 **다름** → 그대로 못 씀 |
| **화면/컴포넌트** | 🔴 공유 안 함. 앱용으로 새로 그림 | `<div>`/Tailwind ≠ `<View>`/StyleSheet |

> **중요한 뉘앙스**: 첫 마일스톤에서 `packages/shared`는 **mobile만** 소비한다(웹은 아직 자기 `src/types` 유지). 웹까지 shared를 쓰게 만드는 "완전 공유"는 무거운 대이사(5번)에서. 그래도 이 단계로 **workspace + shared 패키지 + Metro 해석**이라는 모노레포의 핵심 학습은 이미 달성된다.
>
> **API 클라이언트 공유는 별도 후속 과제**: 토큰 획득 함수와 baseURL을 바깥에서 주입받는 "플랫폼 중립" API 클라이언트로 리팩터하면 그때 shared로 승격 가능. 이번 범위 밖.

## 5. 기술 선택 요약 (근거는 용어 사전 참고)

| 선택 | 무엇 | 왜 |
|---|---|---|
| **Expo** | RN 앱 표준 프레임워크 | 실기기 테스트·빌드가 쉬움. 2026 RN 사실상 표준 |
| **pnpm workspace** | 모노레포 엔진 | "여러 앱이 한 저장소에서 패키지 공유"의 본질. 설정 단순 |
| **Metro 설정** | RN 번들러가 `packages/shared`를 찾게 함 | 모노레포에선 앱 폴더 바깥 코드를 기본으로 못 찾음 (Expo 공식 모노레포 가이드 따름) |
| **TypeScript** | 전 구간 | 웹과 타입 공유의 전제 |
| **Vitest** | `packages/shared` 순수 로직 유닛 테스트 | 이미 설치돼 있음(미사용). DOM 기준이라 RN 화면은 못 하지만 순수 TS엔 최적 |
| **Jest (jest-expo)** | `mobile` 로직·컴포넌트 테스트 | RN/Expo의 표준 유닛·컴포넌트 러너. axios·SecureStore는 mock |
| **Maestro** | 앱 E2E(로그인→목록→상세 흐름) | RN E2E 표준(YAML). Playwright는 웹 전용이라 RN 앱엔 못 씀 |

- 개념 정리는 블로그 초안 `docs/blog-drafts/expo-pnpm-monorepo-first-encounter.md`(용어 사전) 참고.
- 참고 스택(웹): Next 16, React 19, axios, Zustand, TanStack Query.

## 6. 백엔드 (이미 존재 — 새로 설계 안 함)

- 백엔드 서버 코드가 `~/Desktop/cmarket_api`에 이미 있다. 앱은 웹과 **동일한 REST API**를 그대로 호출한다.
- API 기본 주소: `https://cmarket-api.duckdns.org/api` (웹의 `NEXT_PUBLIC_API_BASE_URL`). 앱은 Expo 환경변수(`EXPO_PUBLIC_...`)로 같은 주소를 가리킨다.
- 따라서 **DB/ERD 설계, API 명세 설계 단계는 불필요**하다. 대신 앱 작업 전 **기존 API 계약(로그인·상품 목록·상세 응답 형태)을 읽어 파악**만 한다.

## 8. 검증 게이트 (층별 테스트 + 실기기)

"웹은 브라우저·앱은 네이티브"라 층마다 맞는 도구가 다르다. 각 러너에게 **겹치지 않는 담당 구역**을 준다(같은 코드를 두 러너로 검사하는 중복 금지).

| 층 | 대상 | 도구 | 강도 |
|---|---|---|---|
| 타입/컴파일 | 전 구간 | `tsc --noEmit` + `eslint` | 약한 게이트(타입만) |
| 유닛 | `packages/shared` 순수 로직 | **Vitest** | 로직 검증 |
| 유닛/컴포넌트 | `mobile` 로직·컴포넌트 | **Jest (jest-expo)** | 로직·렌더 검증 |
| E2E | 로그인→목록→상세 흐름 | **Maestro** | 흐름 검증 |
| 사람 검수 | 각 화면 실물 | **실기기(Expo Go)** | 강한 게이트(핵심) |

- 각 러너 담당 구역: Vitest=공유 로직, Jest=앱, Maestro=흐름. (Playwright는 웹 전용이라 이번 앱 범위 밖 → 웹 손댈 때.)
- 단계마다 해당 게이트를 통과해야 다음 단계로.

> ⚠️ 약한 게이트(tsc·lint) 통과 ≠ 앱 동작. 테스트 통과에 더해, 화면이 실제로 렌더되고 데이터가 보이는 걸 **실기기로** 봐야 "됐다".

## 9. 위험과 주의사항

| 위험 | 대응 |
|---|---|
| 루트가 pnpm 워크스페이스가 되며 웹 설치가 pnpm으로 바뀜 → 웹이 깨질 수 있음 | `.npmrc`에 `node-linker=hoisted`(npm처럼 동작) + 전환 직후 `pnpm build`로 웹 즉시 검증. 별도 작업 브랜치에서 진행. 웹을 `apps/web/`으로 **옮기는** 무거운 작업은 후순위 |
| Metro가 `packages/shared`를 못 찾음 | Expo 공식 모노레포 가이드대로 `metro.config.js` 설정 (예상된 삽질 포인트) |
| 토큰 저장 방식 차이(웹 스토어 vs 앱 보안저장소) | API 클라이언트를 공유하지 않고 앱에 별도 작성으로 회피 |
| 범위 확장(기능 욕심) | 첫 마일스톤은 3화면으로 못박음. 나머지는 다음 마일스톤 |

## 10. 첫 마일스톤 완료 기준 (Definition of Done)

아래가 **전부** 충족되면 첫 마일스톤 완료:

1. `pnpm-workspace.yaml` + `mobile/` + `packages/shared/` 구조가 서고, 기존 웹이 여전히 정상 동작한다.
2. Expo 앱이 실기기(Expo Go)에서 실행된다.
3. `packages/shared`의 타입·공유 로직을 `mobile`이 import해서 쓴다(모노레포 공유 성립, Metro 해석 통과).
4. 앱에서 **로그인 → 상품 목록 → 상품 상세**가 실제 백엔드 데이터로 동작한다.
5. 테스트 통과: **Vitest**(shared 순수 로직) + **Jest**(mobile 로직) + **Maestro**(로그인→목록→상세 E2E).
6. `tsc --noEmit`·`eslint` 통과.

- 플랫폼 중립 API 클라이언트를 `packages/shared`로 승격

- (선택) 스토어 출시, Turborepo, CI/CD
