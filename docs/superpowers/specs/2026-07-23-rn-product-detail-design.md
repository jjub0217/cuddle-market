# 앱 상품 상세 화면 설계 (RN 협업 2바퀴)

작성일: 2026-07-23 (목)
관련: `2026-07-19-rn-app-monorepo-design.md`, `2026-07-21-rn-home-slice-requirements.md`, `2026-07-21-rn-home-slice-ui.md`

## 1. 목적

앱의 두 번째 기능으로 **상품 상세 화면**을 만든다. 홈 목록(1바퀴)에서 카드를 누르면 상세로 이동하는
경로를 열어, 얇은 수직 슬라이스(로그인 → 목록 → 상세) 중 마지막 조각을 채운다.

첫 바퀴가 "목록을 그린다"였다면, 이번 바퀴의 새 축은 **화면 전환(네비게이션)**과 **단건 조회**다.

## 2. 범위

### 들어가는 것

읽기 전용 상세 한 화면.

- 브레드크럼(펫 세부종류 › 카테고리) — 표시만, 링크 없음
- 이미지(메인 + 서브) 가로 스와이프 + 거래상태 오버레이
- 뱃지(판매/판매요청, 상품상태)
- 제목, 가격
- 등록 시간, 지역
- 판매자 정보(프로필 이미지·닉네임·지역)
- 설명
- 조회 수, 찜 수 (표시 전용)
- 로딩 / 없는 상품(404) / 오류 상태

여기에 더해 **모노레포 배관 1단계**가 함께 들어간다 (§7). 웹이 `@cuddle/shared`를 볼 수 있게 연결하고,
`formatPrice` 하나를 옮겨 길이 뚫렸는지 증명하는 데까지다. 웹의 나머지 중복 정리는 다음 바퀴다.

### 빠지는 것과 이유

| 빠지는 것 | 이유 | 다시 볼 시점 |
|---|---|---|
| 찜 · 채팅하기 버튼 | 로그인이 있어야 동작. 앱에 토큰 붙이는 API 클라이언트도 아직 없음 | 로그인 루프 |
| 신고하기 | 위와 같음 (`POST /reports/products/{id}`는 토큰 필요) | 로그인 루프 |
| 판매자의 다른 상품 | 로그인과 무관하지만, 이번 바퀴를 얇게 두려고 제외 | 아무 때나 |
| 브레드크럼 링크 | 눌러서 갈 곳(홈 필터)이 아직 없음 | 홈 필터 루프 |

**버튼을 넣을지 말지는 이미 정해져 있다 — 넣는다.** 다만 지금 넣으면 눌러도 아무 일이 없는
껍데기가 되므로 미룬다. 본문 안에 둘지 화면 하단에 고정할지는 실기기에서 스크롤 길이를 보고 정한다
(§8 참고).

## 3. API 계약 (2026-07-23 실측)

```
GET {base}/products/{id}          비로그인 200 OK
```

응답 `data` 주요 필드:

| 필드 | 타입 | 비고 |
|---|---|---|
| `title` `price` `description` | string / number / string | 설명은 실측 6~125자로 짧은 편 |
| `mainImageUrl` | string | |
| `subImageUrls` | string[] | **실측 7건 중 6건이 빈 배열** |
| `productType` | `SELL` \| `REQUEST` | 실측 50건 중 34 / 16 |
| `tradeStatus` | string \| null | **REQUEST는 대부분 null** |
| `productStatus` | `NEW` \| `LIKE_NEW` \| `USED` \| `NEED_REPAIR` | |
| `petType` `petDetailType` `category` | string | 브레드크럼 재료 |
| `addressSido` `addressGugun` `createdAt` | string | |
| `viewCount` `favoriteCount` | number | |
| `isFavorite` | **boolean \| null** | 비로그인이면 `null`. 웹 타입은 `boolean`으로 잘못 선언돼 있음 |
| `sellerInfo` | 객체 | `sellerProfileImageUrl`이 `null`일 수 있음 |
| `sellerOtherProducts` | Product[] | 이번 범위 밖 |

없는 상품(삭제 포함)은 **HTTP 404**에 `{"code":"NOT_FOUND","message":"상품을 찾을 수 없습니다."}`.

성공/오류 판정은 body의 `code`가 아니라 **HTTP status(`res.ok`)** 기준으로 한다 (홈 목록과 동일).

## 4. 화면 구성

웹 브라우저를 모바일 폭으로 줄였을 때의 순서를 그대로 따른다. 웹 코드로 확인한 실제 순서다.

```
┌────────────────────────────────┐
│ ‹                              │  스택 헤더 (뒤로가기만, 타이틀 없음)
├────────────────────────────────┤
│ 앵무새 › 사료/간식             │  브레드크럼 (좌측 정렬, 마지막 항목 강조)
│ ┌────────────────────────────┐ │
│ │      메인 + 서브 사진      │ │  1:1 정사각, 가로 스와이프
│ │      ●○                    │ │  2장 이상일 때만 인디케이터
│ └────────────────────────────┘ │  거래상태 오버레이는 홈 카드와 동일 규칙
│ [판매요청] [사용감 있음]       │  뱃지
│ 쿨매트 구매 희망합니다         │  제목
│ 10,000원                       │  가격 (포인트색 강조)
│ 3일 전 · 서울 은평구           │  시간 · 지역
│ ────────────────────────────── │
│ 👤 유리 / 서울 은평구          │  판매자 (설명보다 위 — 웹과 동일)
│ ────────────────────────────── │
│ 두부간식 잘먹어요              │  설명 (본문에 펼침, 박스 아님)
│                                │
│ 👁 조회 12   ♡ 찜 1            │  조회 · 찜 (설명 아래 — 웹 모바일과 동일)
├────────────────────────────────┤
│  🏠    ✈️                      │  탭바 유지
└────────────────────────────────┘
```

### 웹과 일부러 다르게 가는 곳 — 한 군데

**설명을 자체 스크롤 박스로 만들지 않는다.**

웹은 `min-h-20 overflow-y-auto`로 설명을 박스에 가둔다. 데스크톱 2단에서 왼쪽 사진과 오른쪽 열의
높이를 맞추려는 처리인데, 앱에서는 페이지 안에 또 스크롤 영역이 생겨 **손가락 스크롤이 서로 잡아먹는다**
(중첩 스크롤). 앱에서는 본문에 그대로 펼친다.

### 타입(판매/판매요청) 처리 — 새로 만들지 않는다

웹과 앱 카드에 이미 있는 규칙을 상세로 잇기만 한다.

> **구현 중 정정 (2026-07-27, 실기기 확인 반영)**: 아래 "이미 있는 규칙"이 실은 웹과 어긋나 있어서, 구현하며 다음처럼 통일했다.
> - **뱃지 모양**: 알약(`borderRadius:999`, 웹 `rounded-full`)으로 웹·앱 통일. 판매요청 뱃지 테두리 제거.
> - **강조색**: 가격은 **제목과 같은 검정**(밝은 골드 `#E2A958`은 대비 2.09로 안 읽힘), 브레드크럼 마지막 항목·링크는 **브랜드 브라운 `#633F00`**. "포인트색"은 이 브라운을 뜻한다.
> - **조회·찜**: 아이콘 없이 글자로("아이콘은 누를 수 있는 것에만").
> - **판매자 아바타**: 회색이 아니라 디자인 시스템 크림(`primary-50` `#FAF3E6`).
> - 웹 뱃지 색은 `tokens.colors.css`의 `badge-*` 시맨틱 토큰으로 승격.

| 항목 | 규칙 | 이미 있는 곳 |
|---|---|---|
| 타입 뱃지 | 판매 = 파랑 / 판매요청 = 주황 (모양은 알약으로 통일 — 위 정정) | `mobile/components/product-card.tsx` |
| 거래상태 라벨 | 판매요청 + 완료 → `요청완료`, 판매요청 + null → `요청중` | `mobile/lib/tradeStatus.ts` |
| 오버레이 | 예약중 40% · 완료 계열 60% / 판매중·요청중은 없음 | 같은 파일 |
| 버튼 문구 | `채팅하기` 하나로 통일 (타입과 무관) | 웹 `ProductActions.tsx` |

판매요청 글에 `채팅하기`가 붙는 건 정상이다. 구하는 사람이 글을 올리고, 팔고 싶은 사람이 그 사람에게
말을 거는 구조라 방향만 반대일 뿐 행동은 같다.

## 5. 라우팅 — 탭바를 유지한다

상세에서도 하단 탭바를 그대로 둔다.

**근거**

- 웹 `BottomNav.tsx`의 숨김 목록에 **상품 상세가 없다**. 채팅방·커뮤니티 상세처럼 하단에 입력창이
  필요한 화면만 골라 숨기고 있고, 상품 상세는 탭바를 유지하는 판단이 이미 내려져 있다.
- 커들마켓은 거래 하나로 끝나는 서비스가 아니라 `장터 ↔ 커뮤니티 ↔ 플레이스`를 오가는 서비스다.
  상세에서 이동 통로를 끊을 이유가 없다.
- 앱 IA 초안도 *"앱의 1차 네비게이션은 웹 BottomNav 구조를 계승한다"* 로 적고 있다.

**구조** — Expo SDK 54 공식 문서의 "탭 안에 스택 중첩" 패턴을 따른다.

```
app/(tabs)/
├─ _layout.tsx              Tabs (기존, 화면 이름만 조정)
├─ (home)/                  신규: 홈 탭이 스택을 갖는다
│  ├─ _layout.tsx           Stack
│  ├─ index.tsx             기존 홈 (파일 이동만, 내용 변경 없음)
│  └─ products/[id].tsx     상세 (신규)
└─ explore.tsx              Expo 템플릿 잔재 — 이번엔 손대지 않음
```

카드를 누르면 `router.push('/products/61')` → 스택 위로 밀려 올라오고 탭바는 남는다.
안드로이드 뒤로가기와 헤더 `‹` 둘 다 목록으로 돌아간다.

> 탭 목록을 커들마켓 것(홈/커뮤니티/플레이스/채팅/마이)으로 바꾸는 일은 이번 범위 밖이다.
> 지금은 `Home / Explore` 템플릿 탭이 그대로 보인다.

## 6. 데이터 흐름

```
홈 목록 캐시                          상세 화면
['products'] ─┬─ 제목·가격·사진 ────▶ 진입 즉시 표시 (placeholderData)
              │
              └─ GET /products/61 ──▶ 설명·판매자·서브사진을 채움
                 useQuery(['product', 61])
```

목록에서 눌러 들어오면 이미 아는 값이 제자리에 먼저 들어가므로 빈 화면을 지나지 않는다.
캐시가 없으면(앱 재시작·딥링크) 자동으로 전체 스켈레톤이 된다 — 별도 분기가 필요 없다.

**주의**: 재사용하는 것은 `Product` 객체(순수 데이터)이고, 홈의 `ProductCard` 컴포넌트를 상세에
가져다 쓰는 게 아니다. 상세는 자기 레이아웃을 갖는다.

### 상태별 화면

| 상황 | 보이는 것 |
|---|---|
| 목록 캐시 있음 | 사진·제목·가격 즉시, 설명·판매자만 회색 자리표시 |
| 목록 캐시 없음 | 전체 스켈레톤 |
| 404 | "삭제되었거나 없는 상품이에요" + [목록으로] |
| 네트워크·서버 오류 | "상품을 불러오지 못했어요" + [다시 시도] |

## 7. 코드 구조 — 모노레포답게

지난 바퀴에서는 웹을 건드리지 않으려고 라벨 함수를 앱에 복사했다. 이번 바퀴부터는 **원본을 한 곳에
두고 웹·앱이 같이 보는** 구조로 바꾼다. 이 저장소를 모노레포로 만든 이유가 바로 이것이다.

다만 웹은 운영 중이므로 **한 번에 다 옮기지 않고 두 바퀴로 나눈다.**

| 하는 일 | 이번 바퀴 | 다음 바퀴 |
|---|---|---|
| 배관 뚫기 (웹이 shared를 볼 수 있게) | ✅ | |
| `formatPrice` 를 shared 단일 원본으로 | ✅ | |
| 새로 만드는 라벨 로직 | ✅ 처음부터 shared에 | |
| 웹의 기존 중복(`getTimeAgo` 11곳, `PETS` 등) 갈아끼우기 | | ✅ |

### 7.1 배관 (이번 바퀴)

지금 웹은 shared와 연결조차 되어 있지 않다. 실측한 상태와 할 일:

| 항목 | 지금 | 할 일 |
|---|---|---|
| 루트 `package.json` | `@cuddle/shared` 의존성 없음 | `"@cuddle/shared": "workspace:*"` 추가 |
| `next.config.ts` | `transpilePackages` 없음 | `['@cuddle/shared']` 추가 (빌드 산출물 없이 TS 소스를 그대로 내보내는 패키지라 필수) |
| 루트 `tsconfig.json` | `exclude: [node_modules, mobile, packages]` | 웹이 shared를 타입체크할 수 있게 조정 |

### 7.2 웹을 어떻게 안 깨뜨리나 — 재수출 껍데기

`formatPrice` 하나만 봐도 웹 9개 파일이 쓰고 있다. import 경로를 전부 고치면 diff도 위험도 커진다.
그래서 **웹의 기존 파일을 경로 그대로 두고 내용만 한 줄로 바꾼다.**

```ts
// src/lib/utils/formatPrice.ts  — 경로 유지, 내용만 교체
export { formatPrice } from '@cuddle/shared'
```

```
         [지금]                            [바꾼 뒤]

웹 9개 파일 → 웹 formatPrice.ts       웹 9개 파일 → 웹 formatPrice.ts (껍데기)
                                                            ↓
앱          → shared formatPrice      앱          →  @cuddle/shared  ← 원본 하나
                (따로 존재)
```

웹의 9개 파일은 한 줄도 고치지 않는다. 원본은 shared에만 남는다. 나중에 여유가 생기면 import 경로를
직접 바꾸고 껍데기를 지우면 된다.

### 7.3 파일 목록

```
packages/shared/src/
├─ index.ts                    아래 것들을 내보내도록 갱신
├─ types/product.ts            ProductDetailItem 추가
│                              isFavorite: boolean | null (실측 반영)
├─ lib/format.ts               formatPrice — 웹도 이제 여기를 본다 (기존 파일)
├─ lib/timeAgo.ts              신규 — getTimeAgo
├─ lib/productLabels.ts        신규 — 상품 타입·상태 코드→한글
├─ lib/petLabels.ts            신규 — 펫 세부종류 40개 · 카테고리 8개 코드→한글
└─ lib/tradeStatus.ts          신규 — getTradeLabel (판매요청 예외 포함)

mobile/lib/products.ts         fetchProductDetail(id) 추가
mobile/lib/tradeStatus.ts      getOverlay만 남김 (색상은 화면 표현이라 앱에 둠)
mobile/components/product-card.tsx   안에 있던 순수 함수 3개를 shared 것으로 교체

mobile/app/(tabs)/(home)/_layout.tsx        신규 Stack
mobile/app/(tabs)/(home)/index.tsx          기존 홈 이동
mobile/app/(tabs)/(home)/products/[id].tsx  신규 상세 화면

mobile/components/product-detail/           신규 컴포넌트
├─ breadcrumb.tsx
├─ image-carousel.tsx
├─ product-summary.tsx         뱃지·제목·가격·시간·지역
├─ seller-card.tsx
└─ detail-states.tsx           스켈레톤 · 404 · 오류

src/lib/utils/formatPrice.ts   웹 — 재수출 껍데기로 교체
```

**shared에는 순수 로직만 둔다.** 오버레이 색(`rgba(0,0,0,0.4)`)처럼 화면 표현에 속하는 값은 앱에 남긴다.
웹과 앱은 로직만 공유하고 UI는 공유할 수 없다는 원칙(모노레포 설계 문서)을 그대로 지킨다.

## 8. 나중에 근거를 갖고 정할 것

지금 추측으로 정하지 않고, 실기기에서 보고 판단한다. 이번 바퀴를 웹과 같게 만드는 이유가 여기 있다 —
**비교 기준**이 생겨야 "여기가 웹이랑 같은데 앱에선 답답하다"고 말할 수 있다.

1. **판매자 프로필이 설명보다 위인 것** — 데스크톱 2단이 세로로 펼쳐진 결과다. 앱에서 맞는 순서인지는
   실기기에서 봐야 안다.
2. **찜·채팅 버튼의 위치** — 본문 안(웹과 동일) vs 화면 하단 고정. 지금 데이터로는 설명이 짧아 본문
   인라인으로 충분해 보이지만, 실제 스크롤 길이를 보고 정한다.
3. **사진 좌우 여백** — 웹처럼 여백 안에 둥근 모서리로 둘지, 화면 폭을 꽉 채울지.
4. **탭바 스크롤 숨김** — 나중에 버튼이 붙어 하단이 2단이 되면 답답한지.

### 다음 바퀴로 넘긴 일 (이미 정해진 것)

판단이 필요한 게 아니라 순서상 미룬 것들이다.

- 웹의 기존 중복을 shared로 갈아끼우기 — `getTimeAgo`(11개 파일), `PETS`·`PET_DETAILS`,
  `PRODUCT_CATEGORIES`, `PRODUCT_TYPE_TABS`, `CONDITION_ITEMS`
- 재수출 껍데기 걷어내기 — 웹 import 경로를 `@cuddle/shared`로 직접 바꾸고 껍데기 파일 삭제
- 찜 · 채팅하기 · 신고하기 (로그인 루프)
- 판매자의 다른 상품
- 브레드크럼 링크 연결 (홈 필터 루프)

## 9. 테스트

| 계층 | 대상 |
|---|---|
| Vitest (`packages/shared`) | `getTimeAgo`, 상품 타입·상태 라벨, 펫·카테고리 라벨, `getTradeLabel`(판매요청 예외 포함) |
| Jest (`mobile`) | `fetchProductDetail` 정상 / 404 / 네트워크 오류, `getOverlay`, 기존 카드 테스트 회귀 |
| 타입체크 | `pnpm exec tsc --noEmit` (mobile), `pnpm build` (웹) |
| 실기기 시각 확인 | 판매(SELL) 1건 · 판매요청 + 거래상태 null 1건 · 서브이미지 있는 건(id=60) · 삭제된 건(id=55) |

라벨·시간·거래상태가 shared로 올라가므로 **순수 로직 테스트도 Vitest 쪽으로 함께 옮긴다.** 같은 코드를
두 러너로 검사하지 않는다는 원칙(모노레포 설계 문서)을 지킨다.

### 배관이 진짜 뚫렸는지 증명하는 법 (마커 검증)

웹이 shared를 "보는 것처럼 보이는" 것과 실제로 보는 것은 다르다. 껍데기만 만들어 놓고 번들러가
옛 코드를 쓰고 있어도 화면은 멀쩡해 보인다. 그래서 이렇게 증명한다.

1. `packages/shared`의 `formatPrice`에만 눈에 띄는 표식을 잠깐 심는다 (예: 값 앞에 `ZZ`).
2. 웹을 띄워 상품 가격에 그 표식이 보이는지 확인한다.
3. 보이면 웹이 정말 shared를 보고 있는 것이다. 표식을 지우고 커밋한다.

### 웹 무손상 게이트

**`pnpm build`를 배관 작업 직후와 모든 파일을 다 넣은 뒤, 두 번 돌린다.**
지난 바퀴에 워크스페이스를 추가한 뒤 웹 `next build`가 앱을 타입체크해 실패한 적이 있다.
그때는 배관을 뚫기 전이었는데, 이번에는 웹이 shared를 직접 참조하므로 깨질 경로가 더 많다.
빌드가 실패하면 그 지점에서 멈추고 되돌린다.

## 10. 진행 방식

AI 협업팀(Agent Teams) 2바퀴. 지난 바퀴와 달리 **프론트A와 프론트B의 역할을 바꾼다**
(구현하던 쪽이 리뷰하고, 리뷰하던 쪽이 구현). 반복 루프는 로컬에서 돌리고, GitHub PR은 마지막에 한 번만
올린다(자동 리뷰 토큰 절약).
