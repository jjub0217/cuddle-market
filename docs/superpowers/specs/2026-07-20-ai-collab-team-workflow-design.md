## 1. 개요와 목적 (Why)

실제 소프트웨어 팀의 **협업 사이클**(PM 기획 → 디자인 → 프론트 구현 → PR → 상호 코드리뷰 → dev 머지 → QA 테스트 → 피드백 → 수정 → 반복)을 **Claude Code의 Agent Teams 기능으로 체험**한다. 그리고 그 협업 과정의 결과물로 **RN 앱을 실제로 구현**한다.

**진짜 목적**: 협업 워크플로우 자체를 경험하는 것(학습·이력서·블로그 소재) + 그 과정으로 RN 앱 화면을 실제로 만드는 것. "AI 팀이 무인으로 다 해주는 공장"이 아니라, **사람(스테이크홀더 겸 시각 QA)이 감독하는 작은 팀**을 굴리는 경험.

### 이 설계가 나온 배경 (근본 원인 하나)

브레인스토밍 중, "화면·범위를 정하려는데 자꾸 추측이 들어간다"는 문제가 있었다. 근본 원인은 **요구사항 정의서와 플로우차트가 없어서**였다 — 즉 협업 사이클의 **첫 단계(PM 산출물)를 건너뛰었기** 때문. 그래서 이 워크플로우의 **1번 태스크를 "PM이 요구사항 정의서 + 플로우차트를 만드는 것"**으로 못박는다. 이 문서가 곧 "모두가 추측하지 않게 만드는 단일 진실(SSOT)"이 된다.

## 2. 목표 (성공의 정의)

**목표 = "한 기능을 풀 협업 루프로 한 바퀴 돌려 성공"** (선택지 C: 과정도 배우고 + 실제 쓸 코드도 남긴다).

- 한 기능을 팀 루프로 끝까지 돌려 성공하면, **같은 방식으로 나머지 기능에 복제**한다.
- 처음부터 크게 벌이지 않는다 — Agent Teams가 실험 기능이라, 작게 한 바퀴 도는 것이 배움도 최대, 낭비도 최소.

## 3. 팀 구성 (역할 → 에이전트)

```
[당신] = 스테이크홀더 · 최종 승인 · 실기기 시각 QA
   │
[리드(나)] = EM(엔지니어링 매니저): 조율 · 태스크 분배 · 종합 · 중계
   │
 ├─ PM 에이전트        요구사항 정의서 · 플로우차트 · 마일스톤
 ├─ 디자이너 에이전트   모바일 와이어프레임 · UI 스펙 (+ Figma MCP 선택)
 ├─ 프론트A 에이전트    화면 · 기능 구현
 ├─ 프론트B 에이전트    프론트A의 코드리뷰 (다음 기능에선 역할 교대)
 └─ QA 에이전트        자동 테스트(Jest/Vitest/Maestro) · 코드 검사 · 피드백
```

- **왜 프론트 2명?** "프론트끼리 상호 리뷰"를 재현하려면 최소 2명이 필요하다. 다음 기능에선 A↔B 역할을 바꾼다.
- 총 5역할. 공식 문서 권장(3~5명) 범위. **동시 실행이 아니라 파이프라인**(PM → 디자이너 → 프론트 → QA 순)이라 동시 토큰 부담은 크지 않다.
- **리드 = 나(메인 세션)**. 팀을 조율하고, 각 결과를 종합해 당신에게 보고한다. 당신은 리드 위의 스테이크홀더.

## 4. 협업 루프 (핵심 플로우)

```
Sprint 0 (인프라, 루프 아님 · 단일 스레드):
   모노레포 + Expo 뼈대(RN 계획 Task 3~6) 먼저 깔기
   ← 디자이너 와이어프레임·QA 시각검수가 없는 순수 인프라라, 협업 루프 대상 아님

Sprint 1 (첫 기능, 풀 협업 루프):
   ① PM      → 요구사항 정의서 + 플로우차트 (기존 웹앱에서 추출)
   ② 디자이너 → 모바일 UI 스펙 (① 기반)
   ③ 프론트A → 구현 (② 기반, 자기 브랜치 / worktree)
   ④ 프론트B → ③의 diff 로컬 코드리뷰 → 코멘트
   ⑤ 프론트A → 리뷰 반영 → dev에 로컬 머지
   ⑥ QA     → dev에서 자동 테스트 + 코드 검사 → 피드백
   ⑦ 당신    → 실기기 시각 검수 (QA가 못 보는 "느낌")
   ⑧ 피드백 있으면 → ③으로 되돌림 (디자인 수정 필요 시 → ②로)
   ★ 딱 한 번, 의미 있는 지점에서 진짜 GitHub PR 1개 (실물 경험용)
```

## 5. 사람(당신)의 자리

에이전트가 못 하거나 사람이 맡아야 하는 지점:

- **실기기 시각 QA**: 에이전트는 폰 화면을 볼 수 없다. "모바일에서 실제로 어떻게 보이고 느껴지나"는 당신의 몫. (현실 QA도 자동+수동으로 나뉘며, 여기서 수동 시각 검수를 당신이 맡는다.)
- **최종 승인자**: 각 스프린트 결과를 리드(나)가 당신에게 보고 → 당신이 승인/반려.
- **PM·디자인 개입**: 원하면 언제든 리드를 통해, 또는 해당 에이전트에게 직접.

## 6. 실행 메커니즘

- **네이티브 Claude Code Agent Teams** (실험 기능). 서브에이전트가 아니라 **독립 인스턴스 팀원 + 공유 태스크 리스트 + 메일박스 소통**.
- **표시 모드: `tmux` 분할 판 (확정)** — 팀원마다 판(pane)을 배정해 동시에 본다. **터미널 창은 1개**이며 tmux가 안에서 판으로 나눈다 (Apple Terminal + tmux, `teammateMode: "tmux"`, `brew install tmux` 필요).
  - 팀원은 **리드가 스폰**하고 tmux가 자동 배치한다. 사용자가 창을 여러 개 여는 방식(수동 멀티세션)은 이 설계가 아니다.
  - 폴백: tmux가 말썽이면 `in-process`(설치 0, 방향키 전환)로 전환.
- **활성화**: `settings.json`에 `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1` + `teammateMode: "tmux"` → **재시작 필요**.
- **OMC 비활성화**: 팀원 5명 각각이 CLAUDE.md·MCP·스킬을 로드하므로, OMC의 지시 블록·훅·`team` 스킬이 5배로 퍼져 소음·용어 충돌을 일으킨다. 깨끗한 학습 환경을 위해 끈다. (되돌릴 수 있음.)
- **파일 충돌 격리**: 병렬 프론트 작업 시 **git worktree**로 팀원마다 다른 폴더/파일을 소유하게 한다. (Agent Teams는 팀원을 worktree로 자동 격리하지 않으므로 작업을 파티션한다.)

## 7. PR / 리뷰 / QA 방식 (하이브리드 C)

- **반복 루프는 로컬**: git 브랜치·커밋은 진짜로 하되, PR·리뷰·머지는 로컬에서. 리뷰어 에이전트가 브랜치 diff를 읽고 리뷰 코멘트를 남기고, 담당 프론트가 반영 후 dev에 로컬 머지.
  - 이유: 이 프로젝트는 **develop 대상 PR에 kimi 자동 리뷰가 트리거돼 토큰이 크게 소모**된다. 반복 루프를 로컬로 돌리면 kimi를 피하고 싸고 빠르다.
- **딱 한 번 진짜 GitHub PR**: 의미 있는 체크포인트에서 실제 PR 1개를 올려 "GitHub에서 PR·리뷰가 이렇게 보이는구나"를 경험한다. (kimi 비용 1회로 제한.)
- **QA**: 자동 테스트(Jest/Vitest/Maestro) + 코드 검사 = QA 에이전트. **시각/실기기 검수 = 당신.**

## 8. 범위 & 안 할 것 (YAGNI)

**범위**
- 첫 루프 대상 기능은 **PM의 요구사항 정의서가 정확히 확정**한다 (지금 추측하지 않는다). 유력 후보 = **메인화면의 얇은 슬라이스**(히어로 + 상품 리스트). 필터·정렬·상품등록 버튼 등은 이후 루프의 독립 기능으로 분리.

**안 할 것 (Out of Scope)**
- 무인 완전 자동화 (감독·승인이 항상 사람에게 있음)
- 전체 앱을 한 번에 (한 기능 루프 성공 후 복제)
- 백엔드 협업 (API가 이미 존재 — `https://cmarket-api.duckdns.org/api`)
- 실제 스토어 배포 / CI·CD
- 지엽적 디자인 늪 (색·폰트·간격 완벽주의)

## 9. 완료 기준 (첫 루프 성공 = Definition of Done)

1. PM 요구사항 정의서 + 플로우차트 문서가 나온다 (기존 웹앱 추출 기반).
2. 디자이너 UI 스펙 → 프론트 구현 → 프론트 상호 리뷰 → dev 머지 → QA 테스트 **한 사이클이 실제로 돈다.**
3. 피드백 → 수정 → 재검증 **되돌림 루프가 최소 1회** 작동한다.
4. 결과 RN 화면이 **실기기에서 실제 백엔드 데이터로** 동작한다 (당신의 시각 QA 통과).
5. 진짜 GitHub PR 1개 경험 완료.

## 10. 위험과 주의사항

| 위험 | 대응 |
|---|---|
| Agent Teams는 실험 기능 (세션 재개 안 됨 · 태스크 상태 지연 · 셧다운 느림) | 리드(나) + 당신이 감독. 무인 자동 아님. 재시작하면 팀원은 새로 스폰 |
| 시각 QA를 에이전트가 못 함 | 실기기 시각 검수는 당신이 담당 (설계에 명시) |
| develop PR = kimi 토큰 폭탄 | 반복 루프 로컬화 + 진짜 PR은 1회만 (§7) |
| 이 앱은 초반이 순차 (뼈대는 한 명이 깔아야) | Sprint 0(인프라)은 단일 스레드. 병렬 프론트는 기능 단계부터 |
| 팀원 병렬 작업 시 파일 충돌 | git worktree로 파티션 (§6) |
| 범위 욕심 (기능 늘리기) | 첫 루프는 한 기능. PM 문서가 범위 고정 |
