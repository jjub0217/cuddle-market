# 예약과 결제: 설계

> 2026-11-01(일). 판매자가 채팅한 상대 한 명을 골라 상품을 예약하고, 그 예약자가 채팅방에서 토스페이먼츠 **테스트 모드**로 결제한다.
> 범위는 **서버(cmarket_api) + 웹**이다. 앱은 하지 않는다. 목표는 2026-11-02(월) 전에 운영 배포.

## 1. 왜 만드나

지금 "예약중"은 상품에 붙는 표시일 뿐이다. 서버는 누구와 예약했는지 모르고, 예약된 상품에도 누구나 새 채팅을 걸 수 있다. 결제 기능은 웹과 서버 어디에도 없다.

이번 작업은 "채팅으로 이야기가 끝난 상대와만 거래가 이어지는" 흐름을 만든다. 판매자가 상대를 정하고, 그 상대만 대화와 결제를 이어 간다. 실제 돈은 오가지 않는다(테스트 키).

## 2. 목표, 하지 않는 것, 실패로 보는 것

**목표**
- 판매자가 마이페이지에서 "예약중"을 고를 때, 그 상품으로 채팅한 상대 중 한 명을 골라 예약한다.
- 예약된 동안에는 예약자만 판매자와 대화하고, 예약자만 결제할 수 있다.
- 예약자가 채팅방에서 카드로 결제하면 상품이 "판매 완료"가 되고 그 채팅방은 대화가 끝난다.

**이번에 하지 않는 것**
- 결제 취소, 환불.
- 상세 화면의 "바로구매"(누구나 선착순 구매)와 상세 화면의 "결제하기". 결제 단추는 채팅방에만 둔다.
- 일정 시간이 지나면 예약이 저절로 풀리는 기능. 판매자가 직접 판매중으로 되돌린다.
- 구매 내역 화면. 결제 기록은 서버에만 남긴다.
- 앱(React Native), 운영 결제(`live_` 키), 카드 말고 다른 결제 수단.

**실패로 보는 것 (동작해도 실패)**
- 예약자가 누구인지 다른 사람 화면이나 응답에 드러난다. 판매자 본인의 예약 상대 목록만 예외다.
- 예약자가 아닌 사람이 예약된 상품으로 결제하거나, 새 채팅을 걸거나, 멈춘 채팅방에 메시지를 보낸다(웹을 조작해도 서버가 막아야 한다).
- 웹이 보낸 금액으로 결제가 확정된다. 금액은 서버가 저장한 값과 맞을 때만 확정한다(토스 공식 문서의 필수 검증).
- 결제 비밀 키가 웹 코드, 저장소, 응답, 로그, 대화에 나온다.
- `live_` 키가 들어와 실제 돈이 나간다.

## 3. 사용자 흐름 (사용자가 정함)

```
1. B 가 "신발" 을 판매 상품으로 올린다
2. A(그리고 C 등 누구나) 가 B 에게 채팅을 건다
3. 대화가 끝나면 B 가 마이페이지에서 "예약중" 을 고른다
   → 이 상품으로 채팅한 상대 목록이 뜨고, B 가 A 를 고른다
4. 목록·상세 썸네일에는 "예약중" 배지만 보인다 (누가 예약했는지는 안 보인다)
5. 예약된 동안 A 말고는 새 채팅을 걸 수 없고, C 와 B 가 쓰던 방은 잠시 멈춘다
6. A 가 B 와의 채팅방에서 "결제하기" 를 눌러 카드로 결제한다
7. 결제가 끝나면 상품은 "판매완료" 배지가 붙고, A 와 B 의 채팅방은 대화가 끝난다
```

A 가 결제하지 않으면 B 가 마이페이지에서 판매중으로 직접 되돌린다. 그러면 C 와의 방이 다시 열린다.

## 4. 사용자가 정한 것 (2026-10-31 ~ 11-01)

| 항목 | 정한 내용 |
|---|---|
| 예약자 기억 | 서버가 상품에 예약자를 저장하고, 화면에는 보여 주지 않는다 |
| 예약 상대 고르기 | 마이페이지에서 "예약중"을 고르면 이 상품으로 채팅한 상대 목록이 뜨고 그중에서 고른다 |
| 목록에 보이는 이름·사진 | 채팅방에 저장된 값(방에 들어온 시점의 닉네임·프로필 사진). 채팅 목록과 같은 값 |
| 결제 뒤 | 상품은 판매 완료, A 와 B 의 채팅방은 메시지를 주고받을 수 없다 |
| 예약 중 C 의 방 | "예약된 상품" 안내와 함께 대화가 잠시 멈춘다 |
| 예약을 풀면 | B 가 직접 판매중으로 되돌린다. C 의 방은 다시 정상 대화 |
| 결제 금액 | 결제하는 순간의 상품 가격. 깎았으면 B 가 상품 수정에서 가격을 고친다 |
| 결제 단추 위치 | 채팅방 한 곳(A 의 방)만. 상세 화면에는 두지 않는다 |
| 바로구매 | 하지 않는다 (선착순 구매라 이 흐름과 성격이 다르다) |
| 취소·환불 | 이번에 하지 않는다 |
| 앱·기존 예약 | 예약자가 비어 있는 예약중은 지금처럼 동작한다. 앱은 고치지 않는다 |
| 약관 문구 | 결제 문장을 사실에 맞게 최소한으로 고치고, 결제 화면에 "테스트 결제" 안내를 붙인다 (11절) |

## 5. 지금 코드 (2026-10-31 조사)

- 거래 상태는 `TradeStatus` 의 `SELLING · RESERVED · COMPLETED` 셋이다(`cmarket-domain/.../product/model/TradeStatus.java`). 칸은 `Product.tradeStatus`(문자열 20자). **예약자·구매자 칸은 없다.** `Product` 는 생성자에 `@Builder` 가 붙어 있다.
- 상태 바꾸기는 `PATCH /api/products/{id}/trade-status { tradeStatus }` 하나다. 판매자만 바꿀 수 있고, **바꾸는 순서를 막지 않는다**(판매 완료 → 판매중도 된다). 바뀌면 찜한 사람에게 `PRODUCT_FAVORITE_STATUS_CHANGED` 알림이 간다.
- 웹에서 상태를 바꾸는 곳은 두 곳이다.
  - 마이페이지 판매 목록(`src/features/my-page/components/MyList.tsx`): 데스크탑 드롭다운, 휴대폰 ⋮ 메뉴. REST 로 부른다.
  - 채팅방 메뉴의 "판매완료 처리"(`src/features/chatting-page/components/ChatRoomInfo.tsx`): GraphQL `updateTradeStatus` 로 같은 주소를 부른다.
- 채팅방은 상품 하나에 구매자마다 따로 만들어진다. 참여자는 `ChatRoomUser`(방 번호, 사람 번호, `isActive`, **참여 시점의 닉네임·프로필 사진 저장값**, 마지막 메시지 시각)다.
  - 채팅을 걸 때(`ChatServiceImpl.createChatRoom`)는 상품 존재와 "내 상품이 아닌지"만 본다.
  - 메시지를 보낼 때(`sendMessage`)는 참여자인지, 나갔는지, 차단했는지만 보고, **상품 상태는 보지 않는다.**
- 메시지 종류에 `SYSTEM` 이 이미 있고(`MessageType.java`), 웹 `ChatLog.tsx` 가 그린다.
- 결제 코드는 웹과 서버 모두 없다. 운영 DB 는 `ddl-auto=update` 라 새 칸과 테이블은 자동으로 생긴다.
- 이용약관(`src/app/(main)/terms/page.tsx:219`)과 개인정보처리방침(`privacy/page.tsx:161`)에 "결제를 처리하지 않습니다"가 있다.

## 6. 상태와 채팅이 열리는지

상품에 칸 하나를 더한다: `reservedBuyerId`(예약자 사람 번호, 비어 있을 수 있음). 응답 DTO 에는 넣지 않는다.

**상태 바꾸기 규칙**

```
SELLING   → RESERVED   새 예약 주소: 예약자를 받는다 (웹 마이페이지)
                        기존 PATCH 로 RESERVED: 지금처럼 허용하되 예약자는 비어 있다 (앱, 옛 방식)
RESERVED  → SELLING    기존 PATCH. 예약자를 지운다
RESERVED  → RESERVED   (다른 사람으로 바로 바꾸기) 거절. 판매중으로 되돌린 뒤 다시 예약한다
RESERVED  → COMPLETED  결제가 끝나면 서버가 바꾼다
                        B 가 채팅방 메뉴 "판매완료 처리"로 직접 바꾸는 것도 그대로 둔다 (현금 거래 등)
SELLING   → COMPLETED  지금처럼 허용
COMPLETED → 다른 상태   이 상품에 완료된 결제가 있으면 거절. 없으면 지금처럼 허용
```

**채팅방이 열리는지** (상품 상태, 예약자, 완료된 결제로 그때그때 계산한다)

```
SELLING                      모든 방 열림
RESERVED + 예약자 있음          예약자의 방만 열림. 나머지 방은 "예약됨" 으로 멈춤
RESERVED + 예약자 없음          지금과 같다 (막지 않는다, 결제 단추 없음)
COMPLETED + 완료된 결제 있음   모든 방 닫힘. 예약자의 방은 "거래 완료", 나머지는 "판매 완료"
COMPLETED + 결제 없음         지금과 같다 (막지 않는다)
```

- 멈추거나 닫힌 방에는 **양쪽 모두** 보낼 수 없다. 서버 `sendMessage` 가 거절한다.
- **예약자가 비어 있는 예약중은 지금과 똑같이 동작한다(사용자 결정, 2026-11-01).** 이미 배포된 앱이 상대 없이 예약중으로 바꾸고, 운영 DB 에 이미 예약중인 상품도 예약자가 비어 있기 때문이다. 이 경우 채팅을 막지 않고 결제도 없다. 새 기능은 웹에서 상대를 골라 예약했을 때만 켜진다. 데이터 이전은 하지 않는다.
- 새 채팅 걸기(`createChatRoom`): 예약자가 있는 `RESERVED` 이고 거는 사람이 예약자가 아니면 거절한다. 이미 있는 방을 돌려주는 경우도 같다.
- 채팅방 응답에 이 방의 상태를 담는다: 열림 / 예약됨 / 판매 완료 / 거래 완료, 그리고 이 방에서 결제할 수 있는지(`canPay`). 어느 값도 예약자가 누구인지 알려 주지 않는다.

**대화 기록에 남는 한 줄** (`SYSTEM` 메시지)

```
예약 걸림   예약자의 방     "예약됐어요. 여기서 결제할 수 있어요"
            나머지 방       "판매자가 다른 분과 예약해서 대화가 잠시 멈췄어요"
예약 풀림   예약자의 방     "예약이 풀렸어요"
            나머지 방       "예약이 풀려서 다시 대화할 수 있어요"
결제 완료   예약자의 방     "결제가 완료됐어요"
```

새 메시지로 들어가므로 채팅 목록에서 그 방이 위로 올라오고 안 읽음 표시가 붙는다. 문구에는 예약자를 넣지 않는다.

## 7. 예약 상대 목록과 예약 걸기 (서버)

- **목록**: 판매자 본인만 부를 수 있는 주소 하나. 이 상품의 채팅방에서 판매자가 아닌 참여자를 돌려준다.
  - 담는 것: 사람 번호, 닉네임·프로필 사진(`ChatRoomUser` 저장값), 마지막 대화 시각. 최근 대화 순.
  - 빼는 것: 방을 나간 사람(`isActive=false`), 판매자가 차단한 사람(`UserBlockRepository`), 탈퇴한 사람.
- **예약 걸기**: 판매자 본인만. 받는 것은 예약자 사람 번호. 상품이 `SELLING` 이고, 그 사람이 위 목록에 있어야 한다. 성공하면 `RESERVED` + `reservedBuyerId` 저장 + 6절의 한 줄들.
- 판매 요청 글(`REQUEST` 종류)은 예약을 쓰지 않으므로 이 주소들은 판매 상품만 받는다.

## 8. 결제 (서버)

토스페이먼츠 공식 문서(docs.tosspayments.com, 2026-11-01 확인)에 따른다.

```
1) 주문 준비   A 가 "결제하기" → 웹이 우리 서버에 주문을 만든다
               서버: 상품이 RESERVED, 요청자 = 예약자, 가격 > 0, 완료된 결제 없음 을 확인
                     주문 번호(6~64자 무작위)와 금액(= 지금 상품 가격)을 저장 (상태 READY)
               응답: 주문 번호, 금액, 주문 이름(상품 제목)

2) 결제창      웹이 토스 SDK 로 카드 결제창을 연다. 성공·실패 주소는 우리 웹 페이지

3) 결제 확정   성공 주소로 돌아온 paymentKey · orderId · amount 를 웹이 우리 서버로 보낸다
               서버: 주문이 READY 이고, 요청자 = 주문한 사람이고,
                     받은 금액 = 저장한 금액 = 지금 상품 가격 이고,
                     상품이 아직 이 사람으로 RESERVED 일 때만
                     토스 결제 승인 API(POST https://api.tosspayments.com/v1/payments/confirm,
                     비밀 키 Basic 인증, Idempotency-Key) 를 부른다
               승인되면: 주문 DONE(paymentKey, 승인 시각 저장) → 상품 COMPLETED → 6절의 한 줄
               안 되면:  주문 FAILED, 웹에 알아들을 수 있는 실패 이유
```

- 가격이 0원인 상품은 토스가 결제를 받지 않으므로 예약은 되지만 `canPay` 는 거짓이다. 판매자가 "판매완료 처리"로 직접 끝낸다.
- B 가 주문 준비 뒤에 가격을 바꾸거나 예약을 풀면 3)의 조건이 깨져 승인을 부르지 않는다. A 는 다시 시도한다.
- 같은 주문을 두 번 확정하거나 한 상품에 결제가 둘 생기면 안 된다. 상품 하나에 완료된 결제는 하나뿐이다.
- **테스트 키만 받는다.** 서버의 비밀 키가 `test_sk_` 로 시작하지 않거나 비어 있으면 결제 주소는 503 을 돌려준다(행사 수집 주소의 503 과 같은 방식).
- **결제 기록 테이블**(새로): 주문 번호(유일), 상품 번호, 구매자, 판매자, 금액, 상태(READY · DONE · FAILED), paymentKey, 승인 시각, 실패 이유, 만든 시각. 카드 정보는 저장하지 않는다. 엔티티는 이 저장소 관례대로 생성자에 `@Builder` 를 단다.

## 9. 웹

- **마이페이지 예약 창**: 판매 목록에서 "예약중"을 고르면(데스크탑 드롭다운, 휴대폰 ⋮ 메뉴 둘 다) 창이 뜨고 7절 목록을 보여 준다. 한 명을 골라 확정한다. 채팅한 사람이 없으면 "아직 채팅한 사람이 없어요"만 보이고 예약할 수 없다. 창 모양은 지금 쓰는 모달 부품을 따른다.
- **채팅방**
  - 6절의 방 상태가 열림이 아니면 입력칸 대신 안내를 보여 준다: "예약된 상품이에요" / "판매 완료된 상품이에요" / "거래가 끝난 채팅방이에요".
  - `canPay` 일 때만 위쪽 상품 정보 옆에 "결제하기"와 **지금 상품 가격**, "테스트 결제예요. 실제로 돈이 나가지 않아요"를 보여 준다. 채팅방에 저장된 옛 가격이 아니다.
- **결제 성공·실패 페이지**: 성공 페이지는 돌아온 값으로 우리 서버 확정을 부르고, 결과(상품 이름, 금액, 테스트 결제 안내)를 보여 준 뒤 채팅방으로 돌아갈 길을 준다. 실패 페이지는 실패 이유와 다시 시도할 길을 준다.
- **토스 SDK**: 공식 v2 SDK 를 쓴다(npm `@tosspayments/tosspayments-sdk` 의 `loadTossPayments`, 결제창 `payment().requestPayment({ method: "CARD", … })`). 토스 API 를 웹에서 직접 부르지 않는다.

## 10. 비밀 값과 설정

| 이름 | 넣을 곳 | 쓰는 곳 |
|---|---|---|
| `NEXT_PUBLIC_TOSS_CLIENT_KEY` (`test_ck_…`) | Vercel 환경 변수(Production, Preview), 로컬 `.env.local` | 웹 결제창. 브라우저에 보이는 값이라 이름에 `NEXT_PUBLIC_` 가 붙는다 |
| `TOSS_SECRET_KEY` (`test_sk_…`) | EC2 서버 환경 변수 (`export` 후 `printenv` 로 확인) | 서버 결제 승인. 서버 설정 `toss.secret-key=${TOSS_SECRET_KEY:}` |

- 두 값은 사용자가 토스페이먼츠 개발자센터에서 직접 꺼내 직접 넣는다. 대화에 붙여 넣거나 화면에 출력하지 않는다.
- 비밀 키는 `NEXT_PUBLIC_` 이름에 넣지 않는다. GitHub Secrets 에는 넣을 값이 없다(CI 는 결제를 부르지 않는다). 웹은 클라이언트 키가 없어도 빌드되고, 그때 "결제하기"는 "결제 준비 중"으로 막힌다.

## 11. 약관 문구

- 이용약관 219줄 문장을 바꾼다:
  > 서비스의 결제 기능은 토스페이먼츠 테스트 모드로 제공되며, 실제 대금은 청구되거나 이동하지 않습니다. 서비스는 대금을 대신 받아 두지 않습니다.
- 개인정보처리방침에 두 가지를 더한다: 결제 정보는 토스페이먼츠가 처리하고 서비스는 카드 정보를 저장하지 않는다. 서비스가 보관하는 결제 기록은 주문 번호, 금액, 결제 일시, 결제 상태다.
- 법률 검토를 거친 문장이 아니다. 운영 결제로 바꿀 때 다시 손본다.

## 12. 시험으로 꼭 지킬 것

- 서버: 상태 바꾸기 규칙 표 한 줄마다, 채팅 열림 표 한 줄마다(보내기와 새 채팅 걸기 둘 다), 예약 상대 목록의 빼는 사람 세 종류, 결제 확정의 각 거절 조건(금액 다름, 가격 바뀜, 예약 풀림, 남의 주문, 이미 DONE, 테스트 키 아님). 토스 API 는 가짜로 바꿔 끼워 시험한다.
- 웹: 예약 창(목록, 빈 목록, 확정), 채팅방 안내 네 가지와 결제하기가 `canPay` 일 때만 보이는지, 성공·실패 페이지.
- 응답에 예약자 번호가 없는지를 서버 시험으로 직접 본다.

## 13. 배포 순서

1. 서버: cmarket_api `main` 커밋 → push(사용자 허락) → EC2 에서 사용자가 `cp -a proxy ~/proxy-backup` → `git pull` → `cp -a ~/proxy-backup/. proxy/` → 빌드 → `TOSS_SECRET_KEY` 를 `export` 하고 `printenv` 로 확인 → 다시 켬.
2. 웹: 작업 브랜치 → develop PR(사용자가 머지) → Vercel 에 `NEXT_PUBLIC_TOSS_CLIENT_KEY`.
3. 운영 화면에서 테스트 결제 한 번: 예약 → C 의 방 멈춤 → A 결제 → 판매 완료와 방 닫힘.

서버를 먼저 올려도 지금 웹과 앱은 그대로 동작한다. 상대 없이 보내는 예약중은 옛 방식대로 받기 때문이다(6절).

**알고 넘어가는 앱의 한계**: 웹에서 예약된 상품의 멈춘 방에서, 앱은 입력칸을 그대로 보여 주고 보내기가 실패한다. 앱은 이번 범위가 아니라 다음 앱 작업에서 안내를 붙인다(사용자 결정, 2026-11-01).

## 14. 만드는 사람에게 맡기는 것

- 서버 주소 이름과 DTO 모양, 오류 코드 이름, 방 상태 값의 이름.
- 예약 상대 목록을 한 번에 가져오는 질의 방식, 결제 중복을 막는 방식(잠금이나 유일 제약).
- 결제창의 `customerKey` 값, 성공·실패 페이지 주소.
- 웹이 REST 와 GraphQL 중 어느 길로 부를지(지금 마이페이지는 REST, 채팅방 일부는 GraphQL).

## 15. 내가(Claude) 정한 것

사용자가 따로 말하지 않아 내가 정했다. 틀리면 고친다.

- 예약 중 C 와의 방은 C 와 B **양쪽 모두** 보낼 수 없다.
- 예약자를 바로 다른 사람으로 바꾸지 않고, 판매중을 거쳐 다시 예약한다.
- 결제가 있는 판매 완료 상품은 상태를 되돌릴 수 없다. 결제 없이 B 가 직접 판매 완료로 바꾼 경우는 지금처럼 둔다.
- 결제가 끝나면 예약자가 아닌 사람의 방도 "판매 완료"로 닫는다.
- B 는 결제 완료를 대화 기록의 한 줄로 안다. 따로 알림은 보내지 않는다.
- 결제 수단은 카드 하나. 서버는 테스트 비밀 키가 아니면 결제를 막는다.
- 예약 상대 목록에서 나간 사람, 차단한 사람, 탈퇴한 사람을 뺀다.
- 가격 0원 상품은 예약은 되지만 결제 단추를 띄우지 않는다.
