# 사진 확대창 설계 (#904 · 22바퀴)

> 2026-08-13(목). 사진을 눌러 **전체 화면으로 잘림 없이** 보는 창을 웹·앱에 하나씩 놓는다.
> 앞 바퀴 이어받기: `docs/superpowers/plans/2026-08-11-handoff.md`

## 왜 지금인가

중고거래에서 사진은 설명보다 중요하다. 흠집·라벨·부속품은 사진으로만 확인된다.
그런데 지금은 **사진을 눌러도 아무 일이 안 일어나고**, 상세 화면의 사진틀이 정사각형이라
세로로 긴 사진은 위아래가 잘린 채로만 보인다. 잘린 자리에 흠집이 있으면 살 사람은 영영 못 본다.

## 이미 재서 확인한 것 (다시 조사하지 말 것)

운영 CDN 의 실제 상품 사진(#73)을 직접 받아 재봤다.

```
원본   https://df1xl13ui5mlo.cloudfront.net/user/38/2026/08/05/d5ca418f-…webp
       HTTP 200 · 800 x 1715
_800   HTTP 200 · 800 x 1715      ← 원본과 똑같다
_1600  HTTP 403                   ← CDN 규칙에 아예 없다
```

올리는 쪽도 전부 800 으로 잠겨 있다.

```
웹  browser-image-compression maxWidthOrHeight: 800
    DropzoneArea.tsx:45 · ChattingPage.tsx:162 · ProfileUpdateBaseForm.tsx:87 · ProfileData.tsx:136
앱  shrinkImage()  TARGET_WIDTH = 800   (mobile/lib/product-images.ts:19)
```

여기서 결론 둘이 갈린다.

```
1600px 으로 보여주기   지금은 못 한다. 서버에 그 알갱이가 없다.
                      CDN 은 있는 사진을 줄여 주는 기계지, 없는 것을 만들어 주지 않는다.
                      되게 하려면 올리는 크기부터 키워야 하고(별도 이슈),
                      그래도 **이미 올라간 사진은 영영 800px** 이다 — 서버에도 800 짜리만 남았다

잘림 없이 보여주기     지금 바로 된다. 크기와 상관없다.
                      800x1715 라는 실측이 곧 증거다 — 비율은 멀쩡히 살아 있다.
                      정사각형으로 자르는 것은 **화면 코드일 뿐**이다(MainImage.tsx:69 의 object-cover)
```

그래서 이번 바퀴는 **「온전히 보기」와 「앱에서 손가락으로 넓히기」** 만 한다.
올리는 크기를 1600 으로 키우는 일은 따로 이슈를 열어 다음 바퀴 후보로 남긴다.

## 넓혀 보기 규칙

```
앱   핀치로 최대 3배 · 두 번 톡톡 치면 2배 ↔ 1배 · 손을 놓으면 1배 밑으로는 튕겨 돌아온다
웹   **사진 위를** 클릭하면 「화면 맞춤 ↔ 실제 크기(1:1)」 · 확대 상태에서 끌어서 이동
     ⚠️ 검은 자리 클릭은 닫기다. 사진 위와 검은 자리를 갈라서 다뤄야 한다
```

⚠️ **넓힐수록 뭉갠다.** 원래 알갱이가 800px 뿐이라 그렇다. 3배는 「더 선명해지는」 것이 아니라
「잘려 있던 자리를 보고, 뭉개짐을 감수하고 크게 보는」 것이다. 올리는 크기를 키우면(별도 이슈)
같은 화면이 그대로 선명해진다.

**웹에도 최소한을 넣는 이유** — 브라우저에 맡기면 될 것 같지만 두 가지가 걸린다.

```
① ⌘+휠 로 키우면 **사진은 커진다.** 대신 화면 전체가 커져서
   **X 단추·좌우 화살표·번호가 화면 밖으로 밀린다** — 닫을 단추를 못 찾는다.
   그래서 대체재가 못 된다. 우리 토글은 사진만 키우고 단추는 제자리에 둔다.

② 화면 맞춤은 세로로 긴 사진을 **원본보다 작게** 만든다.
   800x1715 사진을 높이 900 화면에 맞추면 폭이 420 이 된다 — 원본 800 의 절반이다.
   1:1 로 보는 것이 실제로 더 많이 보인다.
```

✅ **확인함 (2026-08-13, 크롬 데스크탑).** 처음에는 「화면을 덮는 창(fixed) 안에서는
브라우저 확대가 안 먹을 것」으로 **추정했는데 틀렸다** — 사진은 커진다. 진짜 문제는
확대가 되느냐가 아니라 **조작 단추가 같이 밀려난다**는 것이었다. 그래서 웹 확대 코드를
남기기로 했다. 추정만 믿고 지웠으면 잘못 지울 뻔했다.

### 확대 제스처는 사진 위에서만 가로챈다 (번개장터를 보고 정했다)

```
번개장터 데스크탑 웹 (2026-08-13 관찰)
  사진 위에서 벌리기     사진만 커진다
  검은 자리에서 벌리기   브라우저 확대. X 단추·번호가 화면 밖으로 나간다
```

우리도 같게 한다. 처음에는 **창 전체**를 가로챘는데, 그러면 「페이지째 키워서 보고 싶다」는
길이 아예 막힌다. 검은 자리는 일부러 브라우저에 맡긴다.

⚠️ 트랙패드로 벌리는 것과 ⌘+휠은 브라우저에 **똑같이 「ctrl 이 눌린 휠」** 로 온다.
그리고 **리액트의 `onWheel` 로는 못 막는다** — 리액트가 휠을 passive 로 달아
`preventDefault` 가 무시된다. 요소에 직접 `{ passive: false }` 로 달아야 한다.

### 두 상태의 크기

```
화면 맞춤   사진 전체가 다 보이게. **원본보다 크게는 안 키운다** — 화면보다 크면 줄일 뿐이다
크게        원본의 2배로 못 박는다. 화면을 넘치면 끌어서 본다
```

⚠️ **맞춤이 화면을 채우도록 키워도 봤지만 되돌렸다**(2026-08-13, 눈으로 견주고 정했다).
사진을 키우는 쪽보다 **위아래 검은 자리가 넉넉한 쪽이 보기 낫다**는 판단이다.

⚠️ 그때 겪은 것 — 맞춤이 커지자 **벌릴수록 사진이 작아졌다.** 「크게」가 원본 크기(1:1)라
맞춤(1.26배)보다 작아졌기 때문이다. 지금은 맞춤이 1배를 안 넘고 「크게」가 2배라 순서가
안전하다. **둘 중 하나를 손대면 이 순서부터 확인할 것.**

참고로 `max-h-full`·`max-w-full` 은 **상한만 정한다 — 원본보다 크게는 안 만든다.**
지금은 그 성질을 그대로 쓴다. 채우려면 `h-full`·`w-full` 이어야 한다.

모바일 웹의 두 손가락 확대는 막혀 있지 않다(`src/app/layout.tsx:6` — `user-scalable` 도 `maximumScale` 도 안 걸었다).

⚠️ **끌어서 움직이기는 마우스일 때만 우리가 한다.** 손가락은 `overflow-auto` 로 브라우저가
이미 밀어 주고 있어서, 우리도 밀면 둘이 겨뤄 모바일 웹에서 미끄러지듯 튄다.

⚠️ **누르자마자 붙잡으면(setPointerCapture) 확대 끄기가 창 닫기가 된다.** 붙잡은 뒤에는
뒤따라오는 click 이 사진이 아니라 **붙잡은 쪽(검은 자리)** 으로 가기 때문이다. 붙잡기는
움직이기 시작한 뒤에 건다. 2026-08-13 에 실제로 겪었고, **jsdom 에는 붙잡기가 없어
시험이 못 잡는다** — 브라우저에서만 드러난다.

**커서** — 목록 썸네일은 `pointer`(진짜로 상세로 간다), 상세 대표 사진은 `zoom-in`(확대한다),
확대창 안에서는 `zoom-in ↔ zoom-out`. `pointer` 는 원래 링크용이라 「어딘가로 간다」로 읽힌다.
셋이 다르게 보이는 것이 오히려 도움이 된다 — 커서만 봐도 이동과 확대가 갈린다.
