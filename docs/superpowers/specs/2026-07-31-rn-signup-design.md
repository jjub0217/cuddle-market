# 이메일 회원가입 설계 — 앱 7바퀴 (2026-07-31 금)

> 앱에 이메일 회원가입 화면을 만들고, 그 과정에서 드러난 **서버 쪽 구멍 하나와 웹 쪽 구멍 하나**를 같이 막는다.

---

## 1. 왜 지금 회원가입인가

지금 앱에는 **로그인만 있고 가입이 없다.** 웹에서 가입한 사람만 앱을 쓸 수 있다는 뜻이다.

Play Console에 앱 정보를 넣을 때 「계정 생성 방법」을 **「앱에서 계정을 만들도록 허용하지 않음」** 으로 신고해 두었다. 이 바퀴가 끝나면 그 신고도 고쳐야 한다.

### 순서에서 이 바퀴가 첫 번째인 이유

비공개 테스트 14일 동안 테스터 12명이 앱을 **지우지 않아야** 한다. 업데이트가 자주 오면 잘 안 지운다. 그래서 **싸고 자주 낼 수 있는 것부터** 낸다.

```
7바퀴   이메일 회원가입          🟢  ← 지금
8바퀴   앱 헤더 + 알림 목록      🟢
9바퀴   커뮤니티 읽기 + 댓글     🟡
10바퀴  소셜 로그인             🟠
11바퀴  상품 등록 · 수정         🟠
12바퀴  채팅                   🔴
```

소셜 로그인이 10바퀴로 밀린 이유는 따로 있다. 백엔드가 소셜 로그인에 성공하면 **웹 주소 한 곳으로만** 돌려보내게 돼 있어(`OAuth2LoginSuccessHandler.java:34`), 앱으로 바로 못 온다. 백엔드나 웹을 손봐야 하는 큰 일이라 뒤로 뺐다.

## 2. 목표와 범위

### 목표

앱에서 이메일로 가입하고, 가입하자마자 로그인된 상태로 홈에 들어간다. 웹과 같은 계정이 만들어진다.

### 이번에 넣는 것

| 곳 | 무엇 |
|---|---|
| 앱 | 회원가입 화면 (입력칸·검증·API 한 벌) |
| 앱 | 화면 구조 **A안(한 화면)·B안(2단계) 두 벌** — 실기기로 보고 하나 고른다 |
| 백엔드 | `signUp()`에 **이메일 인증 확인** 추가 |
| 백엔드 | 비밀번호 해시를 로그로 찍는 줄 삭제 |
| 웹 | 이메일 값이 바뀌면 **인증 상태를 푼다** |

### 이번에 안 하는 것

- **소셜 로그인** — 10바퀴
- **비밀번호 찾기** — 앱에 아직 없다. 별도
- **약관 동의 체크박스** — 웹에도 없다. 넣으려면 웹·앱 같이 해야 하므로 이번 범위 밖
- **테스트 러너 구성** — 별도 이슈 (아래 §12)

## 3. 화면 설계

### 받는 것 — 두 안이 공통으로 쓴다

칸의 종류·순서·검증은 웹과 같다. **A안과 B안이 다른 것은 이걸 한 화면에 두느냐 두 단계로 나누느냐뿐이다.**

```
┌─────────────────────────────────┐
│  ← 회원가입                      │
├─────────────────────────────────┤
│  [ 이메일 인증 영역 ]             │
│  비밀번호                        │
│  비밀번호 확인                   │
│  이름                            │
│  닉네임          [중복체크]       │
│  생년월일  [YYYY][MM][DD]         │
│  거주지 (시/도 · 구/군)  ← 필수    │
│  [ 가입하기 ]                    │
└─────────────────────────────────┘
```

### 생년월일은 세 칸으로 받는다

웹과 같이 `YYYY` / `MM` / `DD` 숫자 칸 셋이다(`BirthDateField.tsx:74,87,100`).

폰에서는 칸을 세 번 옮겨야 해서 날짜 선택기가 더 편할 수 있다. 그런데 선택기를 쓰려면 **새 의존성이 하나 늘고 웹과 모양이 달라진다.** 이번 바퀴의 목적은 가입을 되게 하는 것이지 입력 방식을 새로 만드는 게 아니므로, 웹과 같게 간다. 불편이 실제로 드러나면 그때 바꾼다.

### 인증 영역의 세 가지 상태

```
① 처음                ② 코드 보냄              ③ 인증 완료
 이메일 [        ]     이메일 [aa@bb.com] 🔒    이메일(잠김) + ✅ 인증완료
 [인증받기]            인증코드 [    ] [확인]
                       4:59
```

### 🏁 결정 — **B안(2단계)으로 확정** (2026-07-31 실기기 비교)

둘 다 만들어 Expo Go로 끝까지 가입해 보고 B안을 골랐다.

**고른 이유는 키보드다.** A안은 칸이 9개라 아래쪽(생년월일·거주지)이 키보드에 덮였다.
포커스 스크롤을 넣어 가릴 때만 밀어 올리도록 고쳤지만, 입력할 때마다 화면이 움직이는
건 남는다. B안은 1단계를 4칸으로 끊어 **애초에 가릴 일이 없다.**

탈락 근거였던 「중간 이탈 두 지점」은 실물을 보니 걱정만큼 크지 않았다. 1단계가 짧아
넘어가는 부담이 작고, `1 / 2` 표시가 있어 얼마나 남았는지 보인다.

뒤로가기도 의도대로였다 — 2단계에서 누르면 화면이 닫히지 않고 1단계로 가며 입력이 남는다.

아래는 무엇을 비교했는지에 대한 기록이다.

### 비교한 두 가지 — A안(한 화면) vs B안(2단계)

```
A안 한 화면                    B안 2단계
┌────────────────┐            ┌────────────────┐
│ 이메일          │            │ 1단계           │
│ [인증받기]      │            │ 이메일          │
│ 인증코드        │            │ [인증받기]      │
│ 비밀번호        │            │ 인증코드        │
│ 비밀번호 확인    │            │ 비밀번호        │
│ 이름           │            │ 비밀번호 확인    │
│ 닉네임 [중복체크]│            │ [    다음    ]  │
│ 생년월일        │            └────────────────┘
│ 거주지          │            ┌────────────────┐
│ [  가입하기  ]  │            │ 2단계           │
└────────────────┘            │ 이름           │
 9칸을 쭉 내려간다              │ 닉네임 [중복체크]│
                              │ 생년월일        │
                              │ 거주지          │
                              │ [  가입하기  ]  │
                              └────────────────┘
                               4칸 + 5칸으로 나눈다
```

### 왜 이 둘인가 — 원래 C안(인증 후 접기)을 뺀 이유

7/30에 안이 셋이었다(A 한 화면 / B 2단계 / C 한 화면 + 인증 접기). 그때는 C를 추천했으나, **다시 따져보니 C가 푸는 문제가 작다.**

```
접히는 시점 = 인증이 끝난 뒤
  → 이메일·코드를 입력하는 동안에는 안 접힌다 (그때가 가장 정신없다)

접힌 뒤 남는 칸 = 비번·비번확인·이름·닉네임·생년월일·시도·구군
  → 7칸. 여전히 키보드 위에 다 안 들어간다
```

**C가 줄여주는 건 두 칸뿐이다.** 반면 B는 1단계를 4칸으로 끊어 **아예 안 가리게** 만든다. 차이가 작은 둘을 비교하는 것보다 **차이가 큰 둘을 비교하는 편**이 눈으로 판단하기 쉽다.

또한 7/30 당시 C는 **사례로 뒷받침되지 않은 추론**이었다("검색으로도 인증 후 접기를 쓰는 앱 사례를 찾지 못했다"고 기록돼 있다).

### B안이 지는 부분 — 알고 고른다

| | A 한 화면 | B 2단계 |
|---|---|---|
| 만들기 | 쉽다 (웹과 같다) | 단계 전환 + 뒤로가기 처리 |
| 유지보수 | 웹과 한 벌 | **앱만 다르다** |
| 키보드 부담 | 크다 | **1단계는 없다** (2단계는 여전히 있다) |
| 중간 이탈 | 한 지점 | **두 지점** (1단계만 하고 안 돌아온다) |

**「중간 이탈 두 지점」은 근거 없는 추론이다.** 한 화면이 길어서 포기하는 쪽과 두 단계라 안 돌아오는 쪽 중 어느 게 큰지 모른다. 그래서 실물로 비교한다.

### B안의 구조

**화면을 두 개로 나누지 않고, 한 화면 안에서 단계를 바꾼다.** 입력값이 한 컴포넌트에 모여 있어 1단계로 돌아가도 값이 그대로 남는다. 라우트를 둘로 쪼개면 값을 넘기는 장치가 따로 필요하다.

- 안드로이드 하드웨어 뒤로가기: 2단계에서 누르면 **1단계로** 돌아간다(화면을 닫지 않는다)
- 1단계에서 뒤로가기: 회원가입 화면을 닫는다
- **[다음]은 이메일 인증이 끝나야 눌린다** — 인증 안 된 채로 2단계까지 채우고 막히면 최악이다

> 2단계도 칸이 5개(입력칸 7개)라 키보드에 가릴 수 있다. §8의 포커스 스크롤은 **두 안 모두에 넣는다.**

### 비교하는 방법

비교가 끝나면 진 쪽을 지운다. 비교용으로 로그인 화면에 임시 버튼 두 개를 둔다.

```
로그인 화면 (임시)
  [ 회원가입 (A안 · 한 화면) ]
  [ 회원가입 (B안 · 2단계) ]
```

**입력칸·검증·API 호출은 한 벌로 만들어 두 안이 함께 쓴다.** 다른 것은 배치뿐이다.

### 인증 후 이메일 칸을 잠그는 이유

**인증한 주소와 가입하는 주소가 달라지면 안 된다.** 이게 §7에서 다루는 웹 구멍의 원인이다.

「이메일 변경」을 누르면 ①로 되돌리고 **인증 상태도 같이 푼다.**

### 인증 완료 후 「재발송」을 막는 이유

서버는 같은 이메일로 코드를 다시 보낼 때 **기존 인증 기록을 지운다**(`EmailVerificationServiceImpl:41`). 인증이 끝난 뒤 재발송이 눌리면 이렇게 된다.

```
인증 완료 (verifiedAt 채워짐)
   ↓ 재발송
기존 기록 삭제 → 새 미인증 기록만 남음
   ↓ 가입
서버가 막는다 ❌
```

웹은 이미 막고 있다(`EmailValidCode.tsx:153`). **앱에도 반드시 옮긴다.** 안 옮기면 §6을 켜는 순간 앱에서만 가입이 안 되는 버그가 된다.

## 4. 검증 규칙

웹과 백엔드 코드에서 직접 확인한 값이다. **앱이 새로 정하지 않는다.**

규칙이 두 파일에 나뉘어 있다.
- 이메일·비밀번호: `src/lib/utils/validation/authValidationRules.ts`
- 이름·닉네임·비밀번호 확인: `src/features/signup/validationRules.ts`

| 항목 | 웹 화면 | 백엔드 (`SignUpRequest.java`) | 앱이 쓸 값 |
|---|---|---|---|
| 이메일 | `/^[^\s@]+@[^\s@]+\.[^\s@]+$/` | `@NotNull` | 웹과 같게 |
| 비밀번호 | **10~30자**, 영문 대문자·소문자·숫자·특수문자 `!@#$%^&*()` 모두 포함 | `@NotNull` | 웹과 같게 |
| 비밀번호 확인 | 위와 일치 | — | 웹과 같게 |
| 이름 | **2~10자** | `@NotNull` + `@Size(max=10)` | **2~10자** |
| 닉네임 | **2~10자** + 「중복체크」 필수 | `@NotNull` + `@Size(min=1, max=10)` | **2~10자** |
| 생년월일 | 만 14세 이상 | `@NotNull` + `validateAge` | 웹과 같게 |
| 거주지 (시/도 + 구/군) | **필수** | `@Size(max=50)` — `@NotNull` **없음** | **필수** |

**웹이 백엔드보다 엄격한 곳이 셋 있다.** 이름은 백엔드에 최소 길이가 없고, 닉네임은 백엔드가 1자부터 받고, 거주지는 백엔드가 아예 안 막는다. 앱은 **더 엄격한 웹 쪽**을 따른다 — 웹에서 가입한 사람과 앱에서 가입한 사람의 계정이 달라지면 안 되기 때문이다.

### 거주지가 필수인 근거

화면 이름은 「거주지」다(`AddressField.tsx:33`의 기본값). 필수 강제는 이 경로로 이뤄진다.

```
SignUpForm
  └ AddressField                    label 기본값 '거주지'
      └ CascadingSelectField
          ├ RequiredLabel(required 기본 true)          → 「거주지*」 별표
          ├ Controller rules={{ required: primaryRule }}    :68   시/도 필수
          └ Controller rules={{ required: secondaryRule }}  :94   구/군 필수
```

`react-hook-form`의 `handleSubmit`이 막으므로 안 고르면 가입 버튼이 진행되지 않는다. 배포된 화면에서도 「거주지\*」로 확인했다.

> `src/features/signup/validationRules.ts`에도 `addressSido`·`addressGugun`의 `required`가 있지만 **어디에도 연결돼 있지 않다.** 강제는 위 경로로만 이뤄진다. 헷갈리기 쉬우니 주의. (미사용 규칙 정리는 이번 범위 밖)

인증코드 만료는 **5분**이다(`VERIFICATION_CODE_EXPIRY_MINUTES = 5`). 화면 타이머를 `4:59`부터 내린다.

> 인증이 끝난 뒤에는 5분이 지나도 가입할 수 있다. 서버 검사가 「인증했는가」만 보고 「만료됐는가」는 안 보기 때문이다(§6). 칸이 9개라 5분 안에 다 채우기 빠듯한데, 다행히 안 막힌다.

## 5. 쓰는 API

웹 `src/lib/api/auth.ts`와 같다.

```
GET  /auth/email/check?email=            이메일 중복 확인
POST /auth/email/verification/send       인증코드 발송
POST /auth/email/verification/verify     인증코드 확인  { email, verificationCode }
GET  /auth/nickname/check?nickname=      닉네임 중복 확인
POST /auth/signup                        가입
```

`POST /auth/signup` 본문:

```
email, password, name, nickname, birthDate(YYYY-MM-DD), addressSido?, addressGugun?
```

`?`는 **백엔드가 없어도 받는다**는 뜻이다. 하지만 화면에서 거주지를 필수로 받으므로(§4) **앱은 항상 채워 보낸다.**

가입에 성공하면 **곧바로 로그인 API를 불러** 세션을 만든다. 웹이 그렇게 하고 있다(`SignUpForm.tsx:111-116`).

## 6. 백엔드 — 서버에서도 인증을 확인한다

> 핸드오프에서 이걸 「C안」이라고 불렀다. 화면 쪽 이름과 겹쳐 헷갈리므로 **이 문서에서는 「서버 강제」라고 부른다.**

### 무엇이 문제인가

`POST /auth/signup`은 **이메일 인증 여부를 확인하지 않는다.** 운영 서버에서 실제로 확인했다(2026-07-30).

```bash
curl -X POST https://cmarket-api.duckdns.org/api/auth/signup \
  -d '{"email":"...@example.com", ...}'     # 인증코드를 받은 적이 없다
→ HTTP 201 CREATED
```

`example.com`은 메일을 받을 수 없는 도메인인데도 가입됐다. 인증 API 두 개를 **아예 부르지 않고** 가입만 했다.

**화면이 막고 있을 뿐 서버는 안 막는다.** 화면 검사는 편의(UX)이지 보안이 아니다.

### 어떻게 고치나 — 이미 있는 코드를 옮긴다

같은 검사가 **비밀번호 재설정에 이미 들어 있다**(`AuthServiceImpl:208-215`).

```java
List<EmailVerification> verifications = emailVerificationRepository.findByEmail(email);
boolean isVerified = verifications.stream().anyMatch(EmailVerification::isVerified);

if (!isVerified) {
    throw new IllegalArgumentException("이메일 인증이 완료되지 않았습니다. 인증코드를 먼저 확인해주세요.");
}
```

이걸 `signUp()`의 **나이 검증 다음**에 넣는다. `emailVerificationRepository`는 이 클래스가 이미 생성자로 들고 있다.

### 같이 지울 줄 하나

`AuthServiceImpl:80` — 암호화된 비밀번호를 로그로 찍고 있다.

```java
String encodedPassword = passwordEncoder.encode(command.getPassword());
System.out.println(encodedPassword);   // ← 지운다
```

해시라서 평문은 아니지만 로그에 남길 이유가 없다.

## 7. 웹 — 이메일이 바뀌면 인증 상태를 푼다

### 무엇이 문제인가

웹은 인증이 끝나도 **이메일 칸을 계속 고칠 수 있다.** `disabled`가 걸린 건 버튼뿐이다(`InputWithButton.tsx:67`). 그런데 이메일이 바뀌어도 **인증 상태를 끄는 코드가 없다.**

```
aa@gmail.com 인증 완료   →  isCodeVerified = true, 화면에 "✓ 인증 완료"
   ↓
이메일 칸을 bb@gmail.com 으로 고쳐 씀
   isCodeVerified = 여전히 true   ← 아무도 안 끈다
   ↓
가입 → bb@gmail.com 으로 요청이 나간다
```

`bb@gmail.com`은 인증코드를 받은 적이 없다.

### 확인한 근거 (정적 검사)

| 확인한 것 | 결과 |
|---|---|
| 상태를 바꾸는 함수 4개의 호출처 | **전부 버튼 핸들러 2개 안에만** 있다 |
| `EmailValidCode.tsx`의 `useEffect` | **0건** — 이메일 값 변화를 지켜보는 코드가 없다 |
| `authValidationRules.email` | `required`·`pattern`뿐. `onChange`·`validate` 훅 없다 |
| `<input>`의 `disabled`/`readOnly` | 없다 |
| 제출 가드 `SignUpForm.tsx:86` | 두 플래그만 본다. 이메일 값과 대조하지 않는다 |
| 실제 전송 값 `SignUpForm.tsx:101` | `data.email` — **고쳐 쓴 현재 값**이 나간다 |

> ⚠️ **브라우저에서 클릭해 재현한 것은 아니다.** 이 저장소에 테스트 러너가 구성돼 있지 않고(§12), 인증코드가 실제 메일로 와야 해서 자동 확인이 어렵다. 위는 「끄는 코드가 존재하지 않는다」는 전수 확인이다.

### 왜 이번에 같이 고치나

§6을 켜면 이 경로는 **서버가 막는다.** 막히는 게 옳지만, 화면은 「✓ 인증 완료」라고 해놓고 가입만 실패하니 사용자는 영문을 모른다. 따로 가면 그 어중간한 기간이 생긴다.

### 어떻게 고치나

이메일 값이 바뀌면 인증 관련 상태를 초기화한다. 앱처럼 칸을 잠그는 방법도 있지만, **웹은 변경을 작게 가져간다.**

## 8. 키보드 처리

### 지금 앱이 쓰는 방식

`app/login.tsx:51`

```jsx
<KeyboardAvoidingView behavior={Platform.OS === 'ios' ? 'padding' : undefined}>
  <ScrollView keyboardShouldPersistTaps="handled">
```

안드로이드는 `behavior`를 주지 않고 OS 기본 동작에 맡긴다. 입력칸이 2개뿐인 로그인에서는 이걸로 충분하다.

### 회원가입은 조건이 다르다

A안은 칸이 9개, B안 2단계도 5개(입력칸 7개)라 **키보드 위 공간에 다 안 들어간다.** 아래쪽 칸(생년월일·거주지)에 포커스했을 때 그 칸이 보이게 스크롤되는지가 관건인데, 지금 방식은 그걸 보장하지 않는다. **두 안 모두에 넣는다.**

### 결정 — 포커스 스크롤을 더한다

```
로그인과 같은 KeyboardAvoidingView + ScrollView
  + iOS   automaticallyAdjustKeyboardInsets
  + 안드로이드  칸에 포커스하면 그 칸이 보이게 스크롤
```

**새 라이브러리를 들이지 않는다.** `react-native-keyboard-controller` 같은 전용 라이브러리가 더 매끄럽지만, 새 네이티브 모듈이라 **Expo Go에서 안 돌 가능성이 크다.** 그러면 A·B를 Expo Go로 비교하는 계획 자체가 깨진다.

### 남은 확인거리

`app.json`에 `android.edgeToEdgeEnabled: true`가 켜져 있다. edge-to-edge를 켜면 안드로이드의 기본 「창 줄이기」가 예전처럼 안 먹는 것으로 알려져 있어, 지금 방식이 이미 제대로 동작하지 않을 수 있다.

**로그인 화면으로는 판별되지 않았다.** 칸이 2개라 창이 줄든 안 줄든 버튼이 같은 자리에 오기 때문이다(실기기 캡처로 확인). **회원가입 화면을 만든 뒤 Expo Go로 다시 본다.** 그때는 칸 8개짜리 실물이 있어 애매하지 않다. 문제가 남으면 안드로이드 인셋 처리를 더한다.

## 9. 조사로 확정된 사실

다음 바퀴에서도 쓸 수 있게 적어 둔다.

### 이메일 인증 기록의 구조

```
EmailVerification (엔티티)
  email · verificationCode(6자리) · expiresAt · verifiedAt · createdAt
  isVerified()  → verifiedAt != null
  isExpired()   → now > expiresAt

EmailVerificationRepository
  findByEmail(String)                    ← §6에서 쓴다
  findByEmailAndVerificationCode(...)
  deleteByEmail(String)
  deleteByExpiresAtBefore(LocalDateTime)
```

### 인증 기록은 지워지지 않는다

`verify()`는 `verifiedAt`만 채우고 기록을 남긴다. 그래서 **가입 시점에 확인할 수 있다.** 지워지는 경우는 하나뿐이다 — 같은 이메일로 코드를 다시 보낼 때(`deleteByEmail`).

`deleteByExpiresAtBefore`는 **정의만 있고 아무도 부르지 않는다.** `@Scheduled`를 전수 검색했더니 알림·SSE 두 곳뿐이었다.

> ⚠️ **부작용: 인증 기록이 계속 쌓인다.** 지우는 일정이 없다. 이번 범위는 아니지만 언젠가 정리가 필요하다(§12).

## 9-2. 검토했으나 이번엔 안 하기로 한 것 — 가입 칸 줄이기

「이탈이 걱정이면 꼭 필요한 것만 받고 나머지는 필요한 순간에 받자」는 방향을 검토했다. 조사 결과 **일부는 실제로 가능하다.**

`User.java`의 실제 제약:

```java
name         @Column(nullable = false, length = 10)               ← DB가 막는다
nickname     @Column(nullable = false, unique = true, length=10)  ← DB가 막는다
birthDate    @Column                    ← nullable ("소셜 로그인 사용자는 null일 수 있음")
addressSido  @Column(length = 50)       ← nullable
addressGugun @Column(length = 50)       ← nullable
```

| 항목 | 가입에서 뺄 수 있나 | 비용 |
|---|---|---|
| **거주지** | **뺄 수 있다** | **백엔드 변경 0** — DB도 `SignUpRequest`도 이미 선택이다 |
| 생년월일 | 못 뺀다 | 만 14세 검사가 가입 시점에 필요하다 |
| 이름 | 어렵다 | `nullable = false` — DB 마이그레이션이 필요하다 |
| 닉네임 | 못 뺀다 | 표시 이름이고 `unique` 제약도 있다 |

즉 **거주지는 백엔드가 이미 선택으로 열어뒀는데 화면만 필수로 막고 있다.**

그리고 「가입 후에 부족한 정보를 채우게 하는」 흐름이 이미 있다 — 소셜 가입자는 카카오·구글이 지역·생일을 안 주므로 `SocialCallback.tsx:23`이 추가 입력 화면으로 보낸다.

**그럼에도 이번엔 그대로 둔다.** 줄어드는 폭이 9칸 → 7칸으로 크지 않고, 웹·앱 가입 화면과 계정 데이터를 갈라놓을 위험 대비 이득이 작다. **다음에 이탈이 실제 문제로 드러나면 이 조사 결과를 그대로 쓰면 된다.**

## 10. 하지 않는 것

- **단계별 화면(스텝)** — 한 화면으로 충분하다
- **새 폼 라이브러리** — 앱은 지금 손으로 검증한다(`login-form.tsx`). 회원가입은 칸이 많아 고민했지만, 라이브러리를 들이면 앱 전체에 영향이 간다. 이번엔 손으로 간다
- **전용 키보드 라이브러리** — §8
- **웹 화면의 이메일 칸 잠금** — 웹은 상태 해제만으로 충분하다
- **약관 동의** — 웹에도 없다. 넣으려면 웹·앱 같이 해야 한다

## 11. 완료 기준

```
□ 앱에서 이메일로 가입이 되고, 곧바로 로그인된 상태로 홈에 들어간다
□ A안(한 화면)·B안(2단계)을 실기기에서 눌러 보고 하나를 골랐다. 진 쪽과 임시 버튼을 지웠다
□ 인증 완료 뒤 이메일 칸이 잠기고, 「이메일 변경」으로만 풀린다
□ 인증 완료 뒤 재발송이 눌리지 않는다
□ 인증 없이 가입을 시도하면 서버가 막는다 (curl로 확인)
□ 웹에서 인증 후 이메일을 고치면 인증 표시가 사라진다
□ 웹 기존 가입 흐름이 그대로 된다
□ 앱: tsc · lint · jest 통과
□ 웹: tsc · 바뀐 파일 eslint 통과
□ Play Console 「계정 생성 방법」 신고를 고친다
```
