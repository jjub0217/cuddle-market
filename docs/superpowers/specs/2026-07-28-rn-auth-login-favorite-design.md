# 앱 로그인 + 찜 설계 (RN 협업 3바퀴)

작성일: 2026-07-28 (화)
관련: `2026-07-19-rn-app-monorepo-design.md`, `2026-07-21-rn-home-slice-requirements.md`,
`2026-07-23-rn-product-detail-design.md`

## 1. 목적

앱에 **인증 배관**을 놓고, 그 위에서 도는 첫 기능으로 **찜**을 붙인다.

지금까지 앱이 부른 API는 로그인이 필요 없는 공개 조회 두 개뿐이었다(`mobile/lib/products.ts`의
순수 `fetch`). 상세 화면의 찜·채팅·신고 버튼을 못 붙인 것도 토큰을 실을 방법이 없어서였다.
이번 바퀴의 새 축은 **"내가 누구인지 서버에 증명하며 요청하기"** 다.

찜을 첫 기능으로 고른 이유: 인증된 쓰기 요청 중 가장 작다(버튼 하나, 응답 하나). 화면을 크게
만들지 않고도 "토큰이 진짜 실려서 서버가 나를 알아보는가"를 증명할 수 있다.

## 2. 범위

### 들어가는 것

**앱**

- 인증 배관 — 토큰 저장(SecureStore) · 메모리 상태 · API 클라이언트(Bearer 부착, 401 갱신)
- 로그인 화면 (이메일 + 비밀번호)
- 「마이」 탭 — 게스트면 로그인 화면으로, 로그인 상태면 마이페이지
- 마이페이지 — 프로필 · 고객지원 · **계정(로그아웃 · 탈퇴하기)**
- 탈퇴 모달 (사유 · 상세사유 · 주의사항 · 동의)
- 상품 상세의 **찜 버튼**

**웹**

- W1. 로그인 화면에서 모바일 폭 전용 문구 "우리 아이를 위한 / 믿음직한 선택" 제거
- W2. 마이페이지 모바일 「고객지원」 아래에 「계정」 카드 추가 → 로그아웃 · 탈퇴하기

### 빠지는 것과 이유

| 빠지는 것 | 이유 | 다시 볼 시점 |
|---|---|---|
| 소셜 로그인 (카카오 · 구글) | 앱은 서버가 `cuddle://` 딥링크로 되돌려줘야 하는데, 그 리다이렉트를 서버가 허용하는지 미확인. 확인 전엔 막힐 위험이 큼 | 소셜 바퀴 |
| 회원가입 · 비밀번호 찾기 | 화면이 통째로 필요. 이메일 인증코드 발송·확인 흐름까지 딸림 | 소셜/회원가입 바퀴 |
| 찜한 상품 목록 · 내 상품 목록 화면 | 목록 화면 두 개 + 무한스크롤. 인증과 섞으면 "인증이 틀렸나 목록이 틀렸나" 구분이 어려워짐 | **바로 다음 바퀴** |
| 신고하기 | 사유 선택 + 이미지 다중 업로드(FormData) 모달이 통째로 필요 | 신고 바퀴 (다음다음) |
| 채팅하기 | STOMP 웹소켓 · 방 목록 · 방 화면까지 딸린 별도 서브시스템 | 채팅 바퀴 (마지막) |
| 내 글 · 차단 유저 | 앱에 커뮤니티가 아예 없음 | 커뮤니티가 생길 때 |
| 웹 로그인 폼 라벨 추가 | 현재 placeholder만 쓰지만, 데스크탑 디자인에 영향이 가는 별개 변경 | 별도 이슈 |

### 앞으로의 순서 (합의됨)

```
3바퀴(이번)  로그인 + 찜
4바퀴        찜한 상품 · 내 상품 목록
5바퀴        신고하기
6바퀴        채팅
언젠가        소셜 로그인 + 회원가입
```

## 3. 사전 확인한 사실

추측이 아니라 코드·문서로 확인한 것만 적는다.

**API** (웹 코드에서 확인)

| 하는 일 | 요청 | 비고 |
|---|---|---|
| 로그인 | `POST /auth/login` | 응답 body에 `accessToken` · `refreshToken` · `user` |
| 토큰 갱신 | `POST /auth/refresh` | body `{ refreshToken }` → `data.accessToken` |
| 로그아웃 | `POST /auth/logout` | 인증 필요 |
| 내 프로필 | `GET /profile/me` | |
| 탈퇴 | `DELETE /auth/withdraw` | body `{ reason, detailReason }` |
| 찜 토글 | `POST /products/{id}/favorite` | **켜고 끄는 게 같은 주소**. DELETE 없음 |

탈퇴 사유 5종(`src/constants/constants.ts`의 `WITHDRAW_REASON`):
`SERVICE_DISSATISFACTION` · `PRIVACY_CONCERN` · `LOW_USAGE` · `COMPETITOR` · `OTHER`

**expo-secure-store, SDK 54** (공식 문서 `docs.expo.dev/versions/v54.0.0/sdk/securestore` 확인)

- Expo Go에서 동작한다 (지문인식 옵션만 제외)
- **값 하나당 약 2048바이트 제한** (iOS에서 역사적으로 그 이상을 거부한 사례)
- 웹 플랫폼 미지원 — 실기기로만 테스트하므로 무관
- 안드로이드는 앱 삭제 시 값도 삭제, iOS는 재설치해도 남음

**타입**

`isFavorite`은 `boolean | null` (`packages/shared/src/types/product.ts`). 비로그인 조회에는 값이
없다. → **로그인 직후 상세를 다시 받아야 하트가 채워진다.**

## 4. 접근: 왜 웹을 그대로 베끼지 않는가

웹은 `user + accessToken + refreshToken`을 zustand `persist`로 **한 덩어리 JSON**에 담아
localStorage에 넣는다. 그대로 옮기면 JWT 두 개 + 프로필이 합쳐져 **2048바이트를 넘길 수 있고**,
넘으면 저장이 조용히 실패한다.

그래서 저장할 것을 쪼개고 줄인다.

| 무엇 | 어디에 | 왜 |
|---|---|---|
| accessToken | SecureStore, 독립 키 | 값 하나씩 나눠 2KB 제한 회피 |
| refreshToken | SecureStore, 독립 키 | 〃 |
| 로그인 여부 · 메모리 토큰 | zustand (persist 안 씀) | 화면들이 구독해야 함 |
| 내 프로필(user) | TanStack Query `['me']` | **서버 상태라 저장할 이유가 없다.** 앱을 켤 때 새로 받으면 닉네임·사진 변경이 자동 반영된다 |
| HTTP | `fetch` 래퍼 | 기존 `products.ts`와 같은 결. 새 의존성 없음 |

새로 들이는 의존성은 **`expo-secure-store`와 `zustand` 둘뿐**이다.

**왜 React Context가 아니라 zustand인가.** `fetch` 래퍼는 리액트 컴포넌트가 아니라서 Context를
읽을 수 없다. Context로 가면 "Context용 상태"와 "래퍼가 읽을 모듈 변수"를 둘 다 두고 손으로
맞춰야 하고, 어긋나면 *로그인은 됐는데 요청에 토큰이 안 붙는* 증상이 난다. zustand는
`getState()`로 리액트 밖에서도 읽힌다 — 웹 `api.ts`가 `useUserStore.getState()`를 쓰는 이유와 같다.

**왜 axios가 아닌가.** 웹은 axios 인터셉터를 쓰지만, 앱은 이미 `fetch`로 통일돼 있고 RN에서
axios가 주는 이점이 없다. 인터셉터가 하는 일(토큰 부착 · 401 재시도)은 래퍼 함수 하나로 충분하다.

## 5. 모듈 경계

```
mobile/lib/auth/
  tokens.ts     SecureStore 읽기·쓰기·삭제. 키 2개로 분리.
                ★ SecureStore를 아는 파일은 여기 하나뿐.
  store.ts      zustand. 메모리 토큰 + 상태('restoring' | 'authed' | 'guest').
                리액트 밖에서도 getState()로 읽힌다.
  api.ts        apiFetch(). Bearer 부착 → 401이면 갱신 → 1회 재시도.
  session.ts    login() / logout() / withdraw() / restore().
                서버 · store · SecureStore 세 곳을 한 번에 맞추는 자리.

mobile/lib/
  profile.ts    fetchMe()       GET /profile/me
  favorites.ts  toggleFavorite(id)  POST /products/{id}/favorite
  products.ts   (기존 그대로 — 공개 조회라 토큰 없음)

mobile/hooks/
  use-me.ts        useQuery(['me']) — 'authed'일 때만 실행
  use-favorite.ts  useMutation + 캐시 낙관적 갱신
```

저장소를 나중에 바꿔도 `tokens.ts` 밖은 손대지 않는다.

## 6. 화면 배치

```
[루트 스택]
 ├─ (tabs) ─┬─ (home)  목록 → 상세(♡)
 │          └─ (my)    마이페이지        ← 지금의 Explore 탭을 이걸로 교체
 └─ login   ← 탭바까지 통째로 덮는 화면
```

**Explore 탭은 교체해서 없앤다.** 지금 `mobile/app/(tabs)/explore.tsx`는 Expo 템플릿이 만들어준
빈 껍데기라 앱에서 쓰이지 않는다. 새 탭을 옆에 추가하면 빈 껍데기가 그대로 남아 어수선해지므로,
그 자리를 「마이」가 가져간다. 탭은 계속 2개(홈 · 마이)다.

**`redirectUrl`이 필요 없다.** 웹은 로그인 후 돌아갈 주소를 store에 저장하지만, 앱은 로그인
화면이 *위에 얹히는* 구조라 **성공 후 닫기만 하면 원래 자리**다.

### 무한 루프 함정

"게스트가 마이 탭을 누르면 로그인 화면으로"를 순진하게 만들면:

```
마이 탭 누름 → 마이 화면 열림 → "게스트네?" → 로그인 화면으로 밀어냄
                    ↑                                    │
                    └──────── 로그인 취소하고 뒤로 ←──────┘
                              무한 루프
```

취소하면 마이 화면으로 돌아오고, 마이 화면이 또 밀어내서 빠져나갈 수 없다.
**마이 화면을 열지 않고, 탭을 누르는 순간에 가로챈다:**

```
마이 탭 누름 ─ 게스트? ─ 예 → 탭 전환을 취소하고 로그인 화면만 띄움
                       │        (원래 보던 탭이 그대로 남아, 취소하면 거기로)
                       └ 아니오 → 평소대로 마이 탭 전환
```

## 7. 데이터 흐름

### 7.1 로그인

```
[로그인 화면] 이메일·비번 → POST /auth/login
                              ↓ {accessToken, refreshToken, user}
        ┌─────────────────────┼─────────────────────┐
        ↓                     ↓                     ↓
  SecureStore              store             TanStack Query
  키 2개로 저장         메모리 + 'authed'    ['me']에 user 미리 넣기
                              ↓
              ['product', id] · ['products'] 무효화
              → 상세를 다시 받아 isFavorite 채워짐
                              ↓
                     로그인 화면 닫기 → 원래 자리
```

마지막 무효화가 없으면 *로그인은 됐는데 하트가 빈 채로* 남는다(§3의 `isFavorite: boolean | null`).

### 7.2 앱 재시작 (복원)

```
앱 시작 → SecureStore에서 토큰 2개 읽기 (수십 ms)
   ├─ 없음 → 'guest'. 끝.
   └─ 있음 → 'authed'로 두고 화면 먼저 띄움
              ↓ (뒤에서 조용히)
           GET /profile/me
              ├─ 성공 → 프로필 최신화
              └─ 401  → §7.3 갱신 흐름
```

토큰이 살아있는지는 서버만 안다. **일단 로그인된 것으로 치고 화면을 띄운 뒤 첫 요청이 실패하면
그때 정리**한다. 확인될 때까지 스플래시를 붙잡으면 앱 실행이 매번 느려진다.

### 7.3 401 → 토큰 갱신

```
apiFetch(요청) ── 401? ──아니오──→ 그대로 반환
                    │
                   예
                    ↓
        갱신이 이미 돌고 있나?
         ├─ 예  → 그 결과를 같이 기다림   ← 동시에 3개가 401나도 갱신은 1번
         └─ 아니오 → POST /auth/refresh {refreshToken}
                    ├─ 성공 → 새 토큰 저장 → 원래 요청 1번만 재시도
                    └─ 실패 → 세션 정리('guest') → 원래 요청은 실패로 반환
```

**웹과 일부러 다르게 가는 곳.** 웹은 갱신 실패 시 `window.location.href`로 로그인 페이지에
강제 이동시킨다. 앱에서 그러면 상품을 보다가 화면이 통째로 튕긴다. 앱은 **조용히 게스트로
되돌리고 화면은 그대로 두고**, 다음에 인증이 필요한 동작을 누를 때 로그인 화면을 띄운다.

### 7.4 찜 토글

```
[♡] 탭 ─ 게스트? ─예→ 로그인 화면 (로그인하면 §7.1 → 하트 채워짐)
           │
          아니오
           ↓
   캐시를 먼저 뒤집는다 (하트 즉시 반전 + 찜 수 ±1)
           ↓  ['product', id] 와 ['products'] 목록 캐시 둘 다
   POST /products/{id}/favorite
     ├─ 성공 → 무효화해서 서버 값으로 재확인
     └─ 실패 → 뒤집었던 캐시 원복 + 안내
```

웹은 하트를 `useState`로 따로 들고 있어서 서버 값이 바뀔 때마다 `useEffect`로 맞춰준다
(`src/hooks/useFavorite.ts`). 앱은 **캐시를 직접 뒤집는 방식**으로 간다 — 상세와 홈 목록의
하트가 한 번에 맞춰져서, 상세에서 찜하고 뒤로 나갔을 때 목록 하트가 어긋나지 않는다.

### 7.5 로그아웃 / 탈퇴

```
[로그아웃] → 확인 모달 → POST /auth/logout ─(실패해도 계속)─┐
                                                            ↓
[탈퇴하기] → 사유·상세·동의 모달 → DELETE /auth/withdraw ───┤
                                                            ↓
                          SecureStore 비우기 + store 'guest'
                          + 쿼리 캐시 전부 비우기(남의 찜 정보 잔상 방지)
                                                            ↓
                                                      홈 탭으로 이동
```

로그아웃 API가 실패해도 **기기 쪽 정리는 반드시 진행**한다. 서버가 못 받았다고 기기에 토큰을
남기면 "로그아웃했는데 로그인돼 있는" 상태가 된다. (웹 `useLogout`도 `finally`에서 같은 처리)

## 8. 화면

### 8.1 로그인 화면의 최종 목표 (합의됨)

**모바일 폭 웹 · 앱 = 2단계(A), 데스크탑 웹 = 1단계(B).**

```
A안 최종 (모바일·앱)                    B안 (데스크탑 웹, 현행 유지)
┌──────────────┐                       ┌──────────────┐
│  [로고]       │                       │  [로고]       │
│ [이메일로]    │ ─탭─┐                 │ 이메일 [___]  │
│ [카카오]      │     │                 │ 비번  [___]  │
│ [구글]        │     │                 │ 비밀번호 찾기  │
│ [Apple]      │     │                 │ [ 로그인 ]    │
│  회원가입      │     │                 │ ── 소셜 ──   │
└──────────────┘     ↓                 │ [카카오][구글] │
       ┌──────────────────┐            │  회원가입      │
       │ 이메일로 로그인하기 │            └──────────────┘
       │ ...폼...          │
       └──────────────────┘
```

**A를 목표로 정한 근거**

1. **"이메일 유저가 매번 +1탭"은 실제로 매번이 아니다.** 자동 로그인이 있어 로그인 화면은
   토큰이 완전히 만료됐을 때만 본다.
2. **최종 소셜 버튼은 3개가 될 가능성이 높다.** 애플 앱스토어 심사 규정 4.8상, 다른 소셜
   로그인을 제공하는 앱은 "Apple로 로그인"도 넣어야 한다. B는 한 화면에 요소가 8개가 된다.
3. **키보드.** 모바일에서 키보드는 화면의 40~50%를 덮는다. B는 이메일 칸을 탭하는 순간 소셜
   버튼과 회원가입 링크가 가려져, 마음을 바꾸려면 키보드를 내리고 스크롤해야 한다.

데스크탑을 B로 두는 이유는 세로 공간이 넉넉해 8개가 다 보이고 키보드가 화면을 덮지 않기 때문.
관문을 만들 이유가 없고 기존 디자인도 보존된다.

**이번 바퀴에 드는 비용은 0이다.** 소셜이 없는 지금은 A의 두 번째 화면이 곧 유일한 화면이라,
만들 물건이 B와 똑같다. 차이는 소셜 바퀴에서 앞에 관문 화면을 얹느냐뿐이다. 웹도 이미
`LoginForm` / `SocialLoginButtons`가 별도 파일로 쪼개져 있어 A로 옮기기 쉽다. 앱도 폼을
화면과 분리해 만들어 둔다.

### 8.2 이번에 만드는 앱 로그인 화면

```
┌────────────────────────┐
│  ‹                     │  ← 닫기(원래 자리로)
│  이메일로 로그인하기      │
│                        │
│  이메일 주소            │  ← 라벨
│  [__________________]  │
│  비밀번호               │  ← 라벨
│  [__________________]  │
│  이메일 또는 비밀번호가   │  ← 오류일 때만
│  일치하지 않습니다.       │
│  [      로그인       ]  │
└────────────────────────┘
```

- "우리 아이를 위한 믿음직한 선택" 문구 없음
- **라벨을 단다** — 웹은 placeholder만 써서 입력을 시작하면 무슨 칸인지 사라지지만, 앱은 화면을
  새로 만드는 거라 추가 비용이 없다. (웹 라벨 추가는 이번 범위 밖)
- 비밀번호 찾기 · 회원가입 링크는 **넣지 않는다** — 앱에 해당 화면이 없어 눌러도 갈 곳이 없다.
  소셜/회원가입 바퀴에서 화면과 함께 살린다.
- 입력 검증은 손으로(이메일 형식 · 빈 값). 입력 2개 때문에 폼 라이브러리를 새로 들이지 않는다.

### 8.3 앱 마이페이지

```
┌────────────────────────┐
│  마이                   │
├────────────────────────┤
│ ┌────────────────────┐ │
│ │ (아바타) 닉네임      │ │  ← GET /profile/me
│ │          지역        │ │
│ └────────────────────┘ │
│ ┌────────────────────┐ │
│ │ 고객지원            │ │
│ │  🎧 고객센터      › │ │  ← 웹과 같은 mailto
│ └────────────────────┘ │
│ ┌────────────────────┐ │
│ │ 계정                │ │
│ │  로그아웃         › │ │
│ │  탈퇴하기         › │ │
│ └────────────────────┘ │
├────────────────────────┤
│   [홈]        [마이]    │
└────────────────────────┘
```

프로필 카드는 **아바타 · 닉네임 · 지역**만 쓴다. 웹 `User` 타입에서 `email`은 `email?: string`
(선택 값)이라 소셜 가입 계정 등에서 비어 있을 수 있어, 항상 보여야 할 자리에 두지 않는다.

「내 상품 관리」·「찜한 상품」 메뉴는 **넣지 않는다.** 눌러도 갈 화면이 없는 메뉴를 두면
"준비 중" 같은 군더더기가 생긴다. 다음 바퀴에서 화면과 메뉴를 함께 넣는다.

**프로필 타입은 앱 로컬에 둔다.** 웹 `User`는 `src/types/user.ts`에 있고 `@cuddle/shared`에는
없다. 앱이 실제로 쓰는 필드는 4개뿐(`id` · `nickname` · `profileImageUrl` · 지역)이라, 웹의 14개
필드짜리 타입을 통째로 shared로 올릴 이유가 없다. `mobile/lib/profile.ts`에 필요한 만큼만
정의하고, 웹·앱이 같은 모양을 실제로 공유하게 될 때 shared로 올린다.
(2바퀴 교훈: 로직 dedup ≠ 데이터 dedup)

### 8.4 앱 탈퇴 모달

웹과 같은 항목(사유 · 상세사유 · 주의사항 · 동의 체크)을 담되, **사유 선택 방식만 다르다.**
웹은 드롭다운(`<select>`)이지만 RN엔 그런 기본 요소가 없다. 사유가 5개뿐이니 **목록으로 펼쳐
하나 고르게** 한다 — 탭 수가 오히려 줄고 드롭다운 라이브러리도 필요 없다.

### 8.5 상품 상세의 찜 버튼 위치

**본문 인라인(판매자 카드 아래).** 웹과 순서가 같아 대조하기 쉽고 구현이 가장 단순하다.

```
┌────────────────────┐
│ ‹  상품 상세        │
├────────────────────┤
│   [   이미지   ]    │
│  제목 · 가격        │
│  판매자 카드        │
│  ┌──────────────┐  │
│  │  ♡  찜하기    │  │ ← 여기
│  └──────────────┘  │
│  설명 ...          │
│  조회 · 찜          │
└────────────────────┘
```

**하단 고정 바는 채팅 바퀴로 미룬다.** 지금 채팅이 없는 상태에서 하단 바를 만들면 버튼 하나짜리
바가 되고, 채팅이 들어올 때 어차피 다시 짜게 된다. 채팅 버튼이 생기는 바퀴에 하단 고정 바로
승격시킨다.

모바일 폭 전용 조각만 지운다. 데스크탑 타이틀(`hidden md:block`)은 손대지 않는다.

| 메뉴 | 연결할 기존 것 |
|---|---|
| 로그아웃 | `useLogout()`의 `openLogoutConfirm()` → 기존 로그아웃 확인 모달 |

새 API도 새 모달도 만들지 않는다. 지금 웹 모바일에서 탈퇴는 *프로필 자세히* 오버레이 안에
숨어 있는데, 이걸 겉으로 꺼내는 셈이다.

## 10. 검증

### 자동 테스트

`mobile/lib/*.test.ts` 결 그대로 (`jest-expo` + `fetch` 모킹).

가장 값어치 있는 건 **`apiFetch`의 401 갱신 로직**이다. 눈으로 재현하기 어렵고 조용히 틀리기 쉽다.

- 401 → 갱신 성공 → 원래 요청을 **딱 1번만** 재시도한다
- 재시도가 또 401이어도 **무한 반복하지 않는다**
- 동시에 3개 요청이 401을 맞아도 **갱신은 1번만** 일어난다
- 갱신 실패 시 토큰이 지워지고 상태가 게스트가 된다

`toggleFavorite` · `fetchMe`는 얇은 함수라 얇게만 덮는다.

### 실기기 손 검증 (Expo Go, 순서대로)

1. 게스트로 「마이」 탭 → 로그인 화면이 뜨고, **취소하면 원래 보던 탭에 남는다** (루프 없음)
2. 틀린 비번 → 오류 문구 / 맞는 비번 → 마이페이지에 닉네임
3. 상세 `♡` → 즉시 채워지고 찜 수 +1 → **뒤로 나가서 목록 하트도 채워져 있는지**
4. 비로그인 상태에서 상세 `♡` → 로그인 화면 → 로그인 → **닫히면서 하트가 채워지는지**
5. **앱 완전 종료 후 재실행** → 로그인 유지되는지
6. 로그아웃 → 게스트 복귀 → 「마이」 탭이 다시 로그인 화면으로
7. 웹: 브라우저 폭을 줄여서 → 로그인 화면 문구 사라짐 / 마이페이지 「계정」 카드에서
   로그아웃 · 탈퇴 모달이 뜨는지

**401 재현 방법.** 만료를 기다릴 수 없으니, 저장된 accessToken 뒤에 쓰레기 문자를 붙이는
**개발 전용 버튼**을 잠깐 넣어 확인하고 지운다. (한쪽에만 표식을 심고 같은 경로로 읽어 증명)

### 사전 준비물 (사용자)

⚠️ **탈퇴는 계정이 진짜 삭제된다.** 본 계정으로 누르면 복구할 수 없다. 검증 전에 **버릴 테스트
계정**을 하나 만들어 두어야 한다.
