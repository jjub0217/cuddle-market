# 앱 「플레이스」 설계 (14바퀴)

> 2026-08-05 · 폰(리모트 컨트롤)에서 합의

## 1. 무엇을 만드나

반려동물과 갈 만한 곳을 지도에서 찾는 화면. 웹에 이미 있고(`/map`), 앱에는 없다.

```
동물병원 · 카페 · 식당 · 숙소
```

## 2. 이름은 「지도」가 아니라 「플레이스」다

웹 하단 바가 이미 그렇게 부르고 있다. **새로 짓지 않는다.**

```
웹    홈 · 커뮤니티 · 플레이스 · 채팅 · 마이
앱    홈 · 커뮤니티 · 플레이스 · ____ · 마이
                       ↑ 이번        ↑ 15바퀴
```

자리도 웹 순서 그대로 커뮤니티와 마이 사이. 아이콘도 웹과 같은 `MapPin`.

⚠️ 화면 안에서 「지도」라는 말을 쓰지 않는다. 탭 이름과 화면 이름이 다르면 같은 곳인지 헷갈린다.

## 3. 화면 모양

폰은 가로가 좁아 **웹 구조를 그대로 못 옮긴다.** 웹은 지도 옆에 목록을 세운다.

```
┌─────────────────┐
│ 동물병원 카페 식당 숙소 │  알약 · 가로 스크롤
│                 │
│      지 도       │  네이버 · 서울시청에서 시작
│    ● ● ●        │  핀
│                 │
├━━━━━━━━━━━━━━━━━┤  ← 손가락으로 끌어올린다
│ 행복동물병원      │
│ 서울시 중구 …     │
└─────────────────┘
```

**왜 끌어올리는 목록인가** — 카카오맵·네이버지도·당근 동네지도가 모두 이 모양이다. 지도를 보면서 목록도 볼 수 있다. 탭으로 전환하면 「지도에서 본 자리」와 「목록」을 동시에 못 봐서 오가는 수고가 생긴다.

**상세는 별도 화면으로 민다.** 시트 안에서 펼치는 방식도 있지만, **이 앱은 상품 상세가 이미 별도 화면**이다. 같은 앱 안의 규칙을 따른다([[2026-08-05-app-find-password-design]] §3-1과 같은 기준).

## 4. 서버와의 대화

**웹이 쓰는 것을 그대로 쓴다. 새로 만들 것이 없다.**

```
GET /places?category=&minLatitude=&maxLatitude=&minLongitude=&maxLongitude=
GET /places/{id}
```

응답 DTO를 직접 열어 확인했다(추측하지 않았다).

```
PlaceListItemDto      id · category · name · address · imageUrl
                      latitude · longitude · isRecommended
                      reviewSummary · detail(병원 전용)

PlaceDetailResponse   위 항목 + phone · operatingHours
```

`category` 값 넷: `HOSPITAL` `CAFE` `RESTAURANT` `ACCOMMODATION`

지도를 움직이면 **그때 보이는 네 귀퉁이**(min/max 위도·경도)로 다시 조회한다.

## 5. 웹과 갈리는 곳

| | 웹 | 앱 | 왜 |
| --- | --- | --- | --- |
| 목록 자리 | 지도 옆 세로 | **아래에서 끌어올림** | 폰은 가로가 좁다 |
| 상세 | 옆 사이드바 / 슬라이드 카드 | **별도 화면** | 이 앱의 상세는 다 별도 화면이다 |
| 지도 | 네이버 웹 | **네이버 앱 SDK** | 같은 네이버라 장소·좌표가 어긋나지 않는다 |

**같은 것**: 이름(플레이스), 카테고리 넷과 그 순서, 시작 위치(서울시청 37.5666 / 126.9784), 서버 주소.

## 6. 이번에 안 하는 것

```
병원 24시·응급 필터        다음 바퀴
「이 지역에서 검색」 단추    다음 바퀴 — 지금은 지도를 놓으면 바로 다시 찾는다
내 위치                   다음 바퀴 — 위치 권한을 따로 받아야 한다
장소 후기 쓰기             웹에도 없다
```

**왜 얇게 가나** — 지도는 처음 넣는 네이티브 모듈이라 **붙는지 자체가 위험**이다. 얇게 한 번 세워 실기기에서 돌아가는 걸 본 뒤에 얹는 편이 안전하다.

## 7. 층 나누기 — 폰에서 어디까지 가나

**네이티브 모듈을 새로 넣으면 개발 빌드를 다시 만들어 폰에 다시 깔아야 한다.** 그건 맥 앞에서 할 일이다. 그래서 층을 이렇게 나눈다.

```
1층  서버 붙이기 · 타입 · 시험          폰에서 됨
2층  목록·상세 화면 조각 · 시험         폰에서 됨
3층  지도 · 탭 등록 · 실기기 확인       맥 앞에서
```

1·2층이 일감의 대부분이다. 3층은 마지막에 얹는다.

⚠️ 1·2층을 만들 때 **3층이 없어도 시험이 돌게** 짜야 한다. 지도 조각을 불러오는 코드가 1·2층에 섞이면 폰에서 시험을 못 돌린다.

## 8. 미리 아는 함정

```
판 고정          expo-maps·expo-location은 npm 최신이 SDK 57용이다.
                 우리는 SDK 54 고정 — `npx expo install`로 넣어야 맞는 판이 온다
                 (SDK 54: expo-location 19.0.8 · expo-maps 0.12.10)

네이버 앱 키      키 값을 새로 받는 게 아니라 **안드로이드 패키지 이름을 등록**하는 것이
                 핵심이다(`com.cuddlemarket.app`). 네이버는 등록 하나에 웹·안드로이드를
                 함께 담을 수 있어, 기존 웹 등록에 안드로이드를 추가하면 **키가 같을 수 있다**.
                 ⚠️ 인증서 지문(SHA-1)은 **구글 지도**가 요구하는 것이다 — 네이버는 안 받는다
                 (2026-08-05 정정. 처음에 지문도 필요하다고 잘못 적었다).
                 ⚠️ 웹이 `oapi.map.naver.com` + `ncpKeyId` 를 쓴다 = **새 Maps 단독 상품**이다.
                 예전 「AI·NAVER API」 쪽에서 만들면 안 먹는다

키를 어디 두나    플러그인은 키를 `app.json` 에 적으라고 한다. 그런데 **app.json 은 커밋된다.**
                 이 키는 웹 페이지 소스에 그대로 드러나는 종류라 비밀은 아니지만(패키지 이름·
                 도메인으로 막는다), 저장소에 박아 두는 건 다른 이야기다.
                 → **app.json 을 app.config.js 로 바꿔** `process.env` 에서 읽는다.
                 설정 뼈대를 건드리는 일이라 **지도를 붙일 때 같이** 한다(3층).
                 값은 `mobile/.env` 의 `EXPO_PUBLIC_NAVER_MAP_CLIENT_ID` 에 이미 넣어 뒀다.

지도 위 겹침      끌어올리는 목록이 탭바를 덮는다. 하단 시트 여백 함정을 이미 겪었다 —
                 `insets.bottom`은 **측정되는 상자**에 줘야 한다 (#843)

다시 조회 잦음    지도를 움직일 때마다 부르면 손가락 한 번에 수십 번 나간다.
                 멈춘 뒤에 한 번만 부르게 미룬다

핀 많을 때        한 화면에 수백 개가 들어오면 느려진다. 지금은 서버가 `size`로
                 끊어 주니 그대로 쓴다. 뭉치기(클러스터)는 실제로 느릴 때 한다
```

## 9. 완료 기준

- [ ] 탭바에 「플레이스」가 웹과 같은 자리에 있다
- [ ] 카테고리를 고르면 그 종류만 지도와 목록에 나온다
- [ ] 지도를 옮기면 그 자리 장소로 목록이 바뀐다
- [ ] 목록을 끌어올려 볼 수 있고, 항목을 누르면 상세 화면이 뜬다
- [ ] 상세에 이름·주소·전화·영업시간이 나온다
- [ ] `pnpm gate:mobile` 초록
- [ ] 실기기에서 지도가 실제로 그려진다
