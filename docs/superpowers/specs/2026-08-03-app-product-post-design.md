## 0. 한 줄 요약

앱에서 **상품을 올리고 고치고 지울 수 있게** 한다. 그러려면 **사진 업로드 길**을 처음 뚫어야 하고, 그게 이번 바퀴의 알맹이다.

## 1. 왜 이번 바퀴인가

로드맵에서 11바퀴는 원래 소셜 로그인이었는데 2026-08-03에 순서를 바꿨다.

**10바퀴까지 끝난 앱이 아직 읽기 전용이다.** 지금 앱으로 할 수 있는 것은 읽기·찜·댓글/답글·신고·차단·알림이고, **상품도 글도 못 올린다.** 테스터가 14일 연속 들어올 이유가 약하다. 소셜 로그인은 가입을 빠르게 할 뿐 **앱으로 할 수 있는 일을 늘리지 못한다.**

**출시 병목은 기능이 아니라 테스터다.** 참여 테스터가 3명/12명이라 14일 시계가 아직 시작도 안 했다. 바퀴를 돌리는 것과 테스터를 모으는 것은 나란히 갈 수 있으니, 테스터 모으기를 바퀴 뒤로 미루지 않는다.

## 2. 범위

**넣는 것**

```
등록    홈의 떠 있는 「+ 상품 등록」 → 등록 화면 → 사진·정보 → 올리기
수정    마이 목록 ⋮ · 상세 ⋮ → 「수정하기」 → 값이 채워진 같은 폼
삭제    마이 목록 ⋮ · 상세 ⋮ → 「삭제」 → 확인 창
웹      상세 단추 줄 정리 · shared 목록으로 갈아타기
```

**빼는 것과 이유**

| 뺀 것 | 왜 |
|---|---|
| 판매 요청(REQUEST) 등록 | 이번은 판매 상품만. 다른 점이 둘뿐이라(`price`→`desiredPrice`, `productStatus` 없음) 나중에 쉽게 붙는다 |
| 커뮤니티 글쓰기 | 다음 바퀴. 이번에 뚫는 사진 길을 그대로 쓴다 |
| 사진 끌어서 순서 바꾸기 | 눌러서 「대표로」 지정으로 갈음한다. 순서가 하는 일은 사실상 **대표 정하기** 하나다 |
| 임시저장 | 웹도 상품에는 없다(커뮤니티에만 있다). 상품은 대개 고르는 값이라 잃는 것이 작다. **Task 14에서 폼을 잃는 일을 겪으면 바로 다음에 넣는다** |
| 사진 쓸어내기 | 아래 §8 참고 — 프론트가 「지워 줘」를 부르는 방식은 앱이 죽으면 못 부른다. 서버가 주기적으로 쓸어내는 것이 맞고, 급하지 않다 |

> **웹을 건드리는 범위**: 원래는 「웹과 맞춰 두고 나중에」였는데, 논의 끝에 **웹 상세의 단추 줄도 이번에 고치기로** 했다(§4-4). 앱에만 넣으면 또 갈라지기 때문이다. 그리고 `shared` 목록으로 갈아타면서 웹 `constants.ts`도 손댄다.

## 3. 서버가 주는 것 (코드로 확인함)

`~/Desktop/cmarket_api`의 컨트롤러·DTO·서비스를 직접 열어 확인했다.

```
사진 올리기   POST   /api/images                 multipart · 필드 이름 files · 로그인 필요
상품 등록     POST   /api/products               JSON · 사진은 URL 문자열
상품 수정     PATCH  /api/products/{id}          JSON · ⚠️ 전체 교체
상품 삭제     DELETE /api/products/{id}
거래상태 변경  PATCH  /api/products/{id}/trade-status   { tradeStatus } 하나만
```

### 3-1. 반드시 알아야 할 서버 사실 넷

**① 사진 용량 한계가 두 겹이고 서로 안 맞는다**

```
서버 코드     ImageUploadService.java
              MAX_FILE_SIZE  = 5MB      한 장
              MAX_TOTAL_SIZE = 25MB     전체
              MAX_FILE_COUNT = 5        장수

서버 설정     application-prod.properties
              spring.servlet.multipart.max-file-size=5MB
              spring.servlet.multipart.max-request-size=5MB   ← 요청 전체
```

**설정이 코드보다 먼저 돈다.** Spring이 요청을 받아 읽는 단계에서 5MB를 넘으면 컨트롤러에 닿기도 전에 413으로 자른다. 그래서 **코드의 「전체 25MB」 검사는 한 번도 못 돈다.**

둘 중 하나가 잘못 적힌 것으로 보이지만 우리가 손댈 일은 아니다. 앱은 **가장 빡빡한 값(요청당 5MB)**을 지킨다. 사진을 한 장씩 보내면 한 장이 50~200KB라 근처에도 안 간다.

**② 수정은 `PATCH`지만 실제로는 전체 교체**

`ProductUpdateRequest`의 필수 항목에 전부 `@NotNull`/`@NotBlank`가 붙어 있고, 서비스가 받은 값을 그대로 덮어쓴다(`ProductServiceImpl.java:235-247`).

```
가격 하나만 고쳐도  →  사진·제목·지역까지 전부 다시 보내야 한다
하나라도 빠지면     →  400이 나거나 그 값이 비워진다
```

**고치지 않기로 했다.** 우리 수정 화면이 어차피 값이 다 채워진 폼이라 전부 보내는 게 자연스럽고, 자주 바꾸는 「거래 상태」에는 이미 전용 주소가 따로 있다. 부분 수정으로 바꾸면 「안 보냈다」와 「비우고 싶다」를 구분할 수 없는 새 문제가 생긴다. 이름이 사실과 다른 건 맞지만(정직한 이름은 `PUT`), 바꾸면 웹·앱이 둘 다 깨지고 얻는 건 이름뿐이다.

**③ 남의 상품을 건드리면 403이 아니라 401**

```java
ProductServiceImpl:226   throw new AuthenticationFailedException("상품을 수정할 권한이 없습니다.")
                         → ErrorCode.AUTHENTICATION_FAILED = 401
                         → 실제 도착 문구: "이메일 또는 비밀번호가 일치하지 않습니다."
```

커뮤니티는 같은 상황에 403(`POST_ACCESS_DENIED`)을 준다. 상품만 401이고, 던질 때 넣은 문구는 `ErrorResponse`가 버린다(10바퀴 신고에서 겪은 것과 같은 구조).

**따로 처리하지 않는다.** 수정·삭제 단추는 내 상품에만 그리므로 UI를 따라가서는 닿을 길이 사실상 없다. 이미 지운 상품은 404로, 마이 목록은 내 것만 담는다. 닿지 않는 길에 특별한 문구를 만들면 영원히 안 도는 코드가 남는다.

> ⚠️ 다만 앱은 401을 만나면 토큰을 갱신하고 한 번 다시 보낸다. **하필 그때 갱신이 실패하면 로그아웃된다.** 두 가지가 겹쳐야 하는 아주 드문 경우라 지금 손대지 않는다. 401 관련해서 이상한 일이 생기면 여기를 먼저 본다.

**④ `TradeStatus`에 `BUYING`이 없다**

`ProductController`의 주석에는 "판매 요청: BUYING → RESERVED → COMPLETED"라고 적혀 있지만, enum에는 `SELLING`·`RESERVED`·`COMPLETED` 셋뿐이고 `BUYING`은 주석 처리돼 있다. 보내면 역직렬화가 실패한다.

## 4. 화면 설계

### 4-1. 앱 화면 둘 + 확인 창 하나

```
등록    app/products/new.tsx          루트 스택 (탭바 없음)
        홈의 떠 있는 「+ 상품 등록」 → 여기
        끝내고 나가는 화면이다 — 신고·댓글 스레드와 같은 판단

수정    app/products/[id]/edit.tsx    루트 스택
        등록과 **같은 폼 조각**을 쓰고 값만 채워 들어간다

삭제    화면이 아니라 확인 창
        문구는 웹 그대로 — 「상품 삭제 / 정말로 이 상품을 삭제하시겠습니까?」
```

**등록과 수정이 폼을 나눠 쓰는 이유**는 서버가 전체 교체를 요구해서다. 두 화면이 보내는 모양이 어차피 같은데 따로 만들면 한쪽만 고쳐지는 자리가 생긴다.

### 4-2. 등록 화면에 들어가는 것

웹 `ProductPostForm`의 차례를 그대로 따른다(`ImageUploadField` → `BasicInfoSection` → `PriceAndStatusSection` → `TradeInfoSection`).

```
사진        최대 5장 · 첫 장이 대표          ImageUploadField
제목        2~50자                        BasicInfoSection
펫 종류      종류 → 세부 종류                 PetTypeField (한 쌍으로 묶여 있다)
카테고리     고르기
가격        숫자 · 원                      PriceAndStatusSection
상품 상태    고르기
설명        최대 1,000자 (선택)
거래 지역    시도 → 구군                    TradeInfoSection
```

**펫 종류는 두 값이 묶여 있다.** 웹 `PETS`가 종류 안에 세부 종류를 품는 구조라(`constants.ts:23-`), 종류를 고르면 세부 종류가 그 안의 것으로 좁혀진다. 웹도 `PetTypeField`가 `petType`·`petDetailType`을 한 쌍으로 다룬다(`BasicInfoSection.tsx:35-39`). **종류를 바꾸면 세부 종류를 비워야 한다** — 안 그러면 「조류」인데 세부가 「강아지」인 조합이 서버로 간다.

**거래 지역은 앱에 이미 있는 조각을 그대로 쓴다** — 가입 화면의 `address-field.tsx`가 시도/구군을 하단 시트로 고르게 한다.

### 4-3. 사진 흐름 — 이번 바퀴의 알맹이

```
1  「+」를 누른다        expo-image-picker로 사진첩을 연다 (여러 장 고르기 켬)
2  여러 장 고른다        이미 있는 것과 합쳐 최대 5장
3  줄인다               expo-image-manipulator — 가로 800px · webp
                        웹과 같은 값. 폰 사진 4MB → 50~200KB
4  **한 장씩** 올린다    POST /api/images · multipart · 필드 이름 files
                        올라간 것부터 미리보기에 붙는다
5  폼에는 주소만 남는다   mainImageUrl(첫 장) · subImageUrls(나머지)
```

**고르기는 여러 장, 보내기는 한 장씩이다.** 사용자는 이 차이를 볼 수 없다 — 어느 쪽이든 사진첩에서 여러 장을 골라 「완료」를 누른다. 다른 건 앱이 뒤에서 하는 일뿐이다.

**왜 한 장씩인가** — 용량 때문이 아니라 **폰은 전파가 자주 끊기기 때문**이다.

```
                    한꺼번에              한 장씩
전파 끊김           5장 전부 다시          그 한 장만 다시
한 장이 이상함       5장 전부 실패          그 한 장만 실패
기다리는 동안        아무것도 안 보임        올라간 것부터 보임
```

지하철·엘리베이터·건물 안에서 흔한 일이고, 그때 5장을 다시 고르게 만드느냐 한 장만 다시 누르게 하느냐의 차이다. (줄인 사진 다섯 장을 합쳐도 250KB~1MB라 5MB 한계에 걸릴 일은 드물다 — 용량은 부차적인 이유다.)

**대표 고르기**는 사진을 눌러 「대표로」 지정한다. 누른 사진이 맨 앞으로 올라가고 맨 앞이 곧 `mainImageUrl`이다. 웹은 끌어서 순서를 바꾸지만, 순서가 하는 일이 사실상 대표 정하기 하나라 앱은 누르기로 갈음한다.

### 4-4. 수정·삭제로 들어가는 길

**세 화면이 같은 일을 하되 폭에 맞게 모양만 다르다.**

```
앱          상세 ⋮ → 하단 시트(수정하기 · 삭제)
웹 모바일    상세 ⋮ → 하단 시트(수정하기 · 삭제)     앱과 같은 모양
웹 데스크톱   [수정][삭제]              [♡]
마이 목록    지금 ⋮ 에 상태 변경만 있다 → 수정하기·삭제를 더한다
```

**웹 상세를 이번에 고치는 이유**는 지금 배치가 어긋나 있어서다.

```
지금  상품 상세    「수정하기」 있음 · 삭제 없음      ← 왜 하나만?
      마이 목록    수정·삭제 둘 다
```

내 상품을 보다가 지우려면 마이 → 판매내역 → 찾기 → ⋮ → 삭제로 돌아가야 한다. 앱에만 넣으면 또 갈라지므로 **웹도 같이 고친다.**

「너무 쉽게 지워지는 것 아닌가」의 브레이크는 **확인 창**이 잡는다 — 상품 사진과 이름을 보여주고 「⚠️ 삭제된 상품은 복구할 수 없습니다」를 띄운다. 길을 멀게 만드는 것보다 확실하다.

데스크톱에서 **삭제는 붉은 계열로 갈라 둔다.** 나란히 있으면 잘못 누르기 쉽다.

**찜 단추는 내 상품에도 그대로 둔다.** 찜 수가 목록에 보이므로 자기 상품을 찜해 숫자를 올리는 것이 홍보로 쓰인다 — 의도된 동작이다.

### 4-5. 오류를 어떻게 다루나

```
사진 한 장 실패        그 자리에만 「다시」 · 나머지는 그대로
                      문구는 웹 그대로 — 「이미지 업로드에 실패했습니다. 다시 시도해주세요.」
입력값이 틀림          그 칸 아래 빨간 글씨 (웹 문구 그대로) · 보내기 전에 앱에서 먼저 거른다
등록·수정·삭제 실패     토스트 (9바퀴에 실패도 토스트로 통일했다)
                      삭제는 확인 창을 닫는다 — 실패해도 창이 남으면 갇힌다
```

**성공하면**

```
등록  →  만든 상품 상세로
수정  →  뒤로 (상세가 새로 받는다)
삭제  →  목록에 그대로 머묾 + 「상품을 삭제했습니다」
```

> ⚠️ 웹에는 등록 성공 뒤 **2초 기다리는 코드**가 있다. 사진 크기 변환(Lambda)이 끝나길 기다리는 것이다. 앱에서도 같은 문제가 생기는지는 실기기에서 봐야 안다. **일단 안 넣고**, 상세에서 사진이 안 뜨면 그때 넣는다.

## 5. `apiFetch`에 사진 길 내기

지금 앱의 `apiFetch`는 본문이 **늘 JSON이라고 못 박혀** 있다.

```ts
// mobile/lib/auth/api.ts:82-85
const headers: Record<string, string> = {
  'Content-Type': 'application/json',   // 이 자리를 비울 방법이 없다
  ...((init.headers as Record<string, string> | undefined) ?? {}),
};
```

사진은 multipart로 보내야 하는데, 그때는 `Content-Type`을 **우리가 정하면 안 된다.** 런타임이 경계 문자열(boundary)을 붙여 스스로 정해야 한다.

**본문을 보고 스스로 판단하게 한다.**

```ts
const isForm = init.body instanceof FormData;
const headers: Record<string, string> = {
  ...(isForm ? {} : { 'Content-Type': 'application/json' }),
  ...((init.headers as Record<string, string> | undefined) ?? {}),
};
```

**부르는 쪽은 아무것도 안 바뀐다.** JSON을 보내던 곳들은 `isForm`이 거짓이라 예전과 똑같이 돌고, 사진을 보낼 때만 그 줄이 빠진다. 그리고 **토큰 갱신·재시도가 사진에도 그대로 붙는다** — 전용 함수를 따로 만들었으면 그 로직을 또 짜야 했다.

**따로 만들지 않는 이유**: 2026-08-02에 「같은 규칙을 두 곳에 두면 두 곳 다 틀린다」를 두 번 겪었다(답글 깊이 규칙·알림 시각 표기). 인증을 맡은 자리가 이미 하나 있으니 거기에 둔다.

> 34번째 줄에도 같은 문구가 있지만 그건 **토큰 갱신 전용**이라 늘 JSON이 맞다. 건드리지 않는다.

## 7. 테스트

10바퀴에서 **게이트 371개가 전부 초록인데 실기기에서 7건이 나왔다.** 처음부터 갈라 둔다.

**시험이 잡는 것 (순수 로직)**

```
product-form.ts     필수 값 빠짐 · 제목 2~50자 · 가격 0 이상 · 사진 5장 넘음
product-images.ts   대표 고르기 · 한 장 실패해도 나머지 살아남기 · 순서
product-menu.ts     내 상품에만 수정·삭제가 뜨는가 (게스트에게 안 뜨는가)
auth/api.ts         FormData면 Content-Type을 안 붙이는가     ← 이번 바퀴의 핵심
shared 목록         웹·앱이 같은 값을 쓰는가
```

`apiFetch`의 FormData 분기에 **반드시** 시험을 붙인다. 깨지면 사진이 조용히 안 올라가고 원인을 찾기 아주 어렵다.

**실기기로만 잡히는 것**

```
사진첩이 열리는가 · 권한을 물어보는가 · 거절하면 어떻게 되는가
줄인 사진이 알아볼 만한가 (800px가 충분한가)
올리는 동안 화면이 멈추지 않는가
키보드가 입력칸을 가리지 않는가              ← 10바퀴에서 겪은 자리
등록 뒤 상세에서 사진이 바로 뜨는가           ← 웹이 2초 기다리는 그 문제
```

**러너**: `packages/shared`는 vitest, `mobile/`은 Jest, 웹 `src/`는 vitest.

## 8. 미리 짚는 함정

| 함정 | 왜 위험한가 | 어떻게 |
|---|---|---|
| `apiFetch`의 `Content-Type` | 안 고치면 사진이 **조용히** 안 올라간다 | §5. 시험으로 못 박는다 |
| 수정이 전체 교체 | 한 필드만 보내면 나머지가 날아간다 | 폼에 다 채우고 다 보낸다. 「가격만 바꿔도 나머지가 남는가」를 완료 기준에 넣는다 |
| 요청 전체 5MB | 코드의 25MB를 믿으면 틀린다 | 한 장씩 보낸다 |
| 사진 응답의 `subImageUrls` | 한 장만 올리면 **null**이다 | `?? []`로 받는다 |
| `TradeStatus.BUYING` | 주석에는 있는데 enum에는 없다 | 보내지 않는다 |
| 버려진 사진 | 등록을 그만두면 서버에 남는다. **지우는 API가 없다** | 이번엔 그대로 둔다(웹도 같다). 별도 이슈 — **서버가 주기적으로 쓸어내는** 방식으로. 프론트가 「지워 줘」를 부르는 방식은 앱이 죽거나 전파가 끊기면 못 불러서 **만들어 놓고도 여전히 남는다** |
| iOS HEIC 사진 | 서버 허용 목록에 없다 | 줄일 때 webp로 바꾸므로 자동으로 풀린다. 실기기에서 확인 |

## 9. 완료 기준

**앱**

```
□ 홈에 「+ 상품 등록」이 뜬다 (게스트에겐 안 뜬다)
□ 사진첩에서 여러 장을 한 번에 고를 수 있다
□ 고른 사진이 하나씩 미리보기에 붙는다
□ 사진 하나가 실패해도 나머지는 남고 그 자리만 다시 할 수 있다
□ 사진을 눌러 「대표로」 지정하면 맨 앞으로 온다
□ 사진을 뺄 수 있다 · 5장이 차면 「+」가 사라진다
□ 필수 값을 안 채우고 올리면 그 칸 아래 빨간 글씨가 뜬다
□ 등록하면 만든 상품 상세로 가고 사진·정보가 다 보인다
□ 마이 목록 ⋮ 에 「수정하기」·「삭제」가 있다
□ 상세 ⋮ 에도 있다 (내 상품일 때만)
□ 수정 화면에 기존 값이 다 채워져 있다 (사진 포함)
□ 가격만 바꿔 저장해도 나머지가 안 날아간다          ← 전체 교체 함정
□ 삭제 → 확인 창 → 목록에 머물고 토스트가 뜬다
□ 게스트가 「+」를 못 보고, 남의 상품 ⋮ 엔 신고·차단만 있다
□ 키보드가 입력칸을 안 가린다 (상세·등록·수정 모두)
```

**웹**

```
□ 데스크톱 상세에 [수정][삭제]  [♡] · 삭제가 붉은 계열로 갈라져 있다
□ 모바일 폭 상세에 ⋮ → 시트(수정하기 · 삭제)
□ 카테고리·펫 종류 목록이 shared 값으로 바뀌고 화면이 그대로다
```

**게이트**

```
□ shared vitest
□ 앱 tsc · lint · jest
□ 웹 tsc · lint · vitest · build
```

## 11. 실기기 확인 결과 (2026-08-03)

갤럭시 + Expo Go로 §9의 완료 기준을 훑었다. **기능은 다 돌았고, 드러난 것은 전부 눈으로만

### 고친 것 아홉

```
① 필수 별표(*)가 앱에만 없었다          웹은 RequiredLabel이 붙여 준다. 앱엔 대응물이 없었다
② 「상품 사진」만 글자가 컸다            새로 만든 칸이라 그 자리에서 값을 정했다.
                                       웹은 같은 증상을 이미 고쳐 뒀다
③ 이름표가 흐렸다(13px 회색)            로그인 화면에서 물려받은 값. 칸 여덟 줄 폼에선
                                       뼈대가 안 잡혀 14px 굵은 진한 글씨로
④ 입력칸 테두리가 흐렸다                #E5E7EB → #D1D5DB · hairline(0.5px) → 1

                                       아이콘을 빠뜨렸다

⑦ 등록하기가 조용히 막혔다               막힌 칸이 화면 밖이면 아무 일도 안 일어난 것처럼 보였다
⑧ 화면만 옮기고 커서를 안 옮겼다          ⑦을 고친 뒤 나온 것. 아래 참고
⑨ 칸 아래 문구·「대표」 뱃지가 작았다      12 → 13px
```

### ⑧이 이번 확인의 알맹이다

```
가격 칸에 커서를 둔 채 등록하기 → 화면은 상품명으로 갔는데
                              커서와 숫자 자판은 가격에 남았다
                              → 거기서 친 숫자가 **가격에 붙는다**
```

화면을 옮기는 것만으로는 모자라다. 치는 칸이면 커서까지 옮기고(자판도 그 칸에 맞게 바뀐다),
고르는 칸이면 자판을 내린다. **오류 없이 값만 잘못 들어가는 종류라 시험으로는 안 잡힌다.**

### 흐름을 바꾼 것 둘

```

                (목록엔 가격·제목만 보인다). 웹도 상세로 간다
판매내역 단추     「+ 상품 등록」이 6바퀴부터 흐린 채였다. 이제 눌린다
```
