## ⚠️ 계획서와 달라진 것 — 여기부터 읽는다

### 1. 반응형을 안 쓴다. 높이는 고정값이다

계획서는 「모바일 48 / 데스크탑 40」이었다. **실기기에서 되돌렸다** —
모바일 48이 입력칸(40)보다 커서 어색했다.

```
지금 값 (폭에 상관없이 고정)
  Button sm   36
  Button md   40      ← 입력칸과 같은 값
  Button lg   48
  입력칸       40      Input.tsx 의 h-10
```

⚠️ **다시 반응형으로 바꾸지 말 것.** 사용자가 눈으로 보고 정한 값이다.

### 2. `h-*` 도입 자체가 「padding 으로 작게 만든 곳」을 되돌린다

**앞 세션이 이걸 몰라 네 번 잘못 세었다.** 가장 중요한 교훈이다.

```
전   size 의 py-2 를 className 의 py-1 이 덮어씀 → 26px
후   size 의 h-9 는 padding 으로 못 덮음        → 36px
```

즉 **명목 높이(36→36)만 보면 「안 바뀐다」로 보이지만 실제로는 커진다.**
`tailwind-merge` 는 `h-*` 와 `padding` 을 다른 그룹으로 보기 때문이다.

⚠️ **판단은 코드가 아니라 DOM 으로 한다.** 배포본과 로컬의 같은 요소를 개발자도구에서
견주면 바로 보인다. 사용자가 이 방법으로 두 번 잡아 줬다.

### 3. 그래서 칩들은 높이를 따로 못 박았다

```
소분류 칩 (강아지·고양이…)      h-[26px]    PetTypeFilter.tsx:76
「더보기」                      h-[26px]    PetTypeFilter.tsx:93
대분류 탭 (전체·포유류…)         h-auto      ProductPetTypeTabs.tsx:54
                                          밑줄(border-b-2)이 붙어 padding 이 정해야 한다
전체/판매/판매요청 칩            h-8 / h-7   Tabs.tsx 의 card-pill
```

**칩은 단추가 아니다.** 목록 위에 여럿이 늘어서는 것이라 단추만 한 크기면 화면을 잡아먹는다.
사용자가 「배포본 크기가 좋다」고 두 번 말했다.

### 4. 과제 7(넓게 퍼진 곳 훑기)은 거의 없어졌다

높이를 고정값으로 두면서 `sm`·`md`·`lg` 를 쓰는 곳이 **원래 값 그대로**가 됐다.
남은 확인거리는 입력칸을 쓰는 11개 파일뿐이다.

## 남은 과제

### 과제 3 — 화면마다 덮어쓴 임시 조치 걷어내기

```
✅ LoginForm.tsx            이미 걷어냄 (49fb8b6e)
✅ SocialLoginButtons.tsx   이미 걷어냄 (49fb8b6e)
🔸 FindPasswordForm.tsx     wrapperClassName="h-12" 네 곳이 남았다
```

⚠️ `h-12`(48)를 지우면 입력칸이 40이 된다. **`wrapperClassName` 속성 자체는 남긴다** —
밖에서 높이를 줄 길은 있어도 된다. 쓰던 자리만 걷어낸다.

확인: `localhost:3000/auth/find-password` 에서 칸·단추 줄이 맞는지.

### 과제 4 — 입력칸 테두리 색을 하나로

```
지금 넘기는 값
  border-gray-400          11곳   로그인·가입·비밀번호찾기·프로필수정
  border-outline-variant    2곳   상품 등록 가격 · TitleField
  border-blue-100           1곳   프로필수정 비밀번호  ⚠️ 파랑이다. 뜻이 있는지 화면을 볼 것

⚠️ Input.tsx:23 의 기본값은 border-gray-100 이다. 너무 옅어서 화면마다 덮어쓰고 있었다 —
   이것이 색이 갈린 뿌리다.
```

바꿀 값: **`#D1D5DB`** — 앱과 같다(`mobile/constants/colors.ts` 의 `outline`).
웹 토큰에 이 값이 있는지 먼저 본다(`src/styles/tokens.colors.css`).

⚠️ WCAG 1.4.11(3:1)을 못 넘긴다(1.47:1). **알고 고르는 값이다** — 입력칸은 이름표와
안내글이 이미 「여기 쓰는 칸」임을 말해 주므로 테두리가 유일한 단서가 아니다.
앱이 19바퀴(#786)에 같은 판단을 했다.

### 과제 5 — 웹 주 단추 색을 앱과 맞추기

```
src/components/commons/button/buttonClass.ts:10
  bg-primary (#633F00)  →  bg-primary-600 (#825500)
```

⚠️ **`HomeHero.tsx:44` 를 함께 고쳐야 한다.** 평소 색이 `bg-[#825500]` 이고 hover 가
`hover:bg-primary`(#633F00)라, 이 과제로 둘이 같은 값이 되어 **hover 가 안 보이게 된다.**
hover 를 `hover:bg-primary-700` 으로 옮긴다.

`bg-primary` 를 쓰는 다른 곳(채팅 보내기·커뮤니티 글쓰기 둘)도 함께 본다.

### 과제 6 — 앱 주 단추 높이

```
mobile/app/profile-edit.tsx:468        height: 52 → 48
mobile/app/find-password.tsx:329       height: 44 → 48
```

⚠️ **창 안 단추(46)와 댓글 등록(40)은 손대지 않는다.** 자리가 다르면 크기도 다르다 —
창 안 단추를 화면 아래 단추만큼 키우면 작은 창이 답답해지고, 댓글 등록을 키우면 옆
입력칸보다 커진다. 사용자가 이렇게 정했다.

게이트: `pnpm gate:mobile` · 실기기로 「저장」·「다음」 확인.

## 이 사람과 일하는 법

**앞 세션이 같은 실수를 반복해 사용자를 지치게 했다. 되풀이하지 말 것.**

```
① 숫자를 말하기 전에 실물로 재라
   「43곳이 바뀐다」를 네 번 고쳤다(43 → 26 → 24 → 40 → 실은 3곳).
   코드만 읽고 tailwind-merge 결과를 추측하면 틀린다. DOM 을 본다.

② 화면·단추 이름은 코드를 열어 실제 값으로 적어라
   「/signup 의 가입하기」라고 했는데 실제로는 「/auth/signup 의 회원가입」이었다.
   앱 문구를 웹에 옮겨 적은 실수다. 두 번 지적받았다.

③ 매체를 뭉뚱그리지 마라
   데스크탑 웹 · 모바일 웹 · 모바일 앱은 화면도 진입점도 다르다.
   「상품 상세 → ⋮ → 신고하기」는 데스크탑 웹에 없다.
   확인을 요청할 때 어느 폭에서 무엇을 보는지 못 박아 적을 것.

④ 「무엇을 확인하는지」를 먼저 말하라
   어디를 보라는 말만 하고 무엇을 보라는 말을 빼서 사용자가 헷갈렸다.
   아직 코드를 안 바꿨는데 「미리 보라」고 한 적도 있다.

⑤ 되묻기보다 근거를 대고 판단하라
   색을 정할 때 여덟 번 물어봐서 사용자가 「왔다갔다 지친다」고 했다.
   수치와 실물 증거를 함께 내밀고 한 번에 정하는 편이 낫다.
```

**사용자는 눈으로 보고 판단하는 것이 정확하다.** 대비 수치·크기 계산이 기준을 넘겨도
「어색하다」고 하면 그쪽이 맞다 — 19바퀴(#786)에서 이미 배운 것이다.
