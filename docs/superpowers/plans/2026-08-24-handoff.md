## ⚠️⚠️ `tmux new-session -s claude 'claude'` 처럼 **명령을 붙여 켜지 마라**

2026-08-24 낮에 이것 때문에 tmux 가 통째로 죽었다. **`/exit` 을 한 번 쳤을 뿐인데** 맨
터미널로 튕겨 나왔고, 그 뒤로 판을 못 갈랐다. 문서에는 「tmux 는 그대로 살아 있다」고
적혀 있었는데 **그게 틀린 말이었다.**

```
명령을 붙여 켜면                    명령 없이 켜면
  세션 └ 창 └ 판 → claude            세션 └ 창 └ 판 → zsh → claude
                  ↑ 뒤가 비어 있다                   ↑ 셸이 받쳐 준다

  /exit → claude 끝                  /exit → claude 만 끝
       → 판에 남은 게 없음 → 창 닫힘        → zsh 가 남아 판이 유지된다
       → 창이 없음 → 세션 끝
       → 세션이 없음 → **서버 종료** 💀     → tmux 그대로 살아 있음 ✅
```

**명령을 붙이면 그 명령이 곧 판의 프로세스**라서, 그것이 끝나면 뒤에 남는 것이 없다.
창이 하나뿐이면 세션이 끝나고, 세션이 하나뿐이면 **서버까지 함께 죽는다.**

같은 상황을 다른 소켓(`-L probe`)에 만들어 직접 갈랐다.

```
withcmd    명령('cat')을 붙여 켠 것   → 그 프로세스를 끝내니 세션이 사라졌다
withshell  명령 없이 켠 것            → 그대로 남았다
그리고 그것이 마지막 세션이면 → tmux ls 가 「no server running」
```

# §2. ⭐⭐ 오늘 가장 큰 배움 — **「고쳤는데 안 바뀐다」는 단서다**

세 번 통했다. 셋 다 **내가 넣은 것이 정말 들어갔는지 확인한 뒤**, 들어갔는데도 그대로라서 방향을 틀었다.

| 무엇 | 내 추측 | 확인한 것 | 진짜 원인 |
|---|---|---|---|
| 아이콘이 64×80 | flex 가 눌렀다 → `shrink-0` | `flexShrink: 0` **이 들어갔는데도** 64×80 | 테일윈드의 `max-width: 100%` |
| 프로필 카드가 안 붙음 | `sticky` 를 붙이면 된다 | 붙였는데 안 먹음 | `<aside>` 의 `h-fit` → 미끄러질 여백 0 |
| jest 가 안 끝남 | 두 파일만 고치면 된다 | 고쳤는데 **게이트 경고 그대로** | 같은 문제 파일이 셋 더 있었다 |

## 왜 그런가 — CSS 크기는 **단계**가 있다

```
① 지정한 값      width: 80px       ← w-20
② max 로 깎기    max-width: 100%   ← 부모가 64 → 80을 64로 깎는다   ★ 여기서 졌다
③ min 으로 밀기  min-width/height  ← 최종 승자

flex 의 shrink 는 ① 단계 이야기(줄이 모자랄 때 줄일까 말까)
max-width 는 ② 단계 — **단계가 다르니 shrink 로는 절대 못 막는다**
```

세로가 80 그대로였던 것도 여기서 설명된다. `max-height` 는 안 걸려 있으니까.
**한 쪽만 깎여서** Next 가 「가로세로 중 하나만 바뀌었다」 경고를 띄웠다.

같은 뿌리의 사건이 어제 둘 더 있었다.

```
min-h-screen 을 안 지웠으면   h-[calc(...)] 로 높이를 정해도 min-height 가 이겨(③단계)
                             페이지가 그대로 길어진다
min-h-0 을 안 넣으면          flex 자식은 min-height: auto 가 기본이라 내용보다 못 줄어든다
                             → 안쪽에 overflow-y-auto 를 줘도 스크롤이 안 생긴다
```

**⚠️ 그래서 이렇게 한다:** "분명 고쳤는데 화면이 그대로"일 때 **두 번 시도하기 전에**
「내가 넣은 것이 정말 들어갔나」부터 본다. 들어갔는데도 그대로면 **원인이 딴 데 있다.**
크기 문제는 `min-*`/`max-*` 를 먼저 의심한다.

# §4. ⭐ 적어 두는 것과 따르게 하는 것은 다른 일이다

jest 매달림의 함정은 **`mobile/AGENTS.md` 44줄에 이미 적혀 있었다.** 증상·원인·고치는 법에

```
문서   처음 들어올 때 한 번 읽는다        → 그 뒤로는 안 본다
코드   시험 파일을 새로 만들 때마다 쓴다   → 그 순간에 문서를 다시 열 이유가 없다
```

규칙이 **글로만** 있으면 어기는 순간에 아무도 막지 않는다.

```
사다리 — 위로 갈수록 세다
  ① 문서에 적는다                    ← 여기 있었다. 다섯 파일이 그냥 지나갔다
  ② 리뷰에서 본다                     사람이 매번 기억해야 한다
  ③ 게이트가 막는다                   경고 0건을 잠근다
  ④ 함정을 만들 수가 없게 한다  ★      시험용 QueryClient 만드는 함수 하나를 두고
                                     새로 만드는 길을 아예 없앤다
```

**이 저장소는 CSS 에서는 이미 답을 알고 있다** — `constants/ui.ts` 가 그 증거다.
「`px-*` 를 손으로 적지 말고 이것을 써라」, z 값도 숫자 대신 `Z_INDEX` 상수.
**손으로 적을 기회 자체를 없앤 것**이다. 시험 설정만 아직 그 단계에 안 왔다.

# §8. ⭐⭐ 오늘 낮~저녁 가장 값어치 있던 것 — 「재보니 달랐다」가 네 번

넷 다 **코드만 읽었으면 놓쳤을 것**이고, 실제 브라우저로 찍어 견줘서야 갈렸다. 초점 표시(포커스
링, Tab 으로 옮겨 온 자리를 알려주는 테두리)를 손보다가 나왔다.

## ① `overflow: hidden` 은 outline 도 box-shadow 도 **둘 다 자른다**

「outline 대신 ring(box-shadow 로 그리는 테두리)으로 바꾸면 해결된다」는 전제가 틀렸다. outline·
box-shadow·border 셋을 직접 찍어 견주고서야 알았다. 자르는 것은 **자식**뿐이다 — 부모 자신에게
주거나 `border` 를 쓰면 안 잘린다.

## ② `box-shadow: none` 으로 전역을 끄면 **그 자리의 자기 ring 까지 같이 꺼진다**

같은 속성이라서다. 커뮤니티 검색창이 (원래 있던 자기 ring 대신) 브라우저 기본 파란 테두리로
변한 걸 보고 알았다. → `:not()` 으로 처음부터 대상에서 빼는 방식으로 바꿨다.

## ③ `disabled` 가 붙는 순간 **브라우저가 초점을 강제로 뗀다**

건너뛰기 링크를 눌러도 아무 일이 없던 진짜 원인이다. 크롬 실측:

```
엔터 직후    초점 = 단추
60ms 뒤     초점이 body 로 강제 이동(disabled 가 붙어서)
520ms 뒤    disabled 는 풀리지만 초점은 안 돌아온다
```

→ `disabled` 대신 `aria-disabled` + `onClick` 가드로 바꿨다.

⚠️ **jsdom 은 이 반응을 안 한다** — 이미 `disabled` 인 요소에 초점을 못 주는 것까지만 흉내 내고,
「붙는 순간 강제로 뗀다」는 안 흉내 낸다. 그래서 「초점이 남아 있나」로 시험을 쓰면 **회귀를 심어도
통과한다** — 실제로 `disabled` 로 되돌려 재현해 보니 그 시험은 그대로 초록이었다. **「결과(초점
위치)」가 아니라 「원인(disabled 속성이 안 붙는다)」을 직접 보는 시험**만 회귀를 잡았다
(`LoadMoreFocusButton.test.tsx` 가 그 예다). 이 함정은 `CLAUDE.md` 의 「웹 시험(jsdom)이 못 보는
것」 표에도 새로 추가했다.

## ④ 초점 표시가 **덧쌓여** 두꺼워 보였다

`border` 1px + `ring` 2px 이 겹쳐 3px 처럼 보였다. 사용자가 「두껍다」고 짚어 줘서 알았다. →
전역 규칙을 `border: 1.2px solid` 하나로 통일했다(`src/app/globals.css:139~141`,
`:focus-visible:not(.focus-ring-custom)`). 자기 자리를 그대로 쓰니 덧쌓이지 않는다.

# §10. ⭐ 자동 리뷰가 못 보는 것 — **PR 하나만 본다**

오늘 PR 여섯을 올렸고 kimi 가 **여섯 다 「특이사항 없음」** 이라고 했다. 그런데 **실제로는 충돌이
있었다.** 사용자가 다섯을 머지하자 마지막 하나가 바로 부딪혔다.

```
#1062(초점)  가 항목에 넣은  focus-visible:bg-gray-100
#1064(드롭다운) 이 항목을    tabIndex={-1} 로 바꿨다 → **초점을 아예 안 받는다**
                            → 그 클래스가 **죽은 코드**가 된다
```

**왜 자동 리뷰가 못 잡았나 — 구조 때문이다.**

```
kimi 는 PR 하나의 diff 만 본다 (base 대비로 계산된다)
  → focus-visible:bg-gray-100 은 #1062 쪽에 있고 #1064 의 diff 안에는 없다
  → **두 브랜치를 겹쳐야** 보이는 어긋남이라 각각을 아무리 잘 봐도 안 보인다
```

⚠️ **그래서 이렇게 한다:** 브랜치를 여럿 올렸으면 **확인용 브랜치에 미리 다 합쳐 본다.**
오늘 그렇게 했더니 사용자가 머지하기 전에 이 충돌을 먼저 만났고, **답이 같았다** —
실제 머지에서 푼 것과 똑같은 해결이었다.

```bash
git checkout -b preview/<날짜>-all develop
for b in <브랜치들>; do git merge --no-edit "$b"; done
pnpm gate        # 합친 결과가 통과하는지까지 본다
```

⚠️ 그리고 **확인용 브랜치는 사용자가 눈으로 볼 때도 쓸모가 있다.** 이슈별로 갈라 놓으면
한 브랜치에는 그 이슈 것만 있어서, 사용자가 「아까 고친 게 왜 안 보이냐」고 묻게 된다 —
오늘 실제로 그랬다. 합친 브랜치에서 보여 주면 그 혼란이 없다.

# §11. ⭐ 자동 리뷰가 헷갈리면 **사람도 헷갈린다** — 답이 주석일 때가 있다

#1070 에서 kimi 가 「`Escape` 처리가 누락된 것 같다」고 했다. **오탐이었다** — ESC 는 새로 넣은
`handleKeyDown` 이 아니라 **원래 있던 document 리스너**가 잡고, 크롬으로 재서 작동도 확인했다.

그냥 넘길 수도 있었지만 이렇게 봤다.

> **자동 리뷰가 헷갈렸다면 다음에 이 코드를 볼 사람도 같은 자리에서 헷갈린다.**
> 한 컴포넌트에 키 처리가 **두 군데**로 나뉘어 있는 것이 원인이다.

그래서 **코드는 한 글자도 안 고치고 주석 3줄만** 더했다. 그랬더니 —

```
10:34:30   「Escape 처리가 누락된 것 같습니다」            ← 오탐
   ↓  주석 3줄 (코드 변경 0)
10:42:11   「Escape 가 document 리스너에서 처리 ✓」        ← 정확히 짚었다
           「병합 권장」
```

**주석이 자동 리뷰의 판정을 바꿨다.** 사람에게 쓸모 있는 주석은 기계에도 쓸모가 있다.

⚠️ 다만 **재귀는 끊어야 한다.** 그다음 리뷰가 「주석에 kimi 리뷰를 언급한 게 혼란스럽다」고
또 짚었는데, 그건 접었다 — 자동 리뷰가 자기 자신을 언급한 주석을 다시 지적하는 것까지
따라가면 끝이 없다.

## 잘 된 것 — **판이 스스로 접었다**

`kimiReview` 에게 「다 고치지 마라」를 못 박았더니 kimi 제안 넷을 **근거를 대고 접었다.**
그중 이 판단이 특히 좋았다.

> `단추가없는폭이다` → `isMdOrAbove` 로 바꾸라는 제안을 접었다.
> **「그 변수는 일반적인 breakpoint 판정이 아니라 『단추가 숨는 폭과 정확히 같아야 한다』는
> 의도적 결합이다. 이름을 일반화하면 그 뜻이 오히려 흐려진다.」**

주석을 읽고 **의도까지 읽은 것**이다. 이름 취향으로 보지 않았다.

## ⚠️ 판을 쓸 때 지킨 것

```
git checkout 금지     같은 작업 트리를 쓰므로 판이 브랜치를 바꾸면 리드 작업이 날아간다
커밋·푸시 금지        리드가 브랜치별로 갈라 담는다
게이트·빌드 금지      같은 트리에서 둘이 빌드하면 .next 를 놓고 다툰다
                     (판이 고친 파일의 시험·lint 만 좁혀 돌리는 것은 허용했다)
prettier 금지        관계없는 줄까지 다시 접힌다
pnpm install 금지    오늘 node_modules 가 통째로 빈 사고가 있었다
```

⚠️ **판이 idle 알림을 보내도 「끝났다」가 아니다.** 오늘도 그랬다 — 보고를 한 번 더 청해야
왔고, 어떤 판은 두 번 청했다. **작업 트리(`git status`)로 확인하는 것이 가장 확실하다.**
