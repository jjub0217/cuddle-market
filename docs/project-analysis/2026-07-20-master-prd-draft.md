## 4. 확인된 현재 동작

### 3.1 진입 및 탐색

- 메인 진입 화면은 `/` 홈이며, 상품 목록 중심 구조다.
- 홈에서는 필터, 반려동물 유형, 카테고리, 정렬을 바꿔 상품 목록을 탐색할 수 있다.
- 상품 상세는 `/products/[id]/[name]` 기준으로 동작한다.
- 커뮤니티는 질문/정보 탭 기반으로 탐색한다.
- 지도 화면은 별도 `/map` 경로에서 동작한다.

### 3.2 비로그인 접근

- 상품 목록과 상품 상세는 비로그인 상태에서 접근 가능한 것으로 기록되어 있다.
- 커뮤니티 목록/상세, 지도, 로그인/회원가입/비밀번호 찾기는 비로그인 접근 가능 영역으로 기록되어 있다.
- 사용자 프로필은 최종 문서 기준 로그인 필요 영역으로 정리되어 있다.
- 비로그인 사용자가 상품 상세에서 판매자 정보를 클릭하면 사용자 프로필로 바로 이동하지 않고 로그인 모달이 노출되는 정책이 반영되어 있다.

### 3.3 로그인 필요 동작

- 채팅 목록과 채팅방은 로그인 필요 영역으로 기록되어 있다.
- 마이페이지와 프로필 수정은 로그인 필요 영역으로 기록되어 있다.
- 알림은 로그인 필요 영역으로 기록되어 있다.
- 상품 등록/수정은 로그인 필요 영역으로 기록되어 있다.
- 커뮤니티 글 작성/수정은 로그인 필요 영역으로 기록되어 있다.
- 찜, 채팅 시작, 신고, 차단, 댓글 작성 같은 상호작용은 로그인 필요 동작으로 기록되어 있다.

### 3.4 인증 흐름

- 일반 로그인 성공 시 사용자 정보와 access/refresh token을 저장한다.
- 로그인 성공 후에는 저장된 `redirectUrl`이 있으면 해당 화면으로 복귀하고, 없으면 홈으로 이동하는 구조로 기록되어 있다.
- 소셜 로그인 후 필수 프로필 정보가 부족하면 추가 정보 입력 화면으로 이동한다.
- 인증 상태는 클라이언트에서 rehydrate된다.
- access token 만료 시 refresh token으로 재발급을 시도한다.

### 3.5 주요 사용자 화면

- 홈은 상품 탐색의 중심 화면이다.
- 상품 상세는 이미지, 설명, 찜, 채팅, 판매자 정보, 판매자 다른 상품을 포함한다.
- 커뮤니티는 목록, 상세, 댓글/답글, 글쓰기 흐름을 가진다.
- 채팅은 채팅방 목록, 메시지 로그, 이미지 전송, 채팅방 정보로 구성된다.
- 마이페이지는 대시보드, 판매/구매/찜/차단 목록을 포함한다.
- 프로필 수정은 기본 정보 수정, 비밀번호 변경, 회원탈퇴를 포함한다.
- 알림은 읽지 않음 카운트와 목록 화면을 가진다.
- 지도는 카테고리, 장소 목록, 상세 카드, 현재 지도에서 검색 기능을 가진다.

### 3.6 상태 관리 및 데이터 호출

- 사용자 인증 상태는 Zustand로 관리된다.
- 토스트, 로그인 모달, 지도 상태, 채팅 소켓 상태도 Zustand로 관리된다.
- 서버 데이터는 주로 TanStack Query로 관리된다.
- API 계층은 REST와 GraphQL이 혼합되어 있다.
- 일부 주요 화면은 서버 프리패치 후 클라이언트 hydration 방식으로 동작한다.

### 3.7 예외 처리 UI

- 로딩 상태는 스피너, 스켈레톤, 전용 로딩 상태 컴포넌트로 처리한다.
- 빈 상태는 `EmptyState` 계열 컴포넌트로 처리하는 화면이 있다.
- 오류 상태는 화면 내부 문구와 재시도/이동 버튼으로 처리하는 패턴이 다수다.
- 전역 토스트 컨테이너가 존재한다.
- 로그인 유도는 전역 로그인 모달과 로그인 페이지 이동이 혼용된다.

## 5. 현재 구조에서 해석상 주의할 점

- 전역 미들웨어 기반 인증 구조가 아니라, 여러 화면에서 개별적으로 로그인 여부를 검사하는 구조로 기록되어 있다.
- 라우트 자체 보호와 주요 진입 경로 보호가 항상 같지 않을 수 있다.
- 사용자 프로필처럼 코드만 보면 공개처럼 읽힐 수 있으나, 실제 주요 진입 경로에서는 로그인 모달로 막히는 사례가 이미 확인되었다.
- 따라서 앱/웹 공통 정책을 정의할 때는 `라우트 접근 가능 여부`와 `실제 사용자 진입 UX`를 구분해서 정리할 필요가 있다.

## 6. 앱 정책 결정안

### 5.1 정보 구조 및 최초 진입

- 앱 최초 진입 화면은 상품 목록 중심 홈으로 유지한다.
- 앱의 하단 탭 구조는 웹의 `BottomNav` 정보 구조를 기준으로 유지한다.
- 홈, 커뮤니티, 플레이스, 채팅, 마이페이지를 앱의 1차 네비게이션으로 동일 유지한다.

### 5.2 인증 및 복귀 정책

- 로그인 성공 후에는 이전 화면으로 복귀하는 정책을 유지한다.
- 로그인 유도 방식은 화면 이동 중심이 아니라 모달 중심으로 가져간다.
- 보호 화면 접근 시 앱에서도 `redirectUrl` 개념을 유지한다.
- 사용자 프로필은 앱에서도 로그인 필요 화면으로 유지한다.
- 사용자 프로필 접근 제어는 “주요 진입 경로 차단”이 아니라 “라우트 차단” 기준으로 통일한다.

### 5.3 오류/피드백 UX 정책

- 웹의 모달 오류를 앱에서 일괄적으로 인라인 오류로 바꾸지 않는다. 메시지 성격별로 다음과 같이 매핑한다.
  - 폼 검증, 섹션 실패, 화면 첫 로드 실패는 인라인 오류로 처리한다.
  - 일시적 액션 실패와 성공 피드백은 토스트/스낵바로 처리한다.
  - 삭제, 회원탈퇴 같은 파괴적 확인은 다이얼로그를 유지한다.
  - 신고, 차단, 로그인 유도 같은 선택/유도성 액션은 바텀시트로 처리한다.
  - 원칙적으로 센터 모달은 최소화하고 하단 도달 영역 중심으로 배치한다.
- 에러 표시는 모바일에서 다음 기준으로 분리한다.
  - 전체 화면 에러: 화면 핵심 콘텐츠의 첫 로드가 실패해 보여줄 내용이 없을 때 사용한다.
  - 인라인 에러: 실패가 특정 섹션이나 필드에 귀속될 때 사용한다.
  - 토스트/스낵바: 콘텐츠는 유지되고 액션 결과만 알려주면 될 때 사용한다.
  - 불변 규칙: 이미 렌더된 콘텐츠는 에러 상태로 덮지 않는다.
- 지도 오류는 현재처럼 조용히 유지하지 않고 명시적 오류 정책으로 전환한다.
  - 지도 SDK 로드 실패: 전체 화면 에러와 재시도를 제공하고, 로드 타임아웃을 도입한다.
  - 마커 데이터 첫 로드 실패: 인라인 배너/칩과 재시도를 제공한다.
  - 마커 데이터 재검색/패닝 실패: 토스트와 재시도를 제공하되 기존 마커는 유지한다.
  - 원칙적으로 지도는 지속 사용 화면이므로 데이터 실패만으로 화면 전체를 덮지 않는다.
  - 재시도 동작은 기존 “이 지역 재검색” 흐름을 재활용한다.

### 5.4 상품/커뮤니티/채팅 정책

- 상품 상세에서 판매자 프로필, 채팅 시작, 찜하기의 로그인 유도 방식은 통일한다.
- 커뮤니티 글쓰기, 댓글, 신고, 차단의 비로그인 유도 UX도 통일한다.
- 채팅 진입 시 로그인 화면으로 이동시키는 현재 정책을 앱에서도 유지한다.

### 5.5 사용자 프로필 및 마이페이지 정책

- 사용자 프로필은 읽기 전용 공개 화면으로 바꾸지 않고 지금처럼 로그인 필요 영역으로 유지한다.
- 마이페이지와 사용자 프로필의 역할은 다음과 같이 분리한다.
  - 마이페이지는 본인 계정과 거래 관리 전용 화면으로 사용한다.
  - 사용자 프로필은 타인 열람과 대인 액션 중심 화면으로 사용한다.
  - 중복되는 판매 목록은 마이페이지에서는 관리 관점, 사용자 프로필에서는 열람과 채팅 관점으로 구분한다.
  - `/user-profile/{본인}` 접근 시 마이페이지로 리다이렉트하거나 대인 액션을 숨기는 방향을 기준 정책으로 삼는다.
  - 차단은 마이페이지에서는 목록 관리, 사용자 프로필에서는 실행 액션으로 역할을 분리한다.
- 차단, 신고, 프로필 액션의 우선순위는 유지하되 노출 위치와 방식은 모바일에 맞게 조정한다.
  - 우선순위는 채팅 > 프로필 수정(내 프로필) > 차단/신고 순으로 둔다.
  - 채팅은 프로필 화면의 하단 sticky CTA로 승격한다.
  - 차단과 신고는 상단 우측 케밥 메뉴 뒤에 두고, 드롭다운 대신 바텀시트로 전환한다.
  - 프로필 수정은 내 프로필일 때 상단 액션으로 유지한다.
  - 원칙적으로 긍정적이고 빈번한 액션은 하단 엄지존, 부정적이고 희소한 액션은 상단 케밥 뒤에 둔다.

### 5.6 기술 구조 정책

- 앱은 웹의 REST/GraphQL 혼합 구조를 그대로 가져가지 않고 REST로 단일화한다.
  - 현재 GraphQL BFF는 Next.js 내부에 있어 앱이 재사용하면 웹 배포에 강결합된다.
  - 앱은 Spring Boot REST를 직접 호출하는 구조를 기본으로 한다.
  - 웹의 REST/GraphQL 혼합은 앱에 복제하지 않는다.
  - 향후 앱에서도 GraphQL의 이점이 필요하면 BFF를 Next.js에서 독립 서비스로 분리해 웹/앱 공용화하는 방향을 검토한다.
- 앱은 REST 단일 구조를 전제로 인증 실패 정책도 하나의 REST 기준으로 통일한다.
  - 중앙 axios interceptor 한 곳에서 401을 처리한다.
  - refresh 성공 시 재시도하고, 동시 401은 single-flight로 제어한다.
  - refresh 실패 시 secure-store의 토큰을 비우고 `/login?redirectUrl=현재경로`로 이동한다.
  - 웹의 `window.location` 하드 리다이렉트와 admin 분기는 앱에서 제거한다.
  - 사용자 액션 중 401이면 redirectUrl 복귀를 유지하고, 백그라운드 갱신은 가능한 범위에서 조용히 처리한다.
- 앱은 화면별 개별 인증 가드를 유지하지 않고 중앙집중 구조로 정리한다.
  - 보호 화면은 Expo Router의 `(protected)` 그룹에 모은다.
  - 그룹의 `_layout.tsx` 한 곳에서 인증을 검사한다.
  - 미인증 사용자는 `<Redirect href="/login?redirectUrl=...">`로 보낸다.
  - secure-store 토큰 로딩 중에는 스플래시나 스피너로 게이트해 깜빡임을 막는다.
  - 딥링크와 푸시 진입도 그룹 레이아웃을 반드시 통과하도록 설계한다.
  - 웹의 화면별 `useEffect` 인증 가드 패턴은 앱에 복제하지 않는다.

## 7. IA 요약

- 앱 최초 진입 화면은 상품 목록 중심 홈으로 유지한다.
- 앱의 1차 네비게이션은 `홈 / 커뮤니티 / 플레이스 / 채팅 / 마이` 5탭 구조로 유지한다.
- 인증 화면군은 하단 탭 바깥의 독립 흐름으로 둔다.
- 보호 화면은 Expo Router의 `(protected)` 그룹에 모아 중앙 인증 가드로 관리한다.
- 사용자 프로필은 특정 탭 루트가 아니라, 여러 화면에서 진입하는 독립 보호 화면으로 둔다.
- 마이페이지는 본인 계정/거래 관리 허브, 사용자 프로필은 타인 열람/대인 액션 화면으로 역할을 분리한다.
