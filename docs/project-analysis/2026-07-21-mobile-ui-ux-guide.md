# 커들마켓 모바일 앱 UI/UX 구현 가이드

## 1. 문서 목적

- 웹 프로젝트를 모바일 앱으로 옮길 때, 웹 UI를 그대로 복제하지 않고 모바일 네이티브 UX 기준으로 구현하기 위한 공통 가이드를 제공한다.
- 이 문서는 시각 디자인 시안 문서가 아니라, 앱 개발자가 레이아웃, 상호작용, 상태 처리, 플랫폼 대응을 판단할 때 참고하는 구현 가이드다.

## 2. 핵심 원칙

### 2.1 모바일 Native UX 우선

- 웹의 화면 구성을 그대로 복제하지 않는다.
- 모바일에서는 엄지존, 세로 스크롤, 스택 이동, 제스처 기반 사용 패턴을 우선한다.
- 웹의 hover, 고정 폭 레이아웃, 드롭다운 중심 상호작용은 모바일 친화 패턴으로 치환한다.

### 2.2 React Native Best Practice 우선

- 웹 전용 상호작용을 무리하게 흉내내지 않는다.
- 플랫폼 기본 내비게이션, 키보드 처리, 스크롤 동작, 탭 구조를 존중한다.
- 반복되는 UI는 공통 컴포넌트로 추상화하되, 과도한 범용화는 피한다.

### 2.3 Safe Area 필수 고려

- 상단 상태바, 하단 홈 인디케이터, 노치 영역을 항상 고려한다.
- 하단 sticky CTA, 토스트, 바텀시트, 탭 바는 Safe Area inset 위로 배치한다.
- iPhone 계열뿐 아니라 Android gesture navigation 환경도 함께 고려한다.

## 3. 레이아웃 원칙

### 3.1 기본 화면 구조

- 기본 화면은 `상단 헤더 + 본문 스크롤 영역 + 필요 시 하단 고정 액션` 구조를 사용한다.
- 목록형 화면은 세로 스크롤이 기본이다.
- 상세 화면도 가급적 단일 세로 스크롤로 풀고, 정보 밀도가 높을 때만 섹션을 분리한다.

### 3.2 폭과 여백

- 데스크톱 기준의 양 옆 넓은 여백을 유지하지 않는다.
- 모바일 기본 좌우 패딩은 일관된 spacing scale을 사용한다.
- 카드형 UI는 화면 폭을 적극적으로 사용하되, 탭 바/바텀시트/토스트와 시각 충돌이 없게 한다.

### 3.3 sticky 요소

- 자주 쓰는 핵심 액션은 하단 sticky CTA를 우선 검토한다.
- 상단 sticky 헤더는 뒤로가기, 화면 제목, 보조 액션 정도만 둔다.
- sticky 요소가 여러 개 겹치지 않게 한다.

## 4. 네비게이션 원칙

### 4.1 1차 네비게이션

- 앱의 1차 네비게이션은 `홈 / 커뮤니티 / 플레이스 / 채팅 / 마이` 5탭을 기준으로 구현한다.
- 하단 탭은 루트 허브 성격의 화면에서만 보인다.

### 4.2 2차 네비게이션

- 상세 화면은 스택 push 기반 전환을 사용한다.
- 상세에서 상세로 이어지는 흐름도 과도한 모달 중첩보다 스택 이동을 우선한다.

### 4.3 보호 화면 이동

- 로그인 필요 화면은 라우트 차단 기준으로 관리한다.
- 미인증 사용자가 보호 화면 진입 시 로그인 유도 후, 성공하면 원래 화면으로 복귀한다.

### 4.4 뒤로가기

- Android 하드웨어 back과 iOS 내비게이션 back이 자연스럽게 동작해야 한다.
- 임시 오버레이를 연 경우, 뒤로가기는 우선 오버레이 닫기에 사용한다.
- 직전 화면 복귀가 핵심인 흐름에서는 `replace`와 `push`를 혼동하지 않는다.

## 5. 상호작용 컴포넌트 원칙

### 5.1 바텀시트 우선 사용

- 신고, 차단, 로그인 유도, 선택형 액션은 바텀시트를 우선한다.
- 모바일에서 상단 드롭다운 대신 바텀시트가 기본 대안이다.
- 바텀시트는 한 손 조작이 가능하고, 액션 선택이 명확해야 한다.

### 5.2 다이얼로그 사용 기준

- 삭제, 회원탈퇴, 차단 해제처럼 파괴적 확인이 필요한 경우에만 다이얼로그를 사용한다.
- 단순 안내나 선택지는 다이얼로그보다 바텀시트나 인라인 안내를 우선한다.

### 5.3 토스트/스낵바

- 액션 결과 피드백은 토스트/스낵바를 사용한다.
- 위치는 하단 탭 또는 홈 인디케이터와 충돌하지 않게 조정한다.
- 가능하면 `재시도` 같은 짧은 액션을 함께 제공한다.

### 5.4 인라인 액션

- 폼 검증, 섹션별 실패, 개별 아이템 오류는 인라인으로 보여준다.
- 이미 보고 있던 화면 맥락을 유지하는 것이 우선이다.

## 6. 상태 표현 원칙

### 6.1 로딩 상태

- 첫 진입 로딩:
  - 화면 전체 skeleton 또는 화면 전체 loading state 사용
- 부분 로딩:
  - 리스트 추가 로드, 버튼 pending, 섹션 로딩으로 국소화
- 무한 스피너 방치 금지:
  - 특히 지도 SDK, 외부 이미지, 초기 인증 복원 등은 timeout/실패 분기 고려

### 6.2 빈 상태

- 데이터가 비어 있는 이유가 사용자에게 이해 가능해야 한다.
- 빈 상태에는 현재 화면의 목적과 다음 행동을 짧게 제시한다.
- 예:
  - 등록한 상품이 없습니다
  - 표시할 알림이 없습니다
  - 아직 채팅방이 없습니다

### 6.3 오류 상태

- 전체 화면 에러:
  - 첫 로드 실패로 화면 핵심 콘텐츠가 비어 있을 때만 사용
- 인라인 에러:
  - 특정 섹션, 폼, 액션의 실패에 사용
- 토스트/스낵바:
  - 화면 콘텐츠는 유지되고 액션 결과만 알려주면 될 때 사용
- 불변 규칙:
  - 이미 렌더된 콘텐츠는 갱신 실패만으로 덮어쓰지 않는다

## 7. 폼 UX 원칙

### 7.1 입력 구조

- 긴 폼은 의미 단위 섹션으로 나눈다.
- 필수/선택을 명확히 표시한다.
- 입력 순서가 자연스럽게 이어지도록 구성한다.

### 7.2 검증

- 가능한 한 즉시성 있는 인라인 검증을 우선한다.
- 서버 검증이 필요한 항목은 pending 상태와 결과를 분리해 보여준다.
- 에러 문구는 짧고 구체적으로 쓴다.

### 7.3 키보드 대응

- 키보드가 CTA를 가리지 않게 한다.
- 입력 중 스크롤 위치가 어색하게 튀지 않게 한다.
- 멀티라인 입력, 숫자 입력, 이메일 입력 등 키보드 타입을 적절히 선택한다.

## 8. 목록/상세 화면 원칙

### 8.1 목록 화면

- 필터, 정렬, 검색은 상단에 모으되 화면을 과도하게 차지하지 않게 한다.
- 무한스크롤은 가능하지만, 로딩 피드백과 끝 상태를 명확히 준다.
- 카드 액션이 많으면 카드 전체 탭과 개별 액션 탭의 충돌을 피한다.

### 8.2 상세 화면

- 핵심 정보는 상단에 배치한다.
- 주요 CTA는 하단 엄지존에 배치한다.
- 부정 액션은 상단 케밥 메뉴 뒤로 숨긴다.

## 9. 화면별 우선 적용 패턴

### 9.1 홈/커뮤니티/알림

- 리스트 중심 화면
- 상단 필터/검색 최소화
- 무한스크롤과 빈 상태를 명확히 구분

### 9.2 상품 상세/사용자 프로필

- 상세 정보 + 하단 sticky CTA
- 긍정 액션 우선 노출
- 신고/차단은 상단 액션 메뉴 뒤

### 9.3 채팅

- 채팅방 목록과 채팅방 상세를 스택 구조로 분리
- 입력창은 키보드와 함께 자연스럽게 이동
- 이미지 전송 실패는 인라인 또는 스낵바로 처리

### 9.4 지도

- 화면 자체는 계속 살아 있어야 함
- 데이터 실패가 곧 전체 화면 실패가 되지 않도록 처리
- 재검색 액션은 눈에 잘 띄는 위치에 유지

### 9.5 마이페이지/프로필 수정

- 관리형 화면
- 정보 확인보다 액션 흐름이 중요
- 편집/탈퇴/차단 관리 같은 액션은 명확히 분리

## 10. 플랫폼 대응 메모

### 10.1 iOS

- Safe Area 상하단 inset 반영
- 스와이프 back 제스처 방해 금지
- 바텀시트와 modal presentation이 과도하게 겹치지 않게 함

### 10.2 Android

- 하드웨어 back 동작 정의 필요
- gesture navigation 환경에서 하단 sticky 요소 충돌 방지
- toast/snackbar 위치가 system navigation과 겹치지 않게 조정

## 11. 금지에 가까운 패턴

- 웹 드롭다운을 모바일에서 그대로 재현
- 작은 아이콘만으로 중요한 액션을 숨김
- 전체 화면 에러로 이미 본 콘텐츠를 덮어쓰기
- 키보드가 CTA나 입력창을 가리도록 방치
- 안전영역을 무시한 하단 버튼/토스트 배치
- 동일 화면에서 모달 위에 또 모달을 중첩
- 웹 전용 hover 의존 인터랙션 복제

## 12. 구현 체크리스트

- Safe Area 반영 여부
- iOS/Android back 동작 정의 여부
- 하단 탭 표시/숨김 조건 반영 여부
- sticky CTA와 키보드 충돌 여부
- 토스트/바텀시트/다이얼로그 사용 기준 준수 여부
- 인라인/전체화면/토스트 에러 구분 적용 여부
- 로딩/빈 상태/오류 상태가 모두 정의되어 있는지
- 로그인 필요 액션의 유도 방식이 정책과 일치하는지
